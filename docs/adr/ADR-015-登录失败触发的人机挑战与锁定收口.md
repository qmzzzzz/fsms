# ADR-015 登录失败触发的人机挑战与锁定收口

- 状态：已接受
- 日期：2026-10-31
- 关联：审计一-2（登录防爆破未收口）、审计二-2（管理员重置口令是否写口令历史）、审计二-3（失败尝试是否留痕——裁决取「落库留痕」，见决策 7）

## 背景

登录链此前有三道独立的防线，但**没有一道把"失败到一定次数"变成一道必须跨过的台阶**：

1. **图形验证码**：静态开关，`LOGIN_CAPTCHA_ENABLED` 未设即 `false`，系统配置表无记录时
   同样回落 `false`（`models/SystemConfig.captchaSwitch('login')`）。默认部署下它是**关的**，
   于是"前端有验证码"这件事在默认部署里等于不存在。反向缺陷也真实存在：把它改成默认开启
   会让所有既有部署的自动化客户端（脚本、k6、e2e、内网集成）一次性登不上——开关的默认值
   本身就是产品决策，不是安全缺陷的修法。
2. **账户级临时锁定**：连续失败 10 次写 `User.lockUntil`（10 分钟）。触发条件只需要**知道用户名**，
   不需要口令正确、也不需要过人机验证：任何人对任意已知账户连发 10 次错口令，
   就能让账户主人在窗口内**完全登不进来**（可用性 DoS），而这 10 次尝试的成本接近零。
3. **单 IP / 单账号限流**：`loginLimiter`（单 IP 10 次/15 分钟）与 `loginUserLimiter`
   （单账号 20 次/15 分钟）挡的是"速率"，挡不住"分布式换 IP"与"恰好压在阈值下"。

三者叠加的结果是：**默认部署下，登录链没有"越试越难"的台阶**——失败前 10 次都是同一种廉价尝试，
第 10 次之后账户被锁（而这次锁定同时是攻击者的收益）。

## 决策

1. 新增判据模块 `src/services/loginChallenge.js`：`isChallengeRequired(username)` 数
   **同一用户名**在窗口（15 分钟，与凭据型限流窗口对齐）内、**自最近一次成功登录起算**的
   连续失败次数，达到 `CHALLENGE_AFTER_FAILURES = 3` 即要求人机验证。
2. 计数走 `AuditLog` 的 `login_failed` / `auth_failed`（与 `securityAlert.checkBruteForce`
   同一批动作、同一 collation），**不读 `User.failedLoginCount`**。
3. 闸门接在 `authService.resolveLoginPassword`：静态开关**或**挑战判据任一成立就要求验证码；
   验证码通过才进入口令解析与比对。
4. 判据读取失败 ⇒ **fail-closed**（按"需要挑战"处理），并 `logger.warn` 留痕。
5. `assertAccountUsable` 的临时锁定分支新增 `captchaVerified` 放行臂：本次已过人机验证的
   请求继续走口令比对（口令错仍是统一的 401），使锁定窗口对**账户主人**不是硬墙。
6. `lockUntil` 的写/清语义**不变**：写入阈值仍是 `MAX_FAILED_LOGINS`，仍只由
   `failedLoginCount` 推进；`middleware/auth.js`、令牌刷新、WebSocket 三处门禁照旧按
   `lockUntil` 拒绝；管理员的解锁/禁用动作不变。
7. **闸门拦下的尝试落库留痕**（审计二-3 裁决取「落库留痕」）：`loginChallenge.recordCaptchaRejected`
   写一条**独立动作** `login_captcha_rejected`（`category: auth`、`success: false`、`riskLevel: medium`），
   `reason` 记录"是哪一层要求的"：`captcha_switch`（静态开关）或 `challenge_required`（失败触发的挑战）；
   `riskFactors` 记录"没带验证码"（`captcha_absent`）还是"带错"（`captcha_mismatch`）。
   **该动作不进任何失败计数**——既不在 `loginChallenge.FAILURE_ACTIONS`，也不在
   `securityAlert.checkBruteForce` 的统计动作里。写入跟随"关键审计"纪律：
   `await awaitAuditWrite(...)` 有界等待（审计库卡住不把登录接口挂死），写失败走
   `onAuditWriteFailure`（error 日志 + `audit_write_failed{high}`），对外口径仍是 400 `CAPTCHA_INVALID`。

## 理由

- **判据必须与"账户是否存在"无关**：本仓在"用户不存在"分支同样写失败审计（防止借不存在的
  用户名绕开暴力破解检测），所以用审计行计数天然让两条路径同口径。改用 `User.failedLoginCount`
  会让"是否要验证码"变成用户名存在性预言机——不存在的用户名永远不触发挑战，
  这恰好是审计里另一条（`assertAccountUsable` 的 423+精确分钟数）花力气堵掉的东西。
- **为什么闸门拦在口令比对之前**：拦在这里，被拦下的尝试**不推进** `failedLoginCount`、
  也不写任何失败计数行（`login_failed`/`auth_failed`；它落的是另一种动作，见决策 7）。于是"连续失败 10 次"这个锁定入口对**拿不到人机验证的人不可达**，
  攻击者既无法批量爆破，也无法把已知账户推进锁定窗口。反之若只把验证码加在"进入比对之后"，
  失败计数仍会照常推进，DoS 面原样保留。
- **为什么阈值是 3 而不是 10**：10 是锁定阈值，等它到了再要求验证码等于把"锁定"当成前置层，
  而锁定本身是攻击者的收益。3 次在正常用户输错口令的分布里很少见（连错 3 次已经需要提示），
  同时把自动化尝试的成本从第 4 次起抬到"一次人机验证"。
- **为什么 fail-closed**：判据读不到（Mongo/审计不可用）时登录链的其他依赖同样不可用
  （它要查 User、要写审计、要查锁定），此时"要求验证码"只是多一步人机验证；
  而 fail-open 会把一次存储抖动变成"防爆破闸门整体消失"。这与幂等中间件的 fail-open
  （见 ADR-014）方向相反，原因也相反：那里丢的是去重便利，这里丢的是**唯一性判据**。
  因为不放行任何请求，本项**不进** `failOpenSites` 台账（该台账登记的是"降级即放行"的位点）。
- **为什么给锁定分支开放行臂**：只做 ①② 而不动 ③，等于承认"知道用户名就能锁死账户主人"
  仍然成立——攻击者只要愿意过人机验证（成本极低），仍可反复锁人。开放行臂后，账户主人
  凭正确口令能进；攻击者过人机验证后能做的只是继续试口令，而被试错的口令会**推进计数**，
  一旦再达阈值，锁仍成立（并且他要继续过人机验证）。即：**锁定从"拒绝一切"变成"拒绝不合作者"**，
  这既保住 `lockUntil` 作为审计信号的价值，也去掉了它对主人的可用性伤害。
- **外部口径不变**：所有拒绝仍是同一个 401 `AUTH_INVALID_CREDENTIALS`，验证码失败仍是既有
  `CAPTCHA_INVALID`（400）。不放行任何新错误码，也不在响应里透露"账户被锁定"。

## 备选方案

| 方案                                     | 不采纳的原因                                                                                                                                                  |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 把 `LOGIN_CAPTCHA_ENABLED` 默认改成 true | 一次性打断全部既有自动化客户端（脚本/k6/e2e/内网集成），且"验证码常开"对正常用户是纯负担                                                                      |
| 登录侧验证码开关改为生产 fail-closed     | 把 Redis/Mongo 抖动传导成"没人能登录"，与可用性目标冲突（`failOpenSites` 已记录该取舍）                                                                       |
| 用 `User.failedLoginCount` 做挑战判据    | 不存在的用户名永远不触发 ⇒ 用户名存在性预言机（见上）                                                                                                         |
| 只加验证码、不改锁定分支                 | 攻击者愿意过人机验证时 DoS 仍成立（见上）                                                                                                                     |
| 直接取消账户级锁定                       | 丢掉一条真实信号（"有人正在暴力破解这个账户"），且 `middleware/auth.js` / 令牌 / WS 三处门禁与审计动作 `account_temp_locked` 都要跟着改，判据收益远小于动作面 |
| 挑战判据放进程内存                       | 本仓虽单进程部署，但"单进程"是部署形态的偶然事实；扩容或滚动升级即静默失效（同 ADR-014 的推理）                                                               |

## 后果与局限

- 每个登录请求多两次审计查询（一次"最近一次成功"、一次"窗口内失败计数"），都走
  `username_ci_timestamp` 索引；量级与登录本身同阶。审计写入本身是旁路（`AuditLog.record` 失败
  只告警不阻断），因此"失败没记上"会让挑战与爆破检测同时低估——这是既有盲区，本决策不放大也不消除。
- 判据是"连续失败"：窗口内成功登录一次即清零（自成功时刻起算）。这让"主人刚登录成功、
  别人还在试"的场景不会立刻要求验证码；代价是攻击者若恰好与主人交替登录会重置计数——
  但那种场景已经需要口令正确，不属于本项要堵的路径。
- `captchaVerified` 放行臂让"锁定中的账户"在请求层面继续跑 bcrypt：对每个已过人机验证的请求
  多一次口令比对，属于预期成本；未过人机验证的请求仍然在锁定分支被拒（且不计入计数——
  它们不是"口令错"，而是"账户被锁"）。
- 前端的"补渲染验证码区"依赖错误码 `CAPTCHA_INVALID`：若后续把挑战改成独立错误码，
  `LoginView.vue` 的 catch 分支与 `login.captchaChallengeRequired` 文案必须同步改。
- **闸门拦下的尝试此前零留痕**（本决策原先接受的观测缺口，审计二-3 已裁决为「落库留痕」，见决策 7）：
  现在它写 `login_captcha_rejected`，因此"尝试被人机层拦下"（有该动作的行）与"口令错"
  （有 `login_failed`）在审计库里可分辨，且两者的**计数口径仍只有后者**。
  残留：① 该行只说明人机验证没过，区分不出"真人输错"与"脚本"——那需要前端行为埋点，本仓没有；
  ② 它不进失败计数，所以审计里"被撞闸门的次数"不反馈到闸门自身（这是刻意的：见到次数才收紧，
  等于让攻击者用廉价请求把某个用户名永久推向"必须过验证码"——那正是决策 4 的反面）。
  （2026-11-04 修订：② 的顾虑针对的是"反馈进失败计数、随次数无条件收紧"；同日修订把该动作
  用作**有界粘滞判据**，语义不同，见下方修订节。）

## 修订（2026-11-04）：粘滞挑战与对端维度限流桶

- 状态：已接受（修订首版决策）
- 日期：2026-11-04
- 触发：渗透测试实测（对 admin 账户的口令枚举演练）：429『登录尝试次数过多』在冷却窗口结束后
  **恢复 401 口令校验**；轮换 `X-Forwarded-For` 可重置 per-IP 计数；验证码字段在闸门未触发时
  任意串可通过。三者叠加构成对单账户的持续口令枚举路径。当日尚有另一份观测（#1332
  「账户级闸门持久生效」）与本观测矛盾，经核对确认差异来源正是 429 冷却窗口与判据窗口的
  相对长短——以可复现的观测为准，闸门按"可被持续绕过"处理。

### 修订决策

1. **挑战粘滞化**：`isChallengeRequired` 在原"窗口内连续失败 ≥ 3"之外，新增粘滞判据——
   粘滞窗（`LOGIN_CHALLENGE_STICKY_MS`，默认 6 小时，夹取 [1min, 7d]）内存在本闸拦下的痕迹
   （`login_captcha_rejected` 行，阈值 ≥ 1）即持续要求人机验证。两条判据共用同一个清零点：
   **最近一次成功登录**——账户主人过一次人机验证并登录成功，粘滞即解除。
2. **登录路由新增对端维度桶** `loginPeerLimiter`：组键取**不可伪造的 socket 对端**
   （`req.socket.remoteAddress`），阈值 300 次/15 分钟（只数失败尝试）。它不是 IP 桶的替代：
   真反代下对端是全体客户端共享的代理地址（故阈值取聚合口径且成功不计入）；直连伪造 XFF 时
   对端就是攻击者自己（故轮换转发头不再换桶）。
3. **升级分类登记**：`login-peer` 归入只告警的 AUTH 类（不自动封 IP）——真反代下自动封对端
   等于把枚举噪音放大成全站拒绝服务，与静态面桶不接封禁阶梯是同一条纪律。
4. `.env.example` 补 `LOGIN_CHALLENGE_STICKY_MS` 文档；回归判据：
   `src/tests/services/loginFailureChallenge.test.js`（D 组：粘滞生效/成功清零/静默满窗回落）、
   `src/tests/security/loginPeerBucketXffRotation.test.js`（轮换 XFF 不得重置按来源计数）、
   `src/tests/services/rateLimitEscalation.test.js`（login-peer 必须留在不封 IP 的类别）。

### 修订理由（与首版②的顾虑正面相对）

- 首版拒绝让"被拦次数"反馈到闸门的理由是**可用性 DoS**：廉价请求可以把任意用户名永久推向
  "必须过验证码"。实测枚举路径成立后，天平的另一端变成了**口令枚举本身**——两者都要权衡，
  修订取的是中间形态：
  - 粘滞的**上限**就是"要求验证码"——闸门本来就施加的同一档摩擦，不再随被拦次数加码
    （首版顾虑的"见到次数才收紧"的阶梯不存在）；
  - 粘滞**可被账户主人单方面解除**（一次成功登录），攻击者刷不比"要求验证码"更强的拒绝效果；
  - 失败计数口径**保持不变**（`login_captcha_rejected` 仍不进 `FAILURE_ACTIONS`、不进
    `lockUntil`）——"被拦次数反馈进失败计数"这条首版明确拒绝的形态，本修订没有采用。
- 对端桶之所以必要：trust proxy 的回环兼容档（development 默认一跳）与显式
  `TRUSTED_PROXY_CIDRS` 部署里"能直连应用端口的主体"都能自写 XFF——这是 ipUtils 已登记的
  「TRUSTED_PROXY 可用但不可区分」残余，应用内无法把"真反代转来的客户"与"直连伪造者"分开，
  唯一不可伪造的量是 TCP 源地址。聚合阈值 + 只数失败 + 不自动封 IP，把误伤面压到
  "持续 20 次/分钟失败"的异常流量上。
- 查询成本：判据由两次审计查询变为三次（最近一次成功改为不限窗、失败计数、粘滞计数），
  同走 `username_ci_timestamp` 索引，量级不变。

### 修订后的残余

- 攻击者仍可让任意用户名**长期处于"登录要过验证码"**状态（持续发包即可维持粘滞）——
  这是接受的残余：主人登录只多一步人机验证，且成功即解除；对比修订前"429 冷却后口令校验
  恢复、可持续枚举"，方向是正确的。
- 对端桶在真反代下是聚合口径：桶触顶时整个来源（含正常用户）最多 429 到本窗口结束。
  缓解靠分层——枚举本身由 IP 桶、账号桶、粘滞挑战闸与自动封禁分层承担，对端桶只在
  前两者被请求方可控字段绕开时兜底。
- `login-peer` 的升级信号按 punishIp 记在 reportedIp（TRUSTED_PROXY 裁定）上：直连伪造者
  轮换 XFF 时该信号同样随之轮换，只有对端桶的 429 日志（打印 socket 对端）是稳定定位点。
  把升级信号的惩罚目标改到对端需要动 `resolvePunishableIp` 的裁定语义，超出本修订范围。
