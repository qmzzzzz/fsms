# ADR-004：审计链单进程锁假设

- **状态**：已接受（附规模化前提）；**进程内锁部分已由 A-1 落地取代**，见「后果与局限」的复核注记
- **日期**：2026-08-29（追溯建档）
- **涉及**：`src/utils/auditChain.js`（`withChainLock`）、`src/constants/runtime.js`（`assertSingleProcessAssumptions`）、优化清单 A-1 / R-3

## 背景

审计链是追加写结构：写一条新记录需「读当前链尾哈希 → 以它为 `prevHash` 计算新哈希 → 写入」。若两个写操作并发交错，会各自读到同一个链尾、算出两条 `prevHash` 相同的记录，造成**链分叉**——后续校验无法判定哪条是真，审计完整性被破坏。

## 决策

以**进程内互斥锁**串行化链写入：`withChainLock()` 用 Promise 队列把「读尾→算→写」变成临界区（`src/utils/auditChain.js`）；带 `CHAIN_LOCK_TIMEOUT_MS`（默认 15s）超时保护，超时强制释放并置 `chainTailLoaded=false`，令下次写入从数据库重新同步链尾。

单进程假设集中声明于 `src/constants/runtime.js` 的 `assertSingleProcessAssumptions()`（启动期由 `src/index.js` 调用校验）：

> 本锁仅在单个 Node 进程内有效。多实例/多 worker 部署会各自维护独立链尾，必然产生链分叉。

（该引文原内联于 `auditChain.js`，已随 A-1 落地迁至上述集中声明处。）

## 理由

- 当前部署形态是**单容器单进程**（`docker-compose.yml` 中 `app` 服务单副本），进程内锁已足够保证链的线性。
- 相比引入外部锁组件，进程内锁零依赖、零网络开销、无额外故障面，与当前规模匹配。

## 备选方案

- **数据库原子操作**：用 `findOneAndUpdate` 等条件更新替代「读-改-写」，把原子性下推到 MongoDB；无需外部组件，但链尾的读改写语义较难完全原子化。
- **Redis 分布式锁**：跨实例互斥，是规模化后的目标方案（优化清单 A-1），依赖 Redis 先行落地（R-3）。
- **唯一索引 + 冲突重试**：对 `prevHash` 建唯一索引，冲突即重读重试；实现乐观并发，但高并发下重试放大。

## 后果与局限

- **规模化硬前提**：一旦多副本/多 worker 部署，本锁失效、链会分叉。因此「迁 Redis 分布式锁（A-1）」是扩容前的必做项，与限流/缓存迁 Redis（R-3/M-1）同批。
  > **2026-09-28 复核注记**：A-1 已落地。`withChainLock()` 在进程内锁就绪后叠加 `sharedCache.acquireLockBlocking()` 的跨实例锁（`CHAIN_LOCK_KEY`），链尾亦外置共享（`CHAIN_TAIL_KEY`）；配置 `REDIS_URL` 时多副本不再各自维护链尾，且拿不到锁时**绝不无锁推进链尾**（标记链尾失效 + 本批回退）。本条前提仅对未配 `REDIS_URL` 的部署成立。
- **单进程内的超时兜底**：锁超时强制释放 + 链尾重同步，牺牲一次严格串行换取不死锁，属可控取舍。
