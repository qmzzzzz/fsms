# ADR-013 蜜罐账户与诱饵登录

- 状态：已接受
- 日期：2026-10-31
- 关联控制项：《FSMS 安全设计方案 v2》G 系列（欺骗与反侦察方向的自建能力）

## 背景

本仓原有的「幽灵账号」能力（`services/canaryWatch.js`）只在**用户名不存在**这条分支上工作：
登录时如果有人用了 `CANARY_USERNAMES` 里的名字，系统按「用户名或密码错误」统一 401，
但会记一条 `canary_username_attempt` 高危审计。它抓的是「有人在猜名字」这一层。

它有两个结构性空白：

1. **没有可交互的对象**。哨兵名在库里不存在，任何口令都进不去，攻击者再做多少轮也拿不到
   任何反馈；系统只能看到一个名字被念过一次。
2. **没有可归属的行为面**。真正的入侵者往往是拿着**一份泄露口令字典**在撞：他会用真实存在过、
   且口令已经在别处泄露的账号去试。这条路径上系统现在只有「密码错误 ×N」的记录，
   无法区分「内部人忘了密码」与「外部人拿字典在撞」。

需求因此明确：把「幽灵账号」升级成**真正的蜜罐**——一个**真实存在**、**口令看起来对**、
登录会**成功**的账户；攻击者一旦进来，行为、来源、指纹全部留痕并即时告警，
而这个账户在**所有枚举面**上都不存在。

落地时还受本仓治理面约束（这些都是硬约束，不是偏好）：

- **注释密度棘轮**：`scripts/commentDensity.js` 对 `src/**` 只许降不许升，当前水位零余量 ⇒
  改动的生产代码**不能新增整行注释**（约束写在代码上下文里，理由写进本篇 ADR，见 ADR-011）。
- **枚举面台账**：新增任何 `User.find/countDocuments/aggregate/distinct` 站点，
  要么带排除判据、要么登记说明为什么不带（否则 CI 红）。
- **告警/审计登记型门禁**：新告警类型必须叶子枚举并 spread 进 `ALERT_TYPES`、
  新审计动作必须登记进 `AUDIT_LOG_ACTIONS`、`dispatchNotification` 必须静态引用 `ALERT_TYPES.<KEY>`。
- **单进程清单**：模块级 `Map`/`Set` 必须登记进 `constants/runtime.js` 与 `REQUIRED_MODULES`。
- **测试钩子台账**：`_`/`__` 前缀的生产导出要有人消费并逐一登记（本批把计数从 36 提到 37，随后为事件链巡检的复位钩子再提到 38）。
- **行号锚点台账**：注释里引用的行号有专门门禁（裸锚/署名锚），改动会牵动登记项。

## 决策

1. **真相在数据里，不在环境变量里**：`User` 增加 `isHoneypot`（Boolean，默认 `false`）。
   「这是陷阱账户」由库中的标志位唯一决定；`HONEYPOT_USERNAMES` 只负责**物化**用哪些名字，
   改名单不会让既有的陷阱账户变成普通账户。
2. **名字与哨兵名分开**：默认名单 `sysadmin`（`constants/honeypotAccounts.js`），与 10 个默认哨兵名
   **零交集**，且明确不含 `admin`（本仓默认超管名）。哨兵名继续表示「不存在的名字」，
   蜜罐名表示「存在的账户」；两者交集会在启动期以 info 报告出来，并在哨兵遮蔽对账里被排除。
3. **物化挂在系统初始化**：`services/initData/index.js` 的 `initializeSystem()` 里
   `honeypotWatch.init()`（与 `createDefaultAdmin` / `reconcileSuperAdmin` 同层：都是「启动期写 users 的数据任务」）。
   幂等：已存在且已打标的账户记「沿用」，不重复建号；被**真实账户**占用的名字记错误并拒绝接管。
4. **总开关 fail-closed**：`HONEYPOT_ENABLED` 只认真值词表（`true/1/yes/on`，大小写与空白无关）。
   关闭时：不物化、不接管诱饵登录（即使库里已有打标账户）；**但枚举面排除照旧生效**
   （一个已经存在的诱饵账户绝不能因为关开关就冒出来）。
5. **诱饵口令判据 = 泄露口令词干命中**：`isLurePassword()` 复用 `isBreachedPassword()` 的词干表。
   不是「任意口令都放行」——只有攻击者字典里那种口令才会触发陷阱。
6. **放行走与真实登录同构的路径**：命中诱饵口令时，先 `consumeDummyPasswordTime()` 消耗一次
   等量 bcrypt 时间，再调用与真实登录完全相同的 `issueLoginSession()`。
   于是成功登录的**响应形状与耗时都与真实登录一致**；账户 `roles: []`、`status: 'active'`、
   `mustChangePassword: false`、无手机号、邮箱落在保留域 `honeypot.invalid`。
7. **不命中则完全走原路**：口令没命中泄露词干时，这次尝试进入既有的失败路径
   （计数、锁定、`checkBruteForce`、统一 401），不新增任何可见差异、不发生第二次 bcrypt。
8. **留痕两件套**：审计动作 `honeypot_login`（`category: 'auth'`，`riskLevel: 'critical'`，
   `riskFactors` 含 `honeypot_account_login` / `deceptive_account_interaction` 与来源归属因子，
   `body.honeypot` 记账户名）；告警类型 `HONEYPOT_LOGIN`（→ `honeypot_login`），
   **每账户每日一条**（模块级去重表），避免攻击者用成功率换告警风暴。
9. **枚举面排除的一致性**：`HONEYPOT_EXCLUDED_FILTER`（`{ isHoneypot: { $ne: true } }`）
   在 `constants/honeypotAccounts.js` **单一声明**，调用方一律经 `withHoneypotExcluded()` 展开
   （展开顺序固定，调用方覆盖不掉）。已接线：用户列表/计数/统计聚合、角色成员计数与列表、
   审计范围过滤、哨兵遮蔽对账。
10. **默认不外泄**：`isHoneypot` 同时进 `USER_RESPONSE_EXCLUDE_FIELDS` 与 PII 可见投影的排除列
    （对 `anonymizeUserForOthers()` 这类「PII 可见」响应也同样排除）。
11. **CI 把枚举面钉住**：`src/tests/ci/honeypotExclusionLedger.test.js` 扫描全仓
    `User.find/countDocuments/aggregate/distinct` 站点，分成「必须带判据」与「登记为不带判据」两清单，
    双向比对（新增站点必须表态、登记项必须仍有出处），并自证扫描规模非空、判据非空转。

## 理由

- **为什么要真账户，而不是只留名字**：只有存在且口令可猜的账户才能把「一次猜名字」变成
  「一次完整的失败尝试 + 一次成功的入侵尝试」，后者能给出设备指纹、来源 IP 归属、尝试序列，
  信息量差一个量级。
- **为什么判据是「泄露词干」而不是「任意口令」**：任意口令放行会把「手误打错的真实用户」也送进陷阱，
  既污染情报又制造误报；而泄露词干恰好是撞库字典的特征，且**攻击者不可能事先知道**这个判据。
- **为什么给零角色会话**：蜜罐的任务是「让人进来、把行为留下」，不是「让人干活」。
  零角色让爆炸半径为零（后续每个接口都 403），而这些 403 本身就是「有人在探索权限」的信号；
  同时会话是**真会话**（真 token、真 refresh、进 `UserSession`），所以攻击者看到的证据链是自洽的。
- **为什么口径与真实登录完全同构**：蜜罐最容易被识破的地方是「成功登录却比正常登录快/慢」
  或「响应体缺字段」。因此路径上只加了一次等量 bcrypt 与一次普通会话签发。
- **为什么排除判据只写一份**：`$ne: true` 若在十几处各写一遍，早晚有人写成 `$exists: false`
  或漏写，蜜罐就会从某个导出、某个统计、某个角色成员表里冒出来。单一声明 + 台账闸把这件事
  变成「新增站点必须表态」的机械判断。
- **为什么物化挂 `initializeSystem()`**：它是本仓唯一的启动期数据任务入口（权限、角色、超管、索引、TTL），
  再挂一个新的启动钩子会多一处「忘了调用」的可能；且它 `await` 在接流量之前完成，
  保证第一次探测就会落到「存在但口令不对」而不是「账户不存在」。
- **为什么开关同时管物化与放行**：只做一个方向的开关会制造最糟的组合——
  「已有打标账户 + 关闭放行」是安全的，「不物化 + 已存在账户仍放行」也不危险，
  但为了让语义可推理，统一成「关 = 不新增、不放行、但仍然隐藏」。
- **为什么行号锚点要跟着改**：本批在 `login.js`（模块头 +1、登录链 +15）与 `initData/index.js` 有插入，
  触碰了三个登记项（裸锚台账的 login.js 条目、`profile.js` 的指代目标、凭据门台账的两处引用）；
  不改就等于把错行号固化进源码，这正是那些门禁存在的意义。

## 边界情况与处理

| 场景                                      | 处理                                                                               | 为什么不是别的做法                                                                     |
| ----------------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 诱饵名已被**真实账户**占用                | 拒绝接管，启动日志报错，绝不把该账户打标成蜜罐                                     | 打标等于把一个真人的账户变成陷阱：他的口令会被当作诱饵判据，且会被枚举面隐藏           |
| 诱饵名落在 `CANARY_USERNAMES` 里          | 启动期 info 提示接管关系；哨兵遮蔽对账**不**把它算作遮蔽                           | 遮蔽的定义是「哨兵名被真人账户占用，导致哨兵失效」；被蜜罐占用是**有意升级**，不是失效 |
| `HONEYPOT_USERNAMES` 有重复项             | 去重（归一化后比较）                                                               | 重复会在日志里制造噪音，且让「名字数 = 账户数」的对账失去意义                          |
| 环境变量里有空条目（如尾随逗号）          | 逐条记 `errors`，其余条目照常生效                                                  | 静默忽略会让「我明明配了 3 个名字」无法对账                                            |
| 环境变量全无效                            | 回退默认名单，并把 `fromEnv` 记为 false、`errors` 记原因                           | 静默变成「名单为空 = 没有蜜罐」是最危险的失败方式：看起来一切正常                      |
| 名字不满足 `User` schema（长度/字符规则） | 物化阶段捕获为错误，不抛异常、不中断启动                                           | 启动崩溃会把「配错名字」升级成「服务不可用」                                           |
| 打标账户被启用 MFA                        | 诱饵放行**关闭**（该账户走正常 MFA 流程）                                          | 蜜罐绝不能成为绕过第二因素的通道                                                       |
| `HONEYPOT_ENABLED` 未设置/为假            | 不物化、不放行；已存在账户仍在枚举面被排除                                         | 缺省即关闭符合「默认不开新能力」；隐藏不跟着关，避免开关一关陷阱账户就暴露             |
| 名字大小写/空白差异                       | 与哨兵共用同一份归一化（trim + 小写）                                              | 两套大小写规则迟早会在「`SysAdmin` 是否算命中」上打架                                  |
| 命中诱饵口令后又用错口令                  | 记第二次审计（`honeypot_login`），告警仍按「每日一次」抑制                         | 审计要完整、告警要可用；两者目的不同，不能用同一个闸门                                 |
| 蜜罐账户被删除/改名/被匿名化批处理        | 相关批次与超管对账的过滤器**必须仍然看得到**蜜罐行（已登记为「不许排除」）         | 对账看不到 = 陷阱悄悄消失，且下次启动会以「未打标但名字被占用」报错                    |
| 蜜罐日志/统计出现在运维面板               | 面板只保留「关键告警 + `honeypot_events_total` 计数」，不进用户/角色维度的常规报表 | 常规报表会被运维当成脏数据清理，进而暴露或删掉陷阱                                     |
| 多实例                                    | 去重表是进程内 Map（单进程清单已登记），跨实例可能各发一条                         | 为蜜罐引入共享状态不划算；重复告警的代价远小于漏告警                                   |

## 备选方案

| 方案                                     | 结论                            | 理由                                                                                                                                     |
| ---------------------------------------- | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 直接复用 `CANARY_USERNAMES` 建号         | 采纳（2026-10-31 改判，见 P1d） | 原判「哨兵信号当场消失」成立，但当时只算了代价没算收益：蜜罐换来一个可交互的会话与撞库覆盖，且接管是**逐条登记**的有意决策，不是默认漂移 |
| 任意口令都放行                           | 否决                            | 把真实用户的输入错误也算作入侵，情报被污染、告警被淹没                                                                                   |
| 给蜜罐账户真实（受限）权限，看它能走多远 | 否决                            | 需要一整套「假权限也要自洽」的维护面，且任何一处判漏就是真实越权                                                                         |
| 蜜罐账户出现在列表里，仅标记为只读       | 否决                            | 运维会把它当僵尸账号清理；攻击者也能一眼识别                                                                                             |
| 用定时任务物化                           | 否决                            | 多实例重复执行、启动到首次执行之间有空窗；启动期数据任务已有现成入口                                                                     |
| 关闭开关时仍放行诱饵登录                 | 否决                            | 那是 fail-open：关开关本意是「停用该能力」                                                                                               |
| 把理由写成生产代码注释                   | 否决                            | 注释密度棘轮零余量；且本仓的注释约定是「只留当前约束」，理由归 ADR（ADR-011）                                                            |

## 后果与局限

- **抓不到「持有真实凭据」的攻击**：蜜罐只覆盖撞库/猜口令这一类。持有合法凭据的入侵
  由审计链（ADR-002）、异常检测与 IP 黑名单负责，本能力不与之重叠。
- **需要运维确认这些名字仍在自己手里**：默认名单 = `sysadmin` + 10 个哨兵名 + `admin`（超管名自动剔除，
  改名后生效）。其中若有真实账户，物化阶段会因「已被真实账户占用」而拒绝接管并 fail-loud 报错。
- **判据是启发式的**：`isLurePassword` 命中泄露口令词干表，未命中的字典（长随机串、
  针对性猜测）会走普通失败路径，只留失败计数。这是有意的：宁可少抓，不要误抓。
- **告警去重是进程内**：多实例部署下同一账户在同一天可能收到多条告警（每实例一条）。
- **能力本身需要在生产打开**：默认 `HONEYPOT_ENABLED` 未设置 ⇒ 只物化逻辑存在但不会启用
  （本批只做 P0，见下节）。
- **本批付出了行号锚点的维护成本**：三个登记项随本次插入同步改对；再往 `login.js` 插入代码时
  仍需重复这个动作，这是本仓行号锚点门禁的固有代价。

## P1 影子数据面（本批已落地）

P0 只解决「进来」，P1 解决「进来之后能看到什么、留下什么」。这里的核心判断是：
**陷阱会话的可信度与真实数据的零泄漏，必须由同一个接线点同时保证**——绝不能靠「每个路由自觉」。

1. **单点改道**：`middleware/auth.js` 的 `authenticate` 在 `req.user` 就绪处调用
   `services/honeypotDecoy.js` 的 `steer(req, res)`。诱饵会话的请求在这里分流，
   真实控制器与 RBAC **一律不参与**。判据只看身份上下文里的 `isHoneypot`
   （`authenticate` 从库里读、token 载荷不可信）。
2. **三档判定**（`constants/honeypotDecoy.js` 单一声明）：
   - `decoy`：只读（GET/HEAD）且落在已登记的合成集合前缀内 ⇒ 返回合成数据；
   - `passthrough`：`POST /api/auth/refresh`、`POST /api/auth/logout`、`GET /api/version`
     ——会话自身的续期/登出与公开版本号，不读业务集合，放行以免把攻击者提前赶走；
   - `deny`：其余一切（含**所有写方法**与未知路径）⇒ 用与真实 403 **同一个**
     `ApiResponse.codeError(res, 'PERMISSION_DENIED')` 构造响应，错误体逐字相同。
3. **合成数据**：用户/角色/权限/设备/报警/巡检/报表七张表 + 汇总，全部**启动即冻结**、
   每次响应物化新副本（源数据不可被请求改写）；id 一律以 `hp-` 开头，
   与真实 ObjectId（24 位十六进制）形态必然不相交；计数由列表长度派生（不会出现「列表 6 条、总数 9 条」）。
   时间戳存的是**相对偏移**，出参时按当前时刻物化——数据冻结、呈现随时钟走。
4. **呈现层**：诱饵登录响应里的角色/权限换成合成集合（`decorateLureSession`），
   否则「管理员登录却零角色」是最刺眼的破绽。这只改外观：授权判定不看它，
   因为该会话的每个请求都在第 1 条那里被改道。
5. **留痕**：每个被接管的请求写一条 `honeypot_probe` 审计（写尝试 `critical`、只读 `high`，
   body 记 `{honeypot, verdict}`），并以 `honeypot_probe` 告警按类别每账户每日一条
   （与登录告警共用同一张当日表，键含类别互不挤占）。
6. **接线台账**：`src/tests/ci/honeypotDecoyLedger.test.js` 把 `app.js` 的挂载前缀与合成集合
   双向对齐（少一个 = 有前缀没数据面，多一个 = 僵尸表），不承接数据面的前缀必须逐条登记理由，
   放行白名单逐条钉死（多一条少一条都红）。

**P1 的边界**：开关关闭时老会话不被接管（回落常规 RBAC，但绝不因为关开关就放行）；
非蜜罐会话与未认证请求完全不进这条路径；放行白名单不含任何写业务方法；
合成的 403/404 与真实语义逐字同形；新模块**不带模块级 Map/Set**（共享 honeypotWatch 的当日表），
以免再动单进程清单；新增数据面必须同时改判定表与台账（改闸即改接线）。

**P1b WS 入口（已落地）**：WebSocket 是**另一条认证入口**（`websocketService/handshake.js` 的
`authenticateSocket`），不经过 HTTP 那个接线点。修法与 HTTP 侧同源：握手投影取到 `isHoneypot`，
判据挂在既有的「用户存在闸」尾部（`_assertHandshakeUserExists` → `_assertHandshakeUserUsable`：
存在也未必可用）——建通道是主动行为，一律拒（同形的 `auth-error` + `disconnect`，不留新指纹），
并落 `honeypot_probe` / `critical` 审计与每日一次告警。留痕走 fire-and-forget（审计失败绝不影响拒绝）。

两处工程约束：判据必须**同步**（握手链的 await 序列被 `websocketAuthGhostConnection` 的位置闸钉死，
判据体不得引入新的 await）；判据**不放在 `authenticateSocket` 里**——该函数已贴 complexity 预算，
且 `credentialDoorCheckLedger` 声明「status 与 lockUntil 都写在自己函数体里」，所以蜜罐判据复用
既有方法的尾部，而不是再叠一条分支（改完两处门禁均已复跑）。

**与 HTTP 侧的差异（有意）**：WS 判据**不看总开关**——`HONEYPOT_ENABLED` 关闭时 HTTP 侧不再接管
（老会话回落 RBAC），但 WS 一旦建通道就能订阅推送，所以按 DB 标志 fail-closed。
两条通道的泄漏面不同，开关的语义也允许不同；这条差异由 `honeypotSocketGate` 的用例显式钉住。

## P2-2 路由声明表：把「不可达的 403」收口成逐字 404（批次 A 已落地）

**问题**：P1/P1c 的判定层用「前缀表」判路，于是「前缀之外的一切」在表里被写成 `DENY(403)`。
但改道点只挂在 `authenticate` 上，那些请求根本到不了它——真实链会落到 `app.js` 的兜底 404。
也就是说：表里那句话口径对、**HTTP 上不可达**，却让读者（以及上面 P1c 边界表的两行）以为
「陷阱对未知路径回 403」。同时，同一个前缀下「聚合子路径」与「明细 id」在旧的尾串判定里长得一样：
`/api/users/stats` 被当成「查一个叫 stats 的用户」⇒ 404，而真实链是 200。

**做法**：新增 `src/constants/honeypotRouteTable.js`——「app 里到底有哪些路由」的唯一声明
（127 行：方法 + 全路径 + 权限码 + 认证中间件名 + 陷阱的回答类别 + 敏感标记），判定层改为按表判路：

| 情形                                                              | 判决          | 依据                                                                                      |
| ----------------------------------------------------------------- | ------------- | ----------------------------------------------------------------------------------------- |
| 表里没有这条路径                                                  | `NOT_FOUND`   | 真实链落 `app.js` 兜底 404 ⇒ 陷阱回**逐字副本**（同模板、同打码、无 `errors` 键）         |
| 表里 `auth` 为 null（无 `authenticate`）或 `handling=passthrough` | `PASSTHROUGH` | 改道点不可达，声明真相是「不接管」——放行白名单仍是那三条，此处的 PASSTHROUGH 不扩大放行面 |
| 写方法，或 `handling=deny403`                                     | `DENY`        | 与真实 403 同一个 `codeError` 构造器（写方法先于 handling 判：将来漏写行也不进数据面）    |
| 其余已声明读路由                                                  | `DECOY`       | 交给合成数据面（列表 / 明细 / 聚合 / 汇总 / 本人面，文件面先判）                          |

明细未命中不再统一回「资源不存在」，而是**逐集合点名**（与真实控制器同一个构造器）：
`USER_NOT_FOUND`（读侧显式覆盖 `statusCode: 404`）、`ROLE_NOT_FOUND`、`PERMISSION_NOT_FOUND`、
`DEVICE_NOT_FOUND`、`ALARM_NOT_FOUND`、`INSPECTION_NOT_FOUND`。统一文案把「这个集合里没有这条记录」
与「这个集合根本没有明细」抹平，本身就是差异。

**判据**：`src/tests/ci/honeypotRouteTableParity.test.js` 从 `src/app.js` 的挂载表 × `src/routes/*.js`
的声明 × `app.js` 的内联路由**现算**一遍，与表双向比对（清单多一条/少一条、权限码/认证/敏感标记任一处
不符都红），再把每一行的回答类别交给真实判定链（`resolveDecoyVerdict` → 文件面 → 本人面 → 合成载荷）
现算对拍；404 模板与 `redactUrlQuery` 的来源逐字钉死；`authenticate` 只许逐路由挂（否则「未声明路径」
会真的进改道点）。闸门自带反向自证：塞一条幽灵路由、改坏一个权限码/认证/敏感标记必须被点名。

**登记项（不许静默）**：判据允许「暂时不一致」，但不一致必须在闸门里逐条登记，且**双向**
（现算的不一致集 === 登记集 ⇒ 收口时必须同轮清空登记项）：

| 登记项                         | 条数  | 现状                                                                                               | 收口方式                                                                       |
| ------------------------------ | ----- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `AGGREGATE_BACKLOG`            | **0** | 批次 B 已接线并同轮清空：10 条聚合读端点由 `constants/honeypotDecoyAggregates.js` 现算出同形合成体 | 已收口（空数组本身就是判据：删掉任一条端点，现算立刻落回 `decoy-none` 而变红） |
| `PERM_OUTSIDE_CATALOG_BACKLOG` | 5     | 回 200/文件、但权限码是呈现身份**没有**声称持有的 `security:audit`（`/api/security` 那 5 条）      | 批次 C 二选一：改 `deny403`，或把 `security:audit` 加进呈现目录                |

**批次 B 已接线（同轮清空登记项）**：`steer` 在「通用合成载荷」之前加一道聚合面
（`constants/honeypotDecoyAggregates.js#resolveAggregatePayload`），覆盖 10 条同前缀、不同语义的读端点：
`/api/users/stats`、`/api/roles/all`、`/api/roles/permissions/tree`、`/api/permissions/grants`、
`/api/permissions/grants/review`、`/api/devices/stats`、`/api/devices/expiring`、`/api/devices/reminders`、
`/api/alarms/stats`、`/api/inspections/stats`。它们与列表同前缀，若交给通用判定只会按尾串猜成
「查无此 id」而回 404——真实链在那里是 200，这比数据错更明显。

三条纪律固定在这道口上：**零真实读**（模块只从合成表与真实白名单/枚举派生；探针证明 require 面
不加载任何 `src/models`、`src/services`、`src/controllers`）；**信封复用真实构造器**
（`ApiResponse.success` / `ApiResponse.paginated`，`pagination` 里的 `page:null`、`totalPages:null`、
`hasMore` 由聚合体逐字给出）；**不可派生就登记**（`NON_DERIVABLE` 16 条：「真实响应里有、合成数据证不出」
的属性，如 `asOf`/`scannedAt` 这类请求时刻、`byRole[].roleId` 这类 24 位 id、真实链 `$group` 后无排序键
导致的并列次序）。登记项也走双向判据：`NON_DERIVABLE` 覆盖的端点集必须恰好等于 `AGGREGATE_ENDPOINTS`。

**「不可达」清单（读表前必须知道的事实，避免把口径当行为）**：

- **带 `:id` / `:userId` 的路径先被 ObjectId 参数闸拦下**：`applyObjectIdParams` 用的是 `router.param`，
  它在该路由的中间件链**之前**执行，所以 `PUT /api/users/hp-u1` 在真实链上是 400
  `PARAM_MUST_BE_VALID_OBJECT_ID`，`authenticate` 与改道点都还没轮到。⇒ 写侧 403 的声明只对
  **参数能过关**的写路由可达（如 `POST /api/users`）。
- 因此「陷阱对未知路径回 403」在 HTTP 上从来不可达；批次 A 之后，判决层也终于成立（`NOT_FOUND`）。
- **`GET /api/users/me` 同样不可达（E9）**：它命中的是 `/api/users/:id` 这条路由，`:id` 的 `router.param` 先把它按
  「不是合法 ObjectId」400 掉（`me` 当然不是 24 位 hex）⇒ `resolveDecoyPayload` 里的 `wanted === 'me'` 分支在 HTTP 上
  **进不去**，只有直接调函数的单测能覆盖。台账里不许把这条记成「按会话身份回本人数据」的已实现行为——它是备用分支。

**登记项三（设计待定，不在本批范围）**：诱饵表 id 用 `hp-…` 命名空间（CI 断言它不是合法 ObjectId，防撞号），
而真实链下发的 `_id` 是 24 位 hex。它与上面那条「不可达」叠加：攻击者「点开列表里的某一行」既拿不到明细
（参数闸 400），格式上也一眼不是 Mongo 的 id。彻底收口要把整个诱饵命名空间迁到**保留前缀的 24 位 hex**
（例如固定前四位 `5eed`：既是合法 ObjectId 形态，又能保住「与真实集互斥」的判据），代价是诱饵表、明细可达性
与若干台账要同批改；收益是明细端点从「不可达」变成「可达且同形」。

**本批定案：不迁移（保持 `hp-` 命名空间）**。理由：迁移的收益是让「点开列表里某一行」这条本来就被参数闸挡住的路径变成可达，
而代价是拆掉「诱饵 id 不可能是合法 ObjectId」这条**安全阀**（真实集合接受 24 位 hex，诱饵 id 一旦合法，任何把诱饵 id 当真实 id 转发的代码路径都会静默成功）。
安全阀 > 一条尚未可达的路径的同形度；迁移留作可选演进，动它必须同时改诱饵表、明细可达性与若干台账。

## P1d 名单接管：幽灵账号升级为蜜罐（本批已落地）

哨兵名（幽灵账号）在库里**不存在**，任何口令都进不去；蜜罐账户**存在**，且「猜对口令就进得来」。
本批把默认哨兵名整份接管为蜜罐账户：同一个名字，检测责任从「猜名字」换成「猜对口令」。

| 项           | 取值                                                                                                           |
| ------------ | -------------------------------------------------------------------------------------------------------------- |
| 默认诱饵名单 | `sysadmin` + 全部默认哨兵名（10 个）+ `admin`；名单本体由 `DEFAULT_CANARY_USERNAMES` 派生（12 条目 / 生效 11） |
| 超管名判据   | 生效名单**恒不含** `getSuperAdminUsername()`（默认 `admin`）：派生剔除，env 显式写入也剔除                     |
| 剔除去向     | 经 `dropped` 单独回传（不进 `errors`），启动期 info 播报；`admin` 因此是「超管改名即生效」                     |
| 逐条登记     | 接管集合 ↔ 台账双向一致，多一个少一个都红（`tests/ci/honeypotNameOverlapLedger.test.js`）                      |

**为什么这样做**：哨兵只要「名字」，蜜罐能拿到「会话」。命中哨兵的一次尝试止于一条审计；
命中蜜罐的尝试会把攻击者留下——一个零权限会话，加上此后每一次探测的留痕（P1/P1c 数据面）。
撞库/凭据填充的工具用法是「拿泄露字典里的口令去试」，命中率远高于「只猜名字」。

**代价（如实申报）**

- **哨兵信号在这 10 个名字上退役**：账户已存在 ⇒ `!user` 分支永不进入 ⇒ `canary_username_attempt`
  不再产生。替代物是蜜罐登录告警（口令命中词干时）与失败计数路径（未命中时需到阈值才告警）。
- **「只是猜名字」不再有单发确定性信号**：这是本次升级明确接受的损失，换来可交互会话与撞库覆盖。
- **11 个账户原先把「可一次性识别的簇」写在脸上**：同一 `realName`、同一邮箱域名、同一创建批次。
  本批（P1e）已把 `realName`/`department` 改成按名字确定性派生；创建批次与域名仍是有意保留的残余（见 P1e）。
- **诱饵账户不得开 MFA**：`isLureLogin` 要求 `mfaEnabled !== true`，被开即静默失效；故启动期加了
  fail-loud 对账（`honeypotWatch.runInit` 统计 `isHoneypot:true, mfaEnabled:true` 的条数）。
- **名字越普通，误报面越大**：`user`/`test`/`demo` 被真人手误输入的概率高于 `sysadmin`，
  而 `test`/`guest` 本身就在弱口令词干表内 ⇒ 这类尝试会直接进蜜罐告警。

## P1e 诱饵画像差异化（本批已落地）

P1d 让 11 个账户「存在」之后，它们本身又成了新指纹：同一 `realName`、同一 `@honeypot.invalid` 域名、
同一创建批次。任何能看到这些列的人（比如一处意外漏出的 users 投影）一眼就能看出整片蜜罐农场。
本批把画像也做成派生值。

| 项       | 取值                                                                                                               |
| -------- | ------------------------------------------------------------------------------------------------------------------ |
| 派生输入 | 归一化后的诱饵名（与哨兵名共用 `normalizeCanaryUsername`：`ROOT` 与 `root` 恒同画像）                              |
| 派生输出 | `realName`（姓氏池 24 × 名字池 28）+ `department`（10 项池）；确定性哈希取值，无随机数                             |
| 撞名去重 | `taken` 命中时换一批候选（最多 64 轮）；`taken` 初值取自库里已有诱饵的 `realName`（重跑/分批物化都不撞名）         |
| 接线点   | `honeypotWatch.createHoneypotAccount`：`realName`/`department` 取自派生画像（不再写死 `运维管理员`）               |
| 台账     | 生效名单逐条派生的「姓名+部门」两两不同；接线与三种坏形态由 `tests/ci/honeypotPersonaDifferentiation.test.js` 钉住 |

**为什么是确定性派生，而不是随机挑一个名字**：重跑 init、多实例先后物化、「删号后重新物化」都必须得到同一份画像。
随机取值的后果是同一个诱饵在两次启动之间改名换岗——那比统一画像更可疑，真实员工不会换名字。
确定性还让判据可测：同名恒同画像、不同名不撞名都是纯函数断言，不需要随机种子。

**残余与代价（如实申报）**

- **创建批次与邮箱域名没有伪装**：`createdAt` 由 Mongoose 的 timestamps 统一写入；邮箱域名保持
  `@honeypot.invalid`（RFC 2606 不可路由，且导出/备份里一眼可辨——这是**有意**保留的辨识面）。
  伪造时间戳必须裸写集合，绕过 timestamps 与 PII 加密钩子，代价大于收益：`isHoneypot` 字段本身就在库里，
  能看到这两列的人早已能看到它。
- **画像只降低「一眼可辨」，不构成权限边界**：它挡的是「看到一个整齐的簇就下结论」，挡不住库里那行
  `isHoneypot: true`。本项是纵深冗余，主要防线仍是枚举面排除与诱饵判据。
- **派生姓名可能与真实员工重名**：`realName` 非唯一索引、业务上允许重名，故不把「与真人重名」当作缺陷。
  蜜罐行不进任何枚举面，重名只影响持库读权限者的观感。

## P2 本人自助面：读侧七条从「403/汇总」换成「同形合成体」（本批已落地）

P1c 的台账把读侧七条登记为 `read-shape`：真实会话按 `req.user` 回 200 本人数据，陷阱回 403 或
`/api/security` 的合成汇总。这是当时**最强的一枚指纹**——装扮自称 `system_admin`，
却在「我的资料」「我的权限」上答不出本人是谁。本批把这七条接成**同形合成体**。

**接线位置**：与 P1 同一个改道点（`middleware/auth.js` 的 `steer`），判序为
放行白名单 → 文件/导出类 → **本人自助面** → 通用改道。新模块两个（体积原因，与
`honeypotDecoyData.js` 同一条理由：`max-lines` 是只降不升的棘轮）：

| 文件                                       | 职责                                                                              |
| ------------------------------------------ | --------------------------------------------------------------------------------- |
| `src/constants/honeypotDecoySelf.js`       | 纯声明：呈现层身份、52 行权限目录、7 条合成轨迹行（**零 require 叶子**）          |
| `src/services/honeypotDecoySelfProfile.js` | 会话上下文 → 七个端点各自的字段装配（`me` / `sessions` / `bindings`…）            |
| `src/services/honeypotDecoySelf.js`        | 轨迹物化、评分、候选集与参数拒绝；导出 `resolveSelfResponse` / `sendSelfResponse` |

**七条端点与形态**（逐条钉死在 `tests/services/honeypotDecoySelf.test.js`）：

| 端点                               | 陷阱回什么                                                                     | 与真实的同值关系                                                                |
| ---------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| `GET /api/auth/me`                 | `user` + `permissions`/`menus`/`buttons`/`dataScope`，字段集合与键序同 `getMe` | 身份取自会话（`id`=真实 `userId`），权限取合成目录且是三个出口的并集            |
| `GET /api/auth/mfa/status`         | `{ enabled:false, recoveryCodesRemaining:0 }`，默认消息「操作成功」            | 诱饵账户本就不许开 MFA，这个形态对它是真的                                      |
| `GET /api/auth/sessions`           | 当前这一条（sid 取自会话上下文），键序同 `toClientJSON`；无 sid ⇒ 空表         | `expiresAt − createdAt` = `jwt.refreshExpire` 的时长                            |
| `GET /api/security/my-info`        | 脱敏后的本人资料 + `securityScore` + `suggestions` + `recentLogins`            | 邮箱/手机**各脱敏一次**（`DataMasking` 非幂等），时间与 `/me` 同源              |
| `GET /api/security/bindings`       | 三条绑定（email / phone / department），值与 `my-info` 逐字相同                | 复用同一份呈现层身份，不读真实绑定表                                            |
| `GET /api/security/my-logs`        | 7 条合成轨迹（`_id` 为 24 位十六进制），`days`/`limit`/`category` 生效         | action/category 全在真实审计白名单内；`category` 非法 ⇒ 逐字 400                |
| `GET /api/security/report-targets` | 合成用户/设备/报警候选（含会话本人一行），条目 `id` 为 24 位十六进制           | 搜索走真实 `searchPatterns`（`upperCodePrefixPattern` 等）；类型非法 ⇒ 逐字 400 |

**为什么权限目录要抄全 52 条**：真实链的 `permissions` 是「菜单码 ∪ 按钮码 ∪ 接口码」的并集，
只给 8 条会在「我的权限」与自身菜单树对拍时露馅。目录**逐字复制**真实种子
（`initData/permissionsSystem.js` + `permissionsBusiness.js`），并由
`tests/ci/honeypotSelfShapeParity.test.js` 现算比对 type/module/name/path/method，
任何一侧改动都会红。故意**排除**四条：

- `*:*`（超管通配符：装扮成管理员却不给通配符才自洽——真实管理员本就没有这行）；
- `security:audit`（P1c 的审计导出 403 必须与「装扮里没有该权限」一致）；
- `pii:*` / `pii:export`（未脱敏导出没有二次验证，不能声称有该权限）。

**签署声明也要一起换**（否则一次续期就自报家门）：JWT 载荷可被客户端解码，
所以 `presentedClaims()`（`constants/honeypotDecoy.js`）在**两个签发点**统一改写
`email` 与 `roles`：`services/authService/session.js#issueRevocableTokenPair`（登录/注册）与
`services/authService/token.js#refreshSession`（轮换）。非诱饵会话原样透传，逐字不变。
DB 里的 `email` 仍是 `<name>@honeypot.invalid`（RFC 2606 不可路由，**故意**留给防守方辨识），
呈现层一律用 `ljxfw.cn`；两条链的分工由 `tests/services/honeypotWatch.test.js` 的
「签署声明」用例钉住（登录与续期两条都断言，并反向断言真实账户不被改写）。

**边界表（本批新增/收紧，全部由用例现算）**

| 项                           | 取值与判据                                                                                                          | 为什么可以接受 / 代价                                                         |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |

- 合成角色码是**编造**的（`system_admin`/`ops_manager`/`duty_officer`/`maintainer` ≠ 真实
  `SUPER_ADMIN`/`SECURITY_ADMIN`/…）。真实角色码在库里可被读到，但**不在任何读侧响应里**，
  这条取舍与「装扮优先于可对拍」一致；要真对齐需给角色表也做一份合成目录，收益小于改动面。
- 合成表（`DECOY_USERS`/`DECOY_DEVICES`/`DECOY_ALARMS`）的 `_id` 在**列表**里仍是 `hp-` 前缀

- `/api/users` 列表（以及 `phone` vs 真实 `phoneMasked`/`emailMasked` 的字段名差异）仍不做会话感知：
  它走的是 P1 的合成列表，不是「本人自助面」。

## P1f 事件链聚合（L1，本批已落地）

P1–P1e 的四个信号各自独立成立：撞库口令失败（`login_failed`）、猜哨兵用户名
（`canary_username_attempt`）、诱饵口令命中（`honeypot_login`）、陷阱会话内探测
（`honeypot_probe`）。它们**分开看都是"一次尝试"**，合起来才是"一个人在做一件事"：
一个来源 IP 在同一个业务日内先撞库、再猜幽灵名、再撞进诱饵、然后在陷阱里翻东西，
这条链的证据强度远超四份互相独立的告警。本批把这条链做成一个判据。

**判据（唯一实现：`src/services/honeypotChainWatch.js`）**

| 项       | 取值                                                                                                                                                  |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 维度     | 归一化后的来源 IP（`normalizeIP`）；`ip: null/''` 的行**不参与**                                                                                      |
| 窗口     | **业务日**：`businessDayBounds(businessDateParts().dateStr)` 的 `[start, end]`，不是"最近 24 小时"                                                    |
| 阶段     | 上列四个审计 action；同一阶段重复 N 次**不算链**（那是各检测器自己的频控口径，不是新证据）                                                            |
| 阈值     | 同一 IP 在一个业务日内跨过 **≥2 个不同阶段** ⇒ 升级为 `honeypot_chain_escalated`                                                                      |
| 频控     | 同一 IP 每业务日**只升级一次**，凭据是**审计行本身**（一轮一次 `distinct` 取当日已升级集合预筛 + 写前 `countDocuments` 复核）                         |
| 落库     | `AuditLog.create`：`category: 'security'`、`riskLevel: 'critical'`、`username: 'anonymous'`、`body` 记 stages/events/dayWindow/firstSeenAt/lastSeenAt |
| 出站     | `dispatchNotification(ALERT_TYPES.HONEYPOT_CHAIN_ESCALATED, ALERT_LEVELS.CRITICAL, …)`（fire-and-forget）                                             |
| 取证     | 升级即 `forensicTrigger.markForensicTarget`（跨阶段确认 = 已确认攻击源，与蜜罐登录同一钩子）                                                          |
| 生命周期 | `start()` 起定时器（`unref`）、`stop()` 只 `clearInterval`；间隔 `HONEYPOT_CHAIN_INTERVAL_MS` 默认 300000、最小 60000、**最大 86400000**              |

**为什么去重凭据是审计行而不是进程内 Map**：Map 只在"这个进程、这次启动"里成立。
滚动重启后同一个 IP 会再升级一次；多实例部署时 N 个实例各升级一次。审计行是唯一的
**跨重启、跨实例**事实来源。查询分两层：①**候选侧**一轮一次 `distinct('ip', {action, 当日窗口})`
取"当日已升级来源"集合，先把它们从候选里剔掉；②**写前**仍对要升级的每个候选做一次
`countDocuments` 复核（两个实例同轮起跑时唯一的最后一道闸）。代价如实申报：每轮
1 次 `distinct` + ≤50 次计数查询，全部发生在巡检轮内、不在请求路径上，换来的是
"每业务日一次"在任何部署形态下都成立。

**为什么候选侧要先剔除而不是只靠写前复核**：写前复核只能回答"这个 IP 升过没有"，
回答不了"该不该把名额给它"。已升级的来源在当日窗口里**不会消失**，按最近活动倒序排
它们仍在最前面；若只按"取前 50 个候选再逐个复核"，这 50 个名额会被同一批已升级来源
每轮永久占满，尾部候选再也轮不上（实测：52 个跨阶段来源、最旧的两个 `lastSeenAt`
最小，连跑 3 轮仍未升级）。先剔除再取名额，才让"剩下的候选下一轮继续处理"这句成立。

**为什么审计写失败时本轮不投递**：审计行既是这条链的证据，也是"当日只升级一次"的凭据。
写失败却照常投递，下一轮会因"查不到升级行"而**再投递一次**——一次写故障就变成
按巡检间隔重复的告警风暴，而真正该被看见的"审计写不进去"反而被淹掉。
故写失败只计数（`getHealth().escalationFailures`）并 `logger.error`，下一轮重试；
代价是最坏情况下告警晚一个巡检间隔（默认 5 分钟），换来的是不重复、不静默。

**为什么按业务日而不是滑动 24 小时**：告警的去重口径、审计查询口径、留痕的"当日"口径
在仓内都已经是业务日（`constants/timezone.js` 是唯一事实来源）。用滑动窗口会让
"同一天里被升级两次"这类现象在跨零点时再现，而在跨时区/夏令时切换时更难解释。

**边界情况与处理**

- **NAT / 共享出口**：一条链要求 ≥2 个阶段，且其中至少一个必须是"人类不会误触"的阶段
  （猜幽灵名 / 撞进诱饵 / 陷阱内探测）。纯撞库（`login_failed` 反复）**不**升级——
  一个办公室共享出口输错口令是常态，那是 `securityAlert.checkBruteForce` 的账号/IP 维度，
  不是这条链。误报面与审计字段同时留在 `body.stages` 里，可复盘是哪两个阶段凑成的。
- **伪造前置阶段**：攻击者可以故意先发一次 `login_failed` 再撞诱饵，制造"跨阶段"。
  这对本判据无收益——它会因此**更早**被升级；唯一的代价是告警里多一个阶段名。
- **IP 不可解析**：`normalizeIP` 返回 null 的行不参与合并（绝不把不可解析文本当键，
  同 `forensicTrigger` 的口径）——`toChainIp` 只保留归一化结果，**不回落到裸文本**。
  丢弃不是静默的：每轮丢弃的分组数累加进 `getHealth().unparsableSources`。
  IPv4-mapped（`::ffff:`）在合并**之前**归一化，否则同一个人的两条阶段会被格式差
  撕成两条半链。
- **单轮上限**：上限限的是**升级名额**（`ESCALATION_LIMIT = 50`），不是"看多少条"。
  候选按最近活动倒序，先剔除当日已升级的来源，再取前 50 个升级。分布式撞库时真实候选
  可能远超此数——这是有意的：告警面本身不能变成风暴。被推迟的候选数累加进
  `getHealth().droppedCandidates`（累计**推迟次数**，同一候选推迟多轮会重复计入；
  判读看的是它在涨），它们留在下一轮的待升级候选里，不存在"越旧的越永远
  排不上"的饥饿；每轮实际看到的候选数与待升级数分别读 `lastCandidates` /
  `lastPendingCandidates`。
- **重叠守卫**：上一轮未结束（DB 慢）时本轮只记 `skippedOverlaps` 并 `logger.warn`，
  不并发压入第二轮——同 `auditMonitor` 的"一轮一闸"。
- **间隔上界**：只钳下限是不够的。Node 对超过 2^31-1 ms 的 `setInterval` 会**静默**
  改成 1ms 并打一条 `TimeoutOverflowWarning`（实测 `HONEYPOT_CHAIN_INTERVAL_MS=
3000000000` ⇒ 面板报 `intervalMs: 3000000000`、真实定时器 `_idleTimeout: 1`）：
  面板说 34 天、实际每毫秒一轮全表聚合。故上限压在 24h（远低于溢出线），抬升时
  `logger.warn`，`getHealth().intervalMs` 恒等于定时器真实时长。
  `auditMonitor` / `auditChainMonitor` 原本只有下限，是同一个缺口类 —— **本批一并补齐**
  （同一判据：24h 上限 + 高于上限时 `logger.warn`；判据读的是 start 真正交给 `setInterval` 的
  实参，不是配置值也不是面板读数，见下表两处上界用例）。
- **同族的成功读数与连败归零点**（本批一并补齐）：`auditMonitor` / `auditChainMonitor` 同样补
  `lastSuccessAt`（成功判据 = **整轮没抛**，含告警投递侧），`consecutiveFailures` 的归零点
  从"判定之后、投递之前"移到整轮末尾。这不是顺手统一，而是**修掉一个真实缺陷**：
  `auditChainMonitor` 的失败告警门槛是 `FAILURE_ALERT_THRESHOLD = 2`，而投递每轮都断的那一轮
  旧口径是"先归零、再加 1" ⇒ 连续计数**永远停在 1** ⇒ 「连续两轮才占告警通道」这条判据静默失效、
  投递长期故障时失败告警永不触发。判据见 `auditChainGuardedIntegrity.test.js` 的
  「投递每轮都断时连续失败照样累计」。
- **收尾判据的写法**：两个同族模块各加一条「复位钩子覆盖 health 的**每一个键**」用例——
  跑一轮弄脏 state → `__resetForTest()` → 与复位前的快照 `toEqual`。日后新增读数忘记复位，
  该用例必红（不依赖人手维护一份字段清单，这正是 `honeypotChainWatch` 用 `INITIAL_HEALTH`
  单一声明要解决的同一问题）。
- **成功读数**：`lastRunAt` 在轮次**开始**时落，光看它答不了"上一轮跑完了吗"——旧口径只能
  拿 `lastFailureAt` 反推。故补 `lastSuccessAt`，**只在整轮跑完（聚合 + 候选处理都没抛）时落**；
  两个读数配对比较即可判"跑到底"还是"一半就断了"。`consecutiveFailures` 的归零点同步
  从"聚合之后"移到"整轮末尾"——旧位置会把"聚合成功、断在候选处理"的那一轮记成连败 1
  （真相是连续第 2 轮失败），把判健用的读数往好的方向抹。
- **复位钩子**：`__resetForTest()` 逐键复位 health 与 `effectiveIntervalMs`（`INITIAL_HEALTH`
  是初值的单一声明，日后新增计数不会漏复位）。**不关定时器**：关停只有一个入口 `stop()`，
  钩子顺手 `clearInterval` 会制造"以为停了其实还在跑"（与 `auditMonitor` / `auditChainMonitor`
  的钩子同边界）。代价如实申报：钩子本身是新导出，已按测试钩子台账登记（计数 37 → 38），
  并在本模块用例里逐条 `beforeEach` 消费。

**闸**：`tests/services/honeypotChainWatch.test.js`（16 条：阶段表与标签表键集相等且四个阶段

## P2-3 边界口径（批次 E 首批：E1/E3/E5/E8，本批已落地）

批次 A/B 把「判决」和「十条聚合读端点」接上之后，逐条走查**边界输入**，发现四处只看正常请求看不到的差异。
四条都在本批收口；四条各自配一条只降不升的判据（`tests/ci/honeypotDecoyClockLedger.test.js`）。

| 项  | 缺陷（实测）                                                                                                                                                                     | 收口口径                                                                                                                                                                                                                |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| E1  | `GET /api/alarms/stats?startDate=not-a-date`：真实链 400 `DATE_PARAM_INVALID`（`alarmController.js:428-433`），陷阱回 **404「资源不存在」**——先 200 再换个坏参数就自证是合成端点 | 聚合体按**真实控制器的判序**（先 `isValidDateParam` 后 `isDateRangeReversed`）产 `{kind:"codeError"}`，`sendAggregate` 走 `ApiResponse.codeError` 出体                                                                  |
| E3  | 行时间由「此刻 − 偏移」现算：同一行相隔 1.2s 两次抓取差 **1201ms**（真实库里时间是存量、不可变，diff 一次就能自动化识别）                                                        | 新增 `rowClockNow()`：行时间基准**量化到秒**（秒级新鲜，见下方代价）；一次应答只取**一个**基准（列表/导出共享，行时间不跨秒开裂）；`asOf`/`scannedAt` 这类真·请求时刻字段仍走 `new Date()`（已在 `NON_DERIVABLE` 登记） |
| E5  | `xOffsetMin: null` 被 `Number(null)===0` 静默折成「此刻」；`undefined`/`NaN` 让 `toISOString()` 抛 RangeError ⇒ **500**（合成表当前全是有限数字，属**潜伏**缺陷）                | 「有值」的定义钉成**有限数字**，否则该键给 `null`（与真实 schema 的 `deletedAt: null` 同形）；`materializeRow` 不再折成此刻、不再抛                                                                                     |
| E8  | `tally` 撞缺失字段给 `{_id:undefined}`，JSON 序列化后整个 `_id` **静默消失**（真实 Mongo `$group` 是 `_id:null`）；字段改名漏改一处只产出坏桶不报错                              | `tally` 显式给 `_id: null`；判据从**聚合模块源码**扫出被引用字段名再回合成表核对，并要求「扫到几条 = 源码里有几次调用」                                                                                                 |

**判据为什么这么写**：E1 的错误码从**控制器源码**里现读再与聚合体现算值对拍（`toContain("codeError(res, 'CODE')")`），
抄成两份口径迟早会在某次改动后分叉；E3 断言「同一行时钟秒内两次解析逐字相同」+「与此刻相差 < 1s」+「列表面所有时间戳都落在 2000 年代且至少一个贴近此刻」，把锚点粒度与新鲜度都变成可现算的断言；
E8 的「扫到几条 = 调用几次」是关键的一半——只查「壳里提到的字段在不在表里」，给字段名加一层间接（传变量）就能让判据静默失效。

**代价与残余（如实申报）**

- **行时钟量化到秒：新鲜优先，残留一个可识别面（产品口径已定案）**。量化到秒后行时间始终距此刻 < 1s（最近的合成行不会显示成整点），同一秒内重复读取逐字相同；
  不量化时两次抓取会差出毫秒级抖动——那才是可自动化的判别式。**跨秒读取仍会看到所有行时间整体前移整数秒**（真实库里的行是存量，不随读取前进），
  这条修不掉：要消除它只能放弃新鲜（按进程/按天冻结锚点，行时间不再前进，最近的行会越看越旧）。定案：**新鲜优先**，本残留如实登记。
- **`tally` 字段只做「存在」判据，不做「每行齐全」**：真实 schema 里 `result` 只在 `completed` 巡检行上有值，按行齐全会把合法差异判红。
  必须每行都齐的是**时间列**（`windowRowsOf` 拿它当过滤键，缺一列就静默丢行），这一条由判据钉住。
- **同批登记、尚未收口的边界**（见 `work/hp-edge-cases.md`）：E2 路由级校验器的拒绝路径（`?page=0`/`?limit=101`/非法枚举 ⇒ 真实 400 `VALIDATION_FAILED`，陷阱仍 200）——
  注意**同一前缀下存在两种拒绝码**：`/api/alarms`、`/api/inspections` 的**列表**挂了 `isISO8601`（`alarmRoutes.js:27-28`、`inspectionRoutes.js:40-41`），坏日期先被路由级校验器拒成
  `VALIDATION_FAILED`，只有「两个日期都合法但区间逆序」才落到控制器的 `DATE_RANGE_INVALID`；而 `/stats` 没有路由级日期校验器，坏日期直达 `isValidDateParam` ⇒ `DATE_PARAM_INVALID`（E1 已落地）。E2 必须**逐路由**实现，写反就是一次请求自证；
  E4 三条列表的合成行序与真实排序键不符、E6 `frozenRows` 只冻顶层、E7 合成行空对象与真实 `minimize` 相反、
  E9 `/api/users/me` 的 `me` 分支在 HTTP 上不可达（被 `/:id` 的 ObjectId 参数闸先拦）、E10 空结果集的分页格。

**第三刀（数据面键名与枚举换成真实投影）**

包D 落地时，合成行的键名与真实投影仍不同：`code`/`timeOffsetMin`/`deviceCode`(串)/`location`(串) 对不上 `alarmCode`/`occurredAtOffsetMin`/`deviceId`(子文档)/`location`(子文档)，
`status`/`level` 还是中文档而真实是英文枚举，devices 的 `code`/`name`/`lastCheck` 对不上 `deviceCode`/`deviceName`/`lastCheckDate`，users 的 `phone` 对不上 `phoneMasked`。
第三刀逐集合换成真实投影键（alarms、devices 已落地；inspections、users 随后），并**删掉中文值域桥**——数据面直接用真实英文枚举后，
「合成行是中文、过滤器拿英文去比 ⇒ 合法请求恒回空页」这条可单次请求命中的指纹随之消失。

**为什么把「换名」做成棘轮而不是一次性改动**：换名清单（`PENDING_RENAME`）是机器可读的，且**双向**钉住——待改名期间「旧名必须仍在行里」，改名落地后该条目必须删除、
「旧名必须已消失」自动接手判红。判据里因此同时有两种失败：漏改（旧名还在、新名没到）与改过头（条目没删）。这比人工核对清单可靠，因为清单本身也在被判据消费。

**引用完整性判据（L 组）**：行里每个引用型 id（`reporter.userId`、`handler._id`、`deviceId._id`、`processLog[].operator`、inspections 的 `createdBy`/`reviewedBy`/`devices`、devices 的 `createdBy`）
都必须能在对应合成表的 `_id` 里找到。引用路径**从模型 schema 现扫**（含数组元素与子文档数组内部的 ref），不手抄清单，所以模型将来新增一个 ref 字段，判据自动覆盖。

**代价与残余（如实申报）**

- **引用位一律保持 `hp-*`，不迁 24-hex（已定案）**。P1c 已有两套 id 是**必须**的：`report-targets` 的候选 id 是 sha256 派生 24-hex，因为真实接口就回 24-hex、且前端会原样回传，
  用 `hp-*` 会自报家门。但行内的引用位（`reporter.userId` 等）若也改 24-hex，就变成**数据面内部两套 id**：同一个用户在 `/api/users` 叫 `hp-u1`、在 `/api/alarms` 的引用位叫 `a3f1…`，
  一次交叉比对即可确认「两套 id 体系」——这比「某个子键不像 ObjectId」更强、更好识别。`hp-*` 单点虽假却**内部自洽**（能在 users 表里对上），
  而「合成 id 不是合法 ObjectId」本就是 P1c 登记在案的已知残留。**用已接受的残留换新矛盾，不值。** 这条由 L 组钉住（悬空引用即判红）。
- **`pending` 档必须采样**：真实 schema 的 `status` 默认就是 `pending`，「刚上报未派单」是最常见的初始档；若合成面全采已处理档，`?status=pending` 恒回空页、
  聚合桶里也永远没有 pending，两处一比就露。已补一行「未派单形态」（无 `handler`/`dispatchedAt`/`arrivedAt`/`resolvedAt`/`cause`/`handleResult`、`processLog` 只有一条上报记录）。
- **`users` 的 `?sort=` 白名单未兑现**：合成侧恒按默认 `-createdAt` 排序。真实链支持白名单排序，但**没有对手方可比**（同样的请求在真实侧要真库有数据才能看出差异），故不构成指纹。登记待办。
- **缺键方向不补**：`__v` 与部分 `createdAt` 不下发。缺键比多键安全，且补 `__v` 等于主动伪造「这是 mongoose 文档」的痕迹，收益为负。
- **条件物化键**：`VARYING_KEYS` 登记了行间非恒有的键（alarms 的 `handler`/`dispatchedAt`/`arrivedAt`/`resolvedAt`/`cause`/`handleResult`，devices 的 `expiryDate`/`nextCheckDate`/`remark`/`scrapDate`/`scrapReason`）；
  这些键**无偏移量时整键不出现**，不是漏字段，判据按「真模型里可选」而不是「每行齐全」来判。

**判据的判据（本批新增的自证方式）**：L 组实现时曾漏掉子文档数组内部的 ref——`SchemaDocumentArray` 同时有 `$embeddedSchemaType`（无 `ref`）与 `schema`，
旧写法在中间分支落空后**不递归**，于是 `processLog[].operator` 从未被扫到，而判据里却写着「已覆盖」。
这条由**Lead 用变异实测**发现（把 `operator` 改成悬空 id，L 组仍绿），改成「无 `ref` 时继续向下钻」后两个方向都红/绿。
教训：**判据的覆盖面本身也要用变异来证明**——「清单里写了」不等于「真的扫到了」。

## P2 情报：撞库画像（判据已立，读侧出口已落地）

**决策**：把蜜罐命中（诱饵登录、幽灵名猜测、陷阱内探测）**派生**成一份「来源 + 口令字典特征 + 成功率」的
聚合画像，只服务两个消费方——**黑名单候选**与**告警排序**。画像是**只读派生**，不新增写入路径：
数据源就是审计链上已经落下的 `honeypot_*` 行，留痕先于画像存在，画像只是换个读法。
代价是画像的可回溯期等于审计保留期；换来的是"零新表、零新写入面"——新增一张「谁在撞库」的表，
本身就是新的高价值攻击目标。

**本批同时收紧原口径**：路线图里原先写「只留**词干哈希**与长度档」。哈希不落库——低熵口令的哈希
就是字典可逆（`sha256(口令)` 与口令是一一对应的，字典一跑就还原），存它等于换个形式存口令。
画像只留「命中词干表」这个布尔与档位。

| 字段                            | 取值                                               | 为什么是这个                                                                                                                                                 |
| ------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `sourceKey`                     | 归一化后的 **/24（IPv4）** / **/64（IPv6）** 段    | 撞库轮换的是 /32；按段聚合才看得见"同一台机器换 IP 试"。**不回落裸文本**：`normalizeIP` 返回 null 的行不参与，丢弃量单独计数（同 `honeypotChainWatch` 口径） |
| `credentialStemHits`            | 命中 `constants/breachedPasswords.js` 词干表的次数 | 「持有泄露字典」的唯一可靠特征（大小写/复数同源变异都在表内），且攻击者不可能事先知道这个判据                                                                |
| `lengthBucket` / `charsetClass` | 档位（与口令强度计量同一套档）                     | 只有档没有值：既描述字典特征，又不可反推口令                                                                                                                 |
| `attempts` / `successes`        | 次数                                               | 成功率只拉**真实登录成功**；诱饵放行的"成功"单独计——否则成功率会被诱饵自身抬到 100%                                                                          |
| `accountCardinality`            | 涉及的不同账号名数                                 | NAT/共享出口下"一个 /24 试同一个账号 30 次"是正常的输错口令，与"一个 /24 试 3000 个账号"必须能分开                                                           |
| `businessDay`                   | `constants/timezone.js` 的业务日                   | 与去重、查询、留痕三处口径一致（同 L1 的判据）                                                                                                               |
| `windowStart` / `windowEnd`     | 本轮现算的窗口（业务日 ∩ 保留期）                  | 画像不是累加器：不写明窗口就无法回答「这份画像是哪段时间的」，也无法让「空窗口 ≠ 无攻击」成为可核对的判据                                                    |

**派生前提的修正（评估结论）**：审计行里**没有**任何口令派生字段——`recordLogin` 与两条蜜罐写入口
落的是身份与请求元数据（`username` / `ip` / `userAgent` / `fingerprint` / `reason` / `success` /
`riskLevel`，蜜罐行另带少量 `body`），没有一项取自口令——所以「纯读侧派生」这层
前提只对 `sourceKey`、`attempts`、`successes`、`accountCardinality`、`businessDay` 成立。
`credentialStemHits` / `lengthBucket` / `charsetClass` 必须在**登录时**算好，随**既有**蜜罐审计行的 `body`
一起落库：写入调用点不新增（还是那两次 `create`），「零新写入面」指的是**零新集合**，不是零字段。
把这条差别写在这里，是为了避免下一个人按「纯读侧」去实现，做到一半才发现三个字段无处可取。

**三条硬边界（第一条是红线）**

1. **口令明文绝不落库，哈希也不行**（理由见上）。词干表本身按秘密处理：画像输出里**不得**回显命中了哪一条词干。
2. **画像不得反向暴露蜜罐判据**。画像的读侧与审计行**同码同票据**（见下节 ②），但它是个**聚合面**：
   一次读取就能横向看到许多来源，而审计行是逐条的、且每次都要换票据。所以输出里**不含阶段名、
   不含哨兵名、不含诱饵名**——那些是"如何识别陷阱"的说明书。要复盘走审计行（逐条、可追溯），不走画像。
   **这条与 L1 有意不同**：`honeypot_chain_escalated` 的 `body.stages` 是给安全值班看的确定性告警（逐条、
   可追溯，看的是"这一条链发生了什么"）；画像在**同一读档**上提供"这些来源横向比一比"，一次读取的
   暴露面完全不同。所以 L1 可以带阶段名，画像不行。
3. **跨实例结论写在明面上**。画像每次从审计集合现算、不在进程内累加，因此行集是实例无关的
   （评估见下节 ①）；这条边界转为一条**触发条件**：一旦改成进程内累加，字段表必须补上
   `instanceScope` 并在出口注明，**不许沉默地当全量用**。

**边界情况优先（每条都要在实现前定案）**

- **样本不足不出口**：`attempts < MIN_SAMPLES`（暂定 30）时该来源**不出画像**。宁可没有，也不给运维一份
  "抽签抽出来的攻击者排名"——这种画像一旦存在，就会有人拿它当封禁依据。
- **共享出口是主误报面**：`accountCardinality == 1` 且 `credentialStemHits == 0` 的来源不进黑名单候选
  （一个办公室反复输错同一个账号）。这条同时吃掉"口令过期后多设备重试"这一整类。
- **成功 ≠ 凭据泄露**：成功率只用于排序，不用于判定；`successes > 0` 单独产生一条高优先级信号，
  但**不**自动升格为"凭据已泄露"（自助重置后本人重登也会成功）。
- **画像不是新的告警通道**：读侧只暴露"候选强度 + 时间 + 段"，不投递。投递仍走既有告警链，
  否则会绕过既有频控与"连续两轮才占告警通道"的判据。
- **保留期与审计保留期绑定**：画像从审计行派生，审计行轮转掉之后画像必须同步缩水——
  过期数据留在画像里，等于让"已过保留期"的证据继续影响封禁决策。

**判据（落地时先写闸再写实现）**

1. 正向：给定合成审计行，画像每个字段都能**现算**对拍（键、档位、业务日窗口），不抄一份期望值
   （抄两份口径迟早分叉，同 E1/E8 的写法）。
2. 反向自证：把口令明文塞进输入 ⇒ 画像输出**任何字段**都不得出现它（含长度众数、字符集档的逐字回显）；
   去掉词干命中标记 ⇒ `credentialStemHits` 必须归零；把 `sourceKey` 换成裸文本 ⇒ 该行必须被丢且丢弃量可见。
3. 结构面：画像输出的键集合与上面的字段表**双向一致**（多一个键就红——多出来的键通常是"顺手带上的"泄漏）。
4. 跨实例面：出口必须自述窗口端点（`windowStart` / `windowEnd`），且实现里**不得**出现承载画像样本的
   模块级 `Map` —— 一旦出现就说明聚合搬进了进程内，必须按上面的触发条件回来重评 ADR-005。
5. 静默失效面：画像若做成周期任务，必须复用本批定下的读数契约——间隔上下界（24h 上限）、`lastSuccessAt`
   （只在整轮跑完时落）、`consecutiveFailures` 在整轮末尾归零、`skippedOverlaps`、`__resetForTest()` 逐键复位，
   并经 `compliance.*Health` 原样出口。否则它会重演本批修掉的"面板说在跑、实际每轮都断"。

**三条前置条件的评估结论（都不是代码问题，已定）**

① **跨实例：画像不落任何要跨实例对齐的态，因而不受 ADR-005 管辖**。ADR-005 收口的是「各实例各持一份
就造成**安全语义失效**」的态（限流配额按副本数翻倍、验证码跨实例校验失败、权限回收不生效、审计链分叉），
它的判据不是"有没有 Redis"，而是"这份态缺失或漂移时，防线是否静默失守"。画像不属于此类：它的唯一数据源
是审计集合——**已经在库层是跨实例的唯一事实源**——聚合只发生在读侧，不在进程内累加任何东西，
所以不存在需要对账的第二份态。
**代价如实写明**：两个实例各算各的，窗口端点会差出几秒到几分钟，排名边界上随即有出入；这不影响
任何结论，因为画像不进决策路径（不自动封禁、不投递）。
**触发条件**（满足任一条就回来重做本评估，并按 ADR-005 经 `sharedCache` 收口，而不是另造一套）：
画像进入任何**自动封禁**路径；或改成"进程内累加 + 周期落库"。届时字段表必须补上 `instanceScope`
并如实写 `instance`，不得沉默地当全量用。

② **读侧权限面：不新增权限码**。黑名单的读写侧是 `security:config`（`/api/security/ip-list`
GET/POST 与 `/ip-list/query`），审计读侧是 `security:audit`（另需二次验证票据）；两者在
`permissionCatalogRouteParity` 里都是被真实路由强制的码。画像落 `security:audit` **并同样挂二次验证票据**
（与 `/alerts`、`/audit-logs` 一致）——不新增码，也不降门槛；**"把候选写进黑名单"这个动作沿用既有
写入口，画像自身不写入**。
**实测补充**：默认角色里没有一条授予 `security:config`（只有超管的 `*:*` 通配能到它，安全管理员与
审计监督员都到不了）——所以「候选 → 名单」这一步在默认部署里仍只有超管能落，画像不改变这一点。
新造一个 `security:profile` 之类的码会同时踩两处：`permissionCatalogRouteParity` 把"目录里有码、
却没有任何路由强制它"登记为不许再多的那一类；而它又多出"只能看、不能动"的第三档权限，权限面只增不减。
**边界**：画像**不得**成为绕过 `security:config` 的封禁旁路——它只排序、只给候选，不落名单。

③ **保留期对齐：不新增保留期常量**。`src/constants/retention.js` 的 `RETENTION_DAYS` 是唯一口径，
审计行 TTL 索引的 `expireAfterSeconds` 就是 `RETENTION_SECONDS`；画像窗口取"业务日 ∩ 保留期"，
`windowStart` 下界由 `max(业务日窗口下界, 保留期下界)` 算出 ⇒ 保留期被调小时画像自动跟着缩水，
既不需要第二个数去对齐，也不可能出现"画像比证据活得久"。
**代价如实写明**：画像**不可回填**——保留期之外的历史窗口永远算不出来（行已经被 TTL 删了）。
这不是缺陷，正是"过期证据不得继续影响封禁决策"的同一个决定。

**落地状态（2026-11-01 更新）**：判据先立这件事已经走完——本条的读侧实现随判据一起落地，不再是"待排期"。

### 读侧出口（已落地）

| 项   | 落地形态                                                                                                                                                                                                                                                                   |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 端点 | `GET /api/security/stuffing-profile`（路由独立成 `src/routes/stuffingProfileRoutes.js`）                                                                                                                                                                                   |
| 读档 | `authenticate` → `checkPermission('security:audit')` → `requireReauthTicket()` → `strictLimiter`；**不新增权限码**                                                                                                                                                         |
| 取数 | 审计集合按 `action ∈ TRACKED_ACTIONS` ∧ `timestamp ∈ 业务日窗口` 现算；窗口下界 = `max(业务日下界, 保留期下界)`                                                                                                                                                            |
| 参数 | `businessDay` 只收 `YYYY-MM-DD`：只有整个参数**缺席**才算缺省（=今天），其余形状（含空串、数组）回 400 `DATE_PARAM_INVALID`。**不存在的日历日**（如 `2026-02-30`）沿用本仓既有收口 `clampToRealCalendarDay`（窗口与 `dateStr` 一起夹到真实日历日），不在这里另造第三套判据 |
| 出口 | `data` = 画像条目数组；`meta` 带 `businessDay` / `windowStart` / `windowEnd` / `expired` / `droppedUnparsable` / `droppedBelowMin` / `minSamples` / `count` / `dataScopeType`                                                                                              |
| 失败 | 数据范围不可用原样上冒 403 `DATA_SCOPE_DENIED`；其余故障折算 500 `AUDIT_QUERY_FAILED`（复用既有错码，不新增）                                                                                                                                                              |

**为什么路由独立成文件**：`securityRoutes.js` 的有效行数已被 `max-lines` 棘轮钉在 367 行地板（再加一条路由块就要扩大基线），
与 `forensicRoutes.js` 当年拆出的理由同一条。新文件挂在同一前缀 `/api/security` 下；`src/routes/index.js` 统一导出，
`app.js` 在同一挂载段就近 require（顶部导入块加行会让其后 10 条已登记的行号锚点整体漂移，见 `tests/ci/commentAnchorFreshness.test.js`）。

**已知且有意接受的副作用（空表不许冒充"没有攻击"）**：画像行来自蜜罐审计，而蜜罐审计行的 `userId` 为空
（陷阱账号不是真实业务主体），`applyAuditDataScope` 的 `self` / `department` 两档正是按 `userId` 过滤 ⇒ 这两档操作者
拿到的画像**恒为空**。这与 `/alerts` 的今天表现同源（见 `securityAlertsScopeParity` 的文件头）：本批选择"不降门槛、同源收口"，
而不是给画像单开一条旁路。为了让空表可解释，出口回传调用者自己的 `dataScopeType` 与 `minSamples`（调用者的范围不是秘密：
`/api/auth/me` 已经在回传它）。

**本出口不做的事**：不返回口令明文或哈希（连长度都不是原值，只有档位）；不返回蜜罐账号名 / 阶段名 / 哨兵名；
不写入、不封禁、不生成黑名单条目（`isBlacklistCandidate` 只是给消费方的建议位）；不落任何跨实例态（聚合只在读侧）。

**陷阱面（未落地，记账沿用 deny403）**：路由表把这条端点登记为 `deny403`——陷阱会话在此拿到与真实 403 逐字相同的拒绝，
而不是合成画像。合成画像（读侧形态对齐）属于后续增量：它需要一份与真实响应同形的合成体以及对应的对拍判据，
本批不做，也不把它伪装成"已落地"。

**仍然成立的原始理由**：判据与实现同批落地，是为了避免出现"画像先上线、边界后补"的中间态——那种状态下第一批被封的来源没有判据可复盘。
