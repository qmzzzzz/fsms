# ADR-014 请求级幂等（Idempotency-Key）与响应回放

- 状态：已接受
- 日期：2026-10-31
- 关联：审计一-1（请求级幂等/防重复提交）、审计一-8（导出审批/配额）

## 背景

业务创建类端点（建用户 / 建角色 / 建权限与批量播种 / 建设备 / 建巡检计划 / 上报火警 / 申请临时授权）
此前都是「点一次就多一条」。重复来源不止用户双击：前端超时重试、网关重放、脚本 for 循环重跑、
用户刷新页面后重新提交。后果不是「多一条脏数据」，而是**两条真实业务记录**——
两条巡检计划会让同一个班组被派两次工，两个同名账号会让审计里出现两个「操作人」；
角色/设备/权限的 code 有唯一约束，重复提交则从「多一条」变成「第二个请求 409 E11000」，
对调用方来说这是「提交失败」的错误信号，会诱发第三次重试。

## 决策

1. 中间件 `src/middleware/idempotency.js` 接受 `Idempotency-Key` 请求头，判据落在 Mongo
   （`IdempotencyRecord`，keyHash 唯一索引），判据键为 sha256(端点 scope + userId + 键)。
2. 同键 + 同载荷（载荷 sha256 指纹）的第二次到达**原样回放**第一次的响应，并带
   `Idempotency-Replayed: true` 响应头。
3. 同键 + 不同载荷 ⇒ 409 `IDEMPOTENCY_KEY_REUSED`；上一次仍在处理中 ⇒ 409 `IDEMPOTENCY_IN_PROGRESS`
   （不排队等待：等待会把「重复提交」变成「延迟提交」，对双击场景更糟）。
4. 业务返回非 2xx ⇒ 删除记录（释放键）。失败的提交没有副作用可去重，而「改了字段用同一个键
   重试」是正常用法。
5. **2xx 但响应体无法回放**（超 64KB、非 JSON、流式/空体）⇒ 记录**保留**并置为已完成的
   「不可回放」态，第二次同键到达返回「已完成、无响应体」并与首次同状态码，响应头带
   `Idempotency-Replay-Omitted: true`。容量上限只能影响「能不能回放这一次的响应」，
   绝不能影响「这次提交是否已经发生」——把上限实现成删键，等于让成功提交在重试时再执行一次。
6. 键**可选**：不带则不做判定。前端在每次业务提交时默认带上（`web-admin/src/utils/idempotency.js`），
   使浏览器路径（真实双击、前端重试）自动受保护，而不一次性打断既有 105 处脚本/第三方调用。
7. **在途记录有租约（5 分钟）**：`in_progress` 超过租约仍没有结论 ⇒ 视为无主，同键重试可
   **原子接管并按首次提交继续执行一次**（判据由 `expiresAt` 反推认领时刻，不新增字段）。
   触发条件里带 `state: 'in_progress'`：那行若在这段窗口里被收尾成 `completed`，条件必不匹配，
   重试拿回放，绝不抢走已交付的结论；接管同时重置 `expiresAt`，并发接管只有一个赢家。
   每次接管发 `idempotency_lease_takeover`（medium，登记在 `constants/failOpenSites.js` 的
   `OTHER_ALERT_SIGNALS`）——它意味着「在**上一次是否已落库未知**时又执行了一遍」。
8. **判据载体的存在性由请求路径自己确认**：进程内首个带键请求先建（或确认）`keyHash` 唯一索引，
   建不起来就**不把插入当判据**——走同一条 fail-open 出口（`degradeOpen` + `idempotency_degraded` 计数），
   失败不写进缓存、下一个请求重试。原因是 `autoIndex` 后台建索引失败只打日志、插入照常成功，
   此时「两个并发同键」都能进：去重**静默失效**且日志全绿。同型教训与同款做法见 `services/reauthTicketStore.js`。

## 理由

- **判据为什么落库**：本仓生产虽是单节点副本集，但「只有一个进程」是部署形态的偶然事实，
  不是安全判据。判据放进程内存，扩容或滚动升级的那一刻它就静默失效，失效形态是「偶发重复建号」——
  最容易被当成偶发故障而反复重试的那一类。
- **为什么只存哈希**：幂等键由客户端生成，语义上接近「这次提交的票据」，不排除有人把工号/邮箱
  塞进去。判据只需要「同一个键 ⇒ 同一个哈希」，存原文等于凭空多一列无用途的潜在 PII。
- **为什么键可空**：强制要求会一次性打断全部既有客户端。把「谁该被保护」交给前端兑现，
  后端保留 `required: true` 开关供后续收紧（本仓暂无强制端点）。
- **存储不可用时 fail-open 放行并告警**：丢的是「去重」这项便利；fail-closed 会让所有创建端点在
  Mongo 抖动时整体 500，把可用性事故扩大成写入事故。与二次验证票据消费的 fail-closed 不同——
  那里丢的是唯一性判据本身（见 ADR-002 的同款推理）。
- **键按用户隔离（哈希里带 userId）**：不同用户恰好用了同一个键（UUID 撞车、或复制粘贴同一份脚本）
  不该互相冲突；也不依赖「全局唯一键」这种容易被客户端行为破坏的假设。
- **为什么在途必须有租约，而不是「等 24h TTL 自然回收」**：`in_progress` 只有**有人来收尾**时
  才会变。进程被杀（OOM/SIGKILL/滚动重启）、事件循环被永久挂起、客户端在响应头发出前断开
  （没有人再进收尾分支）这三种情况下，那一行会永远停在 `in_progress`；把键钉满 24 小时
  意味着调用方在这一整天里对同一件事的每次重试都只能拿到 409，而**服务端并不存在任何恢复动作**。
  租约把「结果未知」的代价从 24 小时压到 5 分钟，且接管是条件更新：只有真的无主才夺得到。

## 备选方案

| 方案                            | 不采纳的原因                                                                              |
| ------------------------------- | ----------------------------------------------------------------------------------------- |
| 只在前端做防抖/禁用按钮         | 挡不住超时重试与网关重放；且把服务端不变量交给客户端兑现                                  |
| 业务表加唯一约束（用户名/code） | 现在就有；语义是「冲突」而不是「同一次提交的回放」，且覆盖不了巡检/火警这类无自然键的实体 |
| 进程内 Map 去重                 | 见上：部署形态一变即失效，且无法跨实例回放响应体                                          |
| 强一致分布式锁                  | 为「防双击」引入一把写锁，代价与故障面都远超收益                                          |

## 后果与局限

- 每个带键的创建请求多一次插入与一次更新；记录 24 小时 TTL 回收，量级与业务写入同阶。
- 回放只对 JSON 响应体生效，且有 64KB 上限：流式/二进制响应（如未脱敏导出）**不接**这道中间件——
  回放一个空的 blob 比不做更糟；导出端点的重复执行归口审计一-8（审批 + 配额 + 水印）。
  注意区分两件事：**不做回放**（响应体丢掉，但键仍占位、去重仍成立）与**不做去重**（键被释放、
  重试真的再执行一次）。上限只作用于前者，见决策 5。
- 判定「过期」时以记录自带的 `expiresAt` 为准（与 TTL 索引同源）：过期行既不回放、也不占位，
  按「没有记录」重新执行——TTL 索引的清理有分钟级延迟，判据不能依赖「它已经被删掉了」。
- 回放的是「第一次的结果」，因此若第一次响应里含短时凭据（本仓创建端点都不含），
  在保留窗口内可被同键重放取回；这是幂等语义的固有代价，不是实现缺陷。
- 中间件挂在 `checkPermission` 之后：未授权请求不产生幂等记录，避免无权限者用任意键污染键空间。
- **租约接管 = 可能重复执行一次**：若上一次其实已经落库（进程在写库之后、回填记录之前被杀），
  接管后的这次会再写一遍，而调用方看到的是正常成功、没有任何提示。这是「把 24 小时死锁换成
  5 分钟后可能重复」的显式取舍，代价由 `idempotency_lease_takeover` 计数暴露给运维。
  要彻底消除它需要两阶段提交或业务侧提交号，两者都超出本中间件的边界（业务表没有统一的
  「提交号」列）。反过来说，**不接管**的代价是把「未知结果」变成调用方一天内不可自愈的死锁 —
  本仓选择前者：可观测的偶发重复，优于无出口的长时间拒绝。
- **租约与过期都由主机时钟判定**：接管条件比较的是「记录里的 `expiresAt`（写入它的那一台机器的时钟）」
  与「本次请求所在机器的 `Date.now()`」。多实例下时钟漂移会直接搬动这条 5 分钟边界——
  快的机器会提前接管（多一次可能重复），慢的机器会让请求停在 409 更久（方向只会更严，不会更松）。
  接管口径因此以集群时钟同步为隐含前置：部署侧已有对时预检（`deployment/clock-sync.md`、`src/tests/deploy/clockSyncPreflight.test.js`）。
