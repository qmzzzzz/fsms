# ADR-019：离线升级包与 Ed25519 签名

> 状态：已接受 ｜ 日期：2026-11-02
> 相关：`scripts/build-offline-bundle.sh`、`scripts/offlineBundlePolicy.js`、
> `scripts/offlineBundleSignature.js`、`scripts/offlineBundleScan.js`、
> `scripts/importOfflineBundle.js`、`scripts/hotUpgradeJob.js`、
> `scripts/hotUpgradeAgent.js`、`src/services/upgradeRequestSignature.js`、
> `src/services/upgradeService.js`、`deployment/hot-upgrade.md` §3.3/§9

## 背景

fsms 的蓝绿零停机升级（2026-10-30 上线）只有一条镜像通道：`compose pull`。
air-gap / 内网机器上这条前提不成立，2026-11-01 先落了宿主侧骨架
（打包脚本 + 纯判据层 + 导入 CLI + `--offline` 换装），但有两块缺口：

1. **触发入口**：导入与换装是两条人工 SSH 命令，没有接进「应用内按钮 → 签名请求 →
   宿主代理」队列；应用侧与前端完全无离线入口。
2. **信任锚**：manifest 只带自校验和，没有签名。manifest 自带的 sha256 只能证明
   「payload 与 manifest 同源」，证明不了「manifest 出自构建机」——包在搬运途中
   （U 盘 / 跳板机）被**整体重写**（manifest + SHA256SUMS + payload 一起换）是检测不到的，
   完全依赖「搬运通道可信」这个无法自动校验的前提。

同类系统（yunkun v1.1.3-offline）用「打包即冻结 + 整包 SHA-256 + 五项校验」解决同一问题；
其校验和仍可被整体重写绕过，本 ADR 在同等的「打包即冻结」语义上加了一把密钥。

## 决定

### ① 触发链路：同一队列、同一端点，请求加 `mode` 字段

`POST /api/security/upgrade/requests` 的 body 增加 `mode: 'registry' | 'offline'`
（缺省 registry，路由层 `isIn` 校验）。安全门完全复用：security:config + 唯一超管 +
步进验证 + strictLimiter——**离线不是绕开二次验证的通道**。

代理执行分两段，顺序不可调换：

1. `importOfflineBundle.js --apply`：包目录由代理在受管 bundles 目录内按 digest 定位
   （请求只点名镜像，永远指定不了目录），全量校验 + `docker load`；
2. `hotUpgrade.js --offline`：本地已有该 digest 才继续，复用蓝绿七步。

定位不到包 / 导入退出码非 0 ⇒ 终态 `aborted_import_failed`：未切流、未动数据。
应用容器保持零 docker 面离线包：**能写 bundles 目录（root 0700）的账号 = 能决定线上跑
什么代码**，这个边界不因离线通道存在而松动；应用经心跳只「看」包摘要、经签名请求只「点名」
digest。GB 级包刻意不走应用内上传（容器只读、无 multipart 栈、1MB body 上限——
且上传会打破上述边界），落位一律由运维 scp/USB 完成。

被拒原因：为离线单独开一套端点/队列（两套安全门必然漂移）；应用内上传离线包
（打破 root-only 边界 + 自实现大文件流式上传引入新攻击面，收益仅为省一条 scp）。

### ② 签名：Ed25519 覆盖 manifest.json 原始字节（`manifest.sig`）

签名对象是 manifest.json 的**原始字节**，刻意不做 JSON canonical——键序、空白、行尾
任何一个字节动了就该验签失败；canonical 化反而会把「字节被改过」洗白成「语义相同」。
payload 完整性由 manifest 内 sha256 逐字节比对承接（导入器既有判据），于是
`信任根(目标机公钥) → manifest 字节 → payload 摘要` 传递覆盖整包。

- 构建机：`build-offline-bundle.sh --sign-key <pem>`（`openssl pkeyutl -sign -rawin`，
  需 OpenSSL ≥ 3.0；签完立即回验）；`FSMS_BUNDLE_REQUIRE_SIGNATURE=1` 可把「忘了签名」
  变成构建期报错。私钥永不出构建机。
- 目标机：`importOfflineBundle.js --pubkey-file <file>` / 宿主代理 env
  `OFFLINE_BUNDLE_VERIFY_PUBKEY`。**配置公钥 = fail-closed**（未签名/验签失败一律拒绝）；
  未配置 = 放行但留痕明示 `signature: 'unchecked'`——是否把「未验签」定为拒绝由部署
  显式选择，运行时不替没分发过密钥的环境兜底。
- 零新依赖：验签用 node:crypto 内置 Ed25519（`crypto.verify(null, …)`），签名用 openssl
  （两侧都是标准 Ed25519；openssl 签 → node 验已于 2026-11-02 手工实测互通，
  见 `deployment/hot-upgrade.md` §10）。

被拒原因：只签 SHA256SUMS（导入器当时根本不读它，签名沦为装饰；即便接入机器校验，
链路也比直签 manifest 长）；HMAC 对称签名（构建机与目标机共享密钥，目标机被攻陷即可
伪造新包，非对称公钥无此问题）；引入外部 CA/签名服务（air-gap 场景不成立）。

### ③ 可用性公布：心跳承载包摘要，扫描永远 fail-soft

代理每轮扫描 bundles 目录（只读 manifest + 跑纯判据 + 白名单，**不算 payload 哈希**——
8GiB×N 每 15s 一轮不可承受），available/invalid 各限 10 条、逐字段截断写入心跳
`bundles`。应用经 `readHeartbeat → getOverview` 透传给前端下拉。三条 fail-soft 纪律：

- bundlesDir 不存在（ENOENT）= 未启用离线通道，不是错误；
- 目录不可读 / 扫描异常 → 原因折进心跳 reasons 或 `bundles.error`，**ready 不变红**——
  离线通道坏了不许拖垮在线升级；
- 心跳里 available 是「自称通过校验的候选」，不是完整性背书——全量校验只在执行时发生。

被拒原因：扫描时顺带算 sha256（每 15s 全量哈希 GB 级文件，代理变成常驻读盘机器）；
应用侧直接读 bundles 目录（应用必须保持 root-only 之外的身份，读不到也不该读到）。

### ④ 签名 canonical 的 mode 分型：不整体升版本域

HMAC 请求签名的 canonical 按模式分型：registry（缺省）维持历史 4 段格式逐字节不变，
offline 追加第 5 段 `'offline'`。走哪型由请求里的 `mode` 唯一决定：`mode=offline` 的请求
绝不接受 4 段签名（在线签名贴到离线请求上无效），不带 mode 的请求绝不接受 5 段
（离线签名被剥掉 mode 后冒充在线也无效）——两条旁路都不存在。

不整体升版本域（`upgrade-request:v2:`）的理由：请求 TTL 只有 30 分钟，但应用镜像与宿主
脚本的发布不保证同批——分型让 registry 请求的新旧两侧互相兼容，滚动期不丢在途请求；
offline 请求本来就只有新版代理能执行，无需兼容。

被拒原因：整体升 v2 + 双试验签（多一条静默兼容路径，且旧代理验不了新应用的在线请求，
发布顺序敏感）；canonical 无条件加第 5 段（同左，旧签名全部失效）。

## 踩过的坑（都被实测钉住，不是推测）

- **AboutView 白名单式归一化会静默丢字段**：`normalizeUpgrade` 逐字段重建快照，
  后端新增 `upgrade.bundles` 后前端拿到的是 undefined，离线 radio 恒禁用——
  「后端加了字段」不等于「前端能看见」。已补 `normalizeBundles` 归一并钉住
  （`web-admin/src/tests/views/aboutViewUpgrade.test.js`）。
- **bash 的 `set -e` 陷阱**：`{ A; [ cond ] && B; }` 组合在条件为假时以非零退出，
  会把整条管线变成假失败——SHA256SUMS 的签名行追加必须用 `if` 分开写
  （`build-offline-bundle.sh` 内有注释）。
- **测试 helper 的签名贴型**：请求构造 helper 的签名必须与 `overrides.mode` 一致，
  「4 段签名 + mode:offline」正是验签要拦的形态——first 失败先怀疑 helper 而不是实现
  （`hotUpgradeAgent.test.js` 的 `requestOf` 注释）。

## 后果

- 正向：air-gap 机器获得与在线同门槛（白名单/二次验证/判据重放）的应用内一键升级；
  「包被整体重写」从不可检测变为 fail-closed 可检测；离线与在线共用同一套蓝绿七步与
  观察窗口，行为差异只剩「镜像从哪来」。
- 代价：多一把密钥的分发与保管流程（构建机私钥 + 目标机公钥）；宿主代理每轮多一次
  bundles 目录扫描（只读 manifest，实测毫秒级）；应用/代理两侧请求体多一个 mode 字段。
- 边界（如实声明）：签名不改变「不自做解包」的原决策；未配置公钥的目标机退回
  「搬运通道可信」模型（留痕可见）；全链路未在真实 air-gap/双色环境实测，
  见 `deployment/hot-upgrade.md` §10。
- 关联测试：`src/tests/deploy/offlineBundle{Signature,Scan,Policy}.test.js`、
  `src/tests/deploy/hotUpgradeOfflineDispatch.test.js`、`src/tests/deploy/deployCommands.test.js`、
