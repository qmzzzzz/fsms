# ADR-020：离线包单文件传包与代理自动落位

## 背景

ADR-019 把离线包定为**目录形态**（`manifest.json` / `manifest.sig` / `SHA256SUMS` /
`payload/fsms-app.tar` 四个条目），并要求「导入器只接受已解压的目录」。这在**校验**层面
是对的（不自己解包 ⇒ 不开新的路径穿越面），但在**搬运**层面留下了一个现实缺口：

运维搬运用的是 scp / U 盘，而「传一个目录」意味着传四个条目、可能还有一个子目录。
漏传任何一个都是可发生的，且**失效形态不可见**：漏了 `manifest.sig` 的包看起来完全正常
（四个文件里少一个，而多数人不会去数），直到目标机 fail-closed 拒绝——现场表现是
「包坏了」，真实原因是「少传了一个文件」。

同族系统（a033/LANSEC）解决这类问题的做法是**单文件 + 安装脚本**：
`lansec-v0.4.0-all-in-one-linux-amd64.tar.gz` 一个文件搬到目标机，`sudo bash ./install.sh`
一步装完。其 `install.sh` 在解压后校验 `SHA256SUMS`，在改动系统之前拒绝坏包。

本 ADR 取它的**传包形态**（单文件），但不取它的**安装语义**（装完即重启服务）——
后者与 ADR-019 §9 第一条纪律（不做自动升级，自动升级 + 迁移 = 半夜静默炸库）直接冲突。

## 决定

### ① 传包形态：单 `.tar.gz` + 外层签名

构建产出新增两个文件（`--archive`）：

```
fsms-offline-<版本>.tar.gz        # 内含 ADR-019 的四个条目
fsms-offline-<版本>.tar.gz.sig    # 对归档 sha256 的 hex 文本的 Ed25519 签名
```

`--archive` **必须**与 `--sign-key` 同时给：目录形态允许未签名（可由搬运前后人工比对
清单兜底），单文件形态不允许——它存在的意义正是「让传一个文件这件事可被机器验证」。

**外层签名签的是归档 sha256 的 hex 文本（64 字节），不是归档本身**：Ed25519 是 one-shot
签名（`crypto.sign(null, buf)` 要求完整 Buffer 在内存），8 GiB 归档整包签必 OOM——而 OOM
在现场的表现是「构建进程被杀」，不是「包太大」。签摘要 = 传递覆盖整包：

```
信任链（三层，逐层收窄）
  ① .tar.gz.sig  →  归档 sha256 文本        （搬运完整性 + 构建机来源）★本 ADR 新增
  ② manifest.sig →  manifest.json 原始字节  （ADR-019）
  ③ manifest 内 sha256 → payload 逐字节      （ADR-019）
```

被拒原因：签归档原始字节（OOM）；只签 manifest 不签归档（解包前无法验证——见下条）。

### ② 解包：调系统 `tar` 且**只解点名条目**（ADR-019 §9 的收窄）

ADR-019 §9 写「不自己做离线包的解包」，其理由是*「在升级链路上再实现一次安全解包，
等于再开一条路径穿越面」*。本 ADR 收窄这句话的**范围**而不改变它的**意图**：

- **不自写 tar 解析器**（在 JS 里手撸 512 字节头、PAX 扩展头、GNU longname —— 那才是
  真正的「再实现一次安全解包」）；
- 改为**调系统 `tar` 且只解点名的条目**，路径穿越面因此不是「被检查掉了」而是**不存在**：

| 步骤       | 做法                                                                    | 为什么这样                                                            |
| ---------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 列条目     | `tar -tzf`，逐条过 `assertSafeRelativePath`（与包内路径**同一条判据**） | 不复制第二套规则                                                      |
| 第一段解包 | **只解 `manifest.json`**                                                | 它是「点名」的唯一来源——payload 的真实名字写在它里面                  |
| 第二段解包 | manifest 声明的 payload + `manifest.sig` + `SHA256SUMS`                 | 归档里任何未被点名的条目**没有落点**                                  |
| 落点复核   | 逐条 `lstat`：普通文件 + 非符号链接                                     | 比解析 `tar -tv` 文本可靠（不解析会随 locale 变化的输出）             |
| 权限       | 解包后**递归 chmod**（目录 0750 / 文件 0640）                           | 不用 `--no-same-*`：那是「请求 tar 别照搬」，而实际落盘的权限要看结果 |

条目名一律排在 `--` 之后（GNU tar 的选项终止符），`tar` 调用收在
`scripts/offlineBundleIntakeExec.js` 一处——评审时能一眼看完整个命令面。

被拒原因：整包全解再扫描（扫描与解包之间总有一个窗口，且「扫描器漏了什么」是单点风险）；
引入归档处理库（本仓无该依赖，且为新能力拉进一条供应链面）。

### ③ 落位校验：复用导入器的**演练模式**，零新增判据

解包到 `bundles/.staging-<uuid>/` 后，直接跑
`node scripts/importOfflineBundle.js --bundle <staging> --dry-run`：
验签、白名单、payload 逐字节比对全部复用，**判据只有一份实现**。通过才 `rename` 到
`bundles/<归档名去扩展名>/`（同目录原子 rename）。

为此**修正了导入器的演练语义**（实测踩中）：原先 `--dry-run` 在校验之前返回，
于是「payload 与 manifest 对不上」的包会被演练报成成功——而落位正是拿演练当预检用，
那会变成「预检通过、apply 才发现坏」的假绿。现在演练**跑完全部校验**再返回，
措辞也从「未做任何改动」改为「全部校验已通过，未 docker load」。

被拒原因：落位侧自己实现一套校验（两份实现必然漂移——ADR-019 已为签名判据立过这条规矩）。

### ④ 传输完成的判定：静默期 + 双读数

`scp` 最自然的用法是**直写目标名**（不是先写 `.part` 再改名）。判据因此不能依赖运维的
命名习惯，只能依赖**时间**与**稳定性**：

- `mtime` 距今 ≥ `OFFLINE_BUNDLE_SETTLE_SECONDS`（默认 60）——挡「正在被写」；
- 两次读数 `size` 一致——挡「已暂停但尚未续传」（scp 中断后 resume 的形态）。

未就绪的条目进心跳 `intake.pending`（应用侧显示「已传完、等待落位」），
**而不是静默忽略**——否则「传了包但下拉里没有」只能 SSH 上去查，那正是本功能要消掉的步骤。

被拒原因：要求运维先写 `.part` 再改名（改变肌肉记忆去配合判据；且忘改名时包永远不落位）。

### ⑤ 每轮最多落一个，且排在消费请求之前

落位耗时（GB 级 sha256 + 解包）会拖长一轮；「每轮一个」让「哪个包失败了」在留痕里
始终可归因到具体归档名。排在消费请求之前是因为**请求瞄的 digest 可能正躺在 inbox 里
等着落位**——先落位后消费，它最迟在**同一轮**就能被满足；反过来要等下一轮 15s，
而用户已经在看着弹窗了。

落位若成功，本轮还重扫一次 `bundles` 并把结果写进心跳，让 `available` 在同一轮就更新。

被拒原因：一次落完所有包（一轮时长不可控，且失败归因会糊成一团）。

### ⑥ fail-soft 第三层：落位失败只影响「这一个包」

与 ADR-019 ③ 同纪律，且**更强**：落位是这条链上唯一会**解包与写盘**的动作，
它的异常面因此最大。三条边界：

- `intakeOne` 是**库函数，绝不 `process.exit`**（实测踩中）：它会被宿主代理在 `runOnce`
  里调用，而代理是长驻调度单元——库函数里一个 `process.exit` 会把整个代理连同心跳
  一起带走，应用侧看到的是「代理离线」，真实原因却只是某个包没签名。
  退出只发生在 `main()`（CLI 形态）；
- 失败折进心跳 `intake.rejected`（归档名 + outcome + reason），**ready 不变红**；
- inbox 目录不存在 = 未启用落位通道（ENOENT 折成空列表，不是错误）。

## 踩过的坑（都被实测钉住，不是推测）

- **相对名进 `resolveWithinRoot` 会按 cwd 解析**：落位目标 `v9.9.9` 被解析到**仓库根**
  之下（实测）。修法：先与根拼成绝对路径再校验。同类问题在条目落点复核处也有一份。
- **目录条目与文件条目混传给 `tar`**：`tar -czf x.tar.gz -C dir payload` 会产出
  `payload/` 与 `payload/fsms-app.tar` 两条，一起交给 `-xzf ... -- payload payload/x.tar`
  会以 `Not found in archive` 失败（GNU tar 1.35 实测）。修法：解包只传文件条目
  （`fileEntriesOnly`），目录随父路径隐式创建。
- **`--dry-run` 不跑 payload 校验**：见 ③。这个坑是「拿演练当预检」才暴露的——
  用 `--dry-run` 只做「结构合规检查」的既有用例全绿，因为没人验证过它到底校验了什么。
- **Git Bash 的 GNU tar 只接受 POSIX 路径**：`C:\dir\a.tar.gz` 与 `C:/dir/a.tar.gz` 都被
  解析成**远程归档**（`host:path` 是 tar 的古老语法），报 `Cannot connect to C: resolve
failed`。生产（Linux）不受影响，但开发机与 Windows 上的测试会成片红，且报错形态指向
  「归档坏了」而不是「路径形态不对」。修法：`toTarPath` 在 Windows 上转 `/c/...` 形态。
- **Mimosa 的「命令注入」判据拦泛化执行壳**：`execFileSync(file, args)` 里 file/args
  都是变量时会被拦（哪怕 file 是 `process.execPath`）。本仓既有先例
  （`provision-mongod.js` 的 tar 调用、`importOfflineBundle` 的 `runInherit/runCapture`）
  都是**字面量 file + 数组字面量 argv**——照此形态写即可通过，判据本身是对的
  （它守的正是「argv 里每个动态元素都能被复核」）。

## 后果

- 正向：搬运面从「四个条目 + 一个子目录」收敛为**两个文件**（归档 + 外层签名），
  且两个文件都可被机器验证；落位全自动（代理每轮最多一个），应用侧行为完全不变
  （下拉里出现即点按钮）；信任链新增一层，覆盖了 ADR-019 覆盖不到的部分
  （解包前的归档本身）。
- 代价：多一次归档/解包（GB 级包的解包耗时在大文件上是分钟量级——故「每轮一个」）；
  多两个环境变量（`OFFLINE_BUNDLE_INBOX` / `OFFLINE_BUNDLE_SETTLE_SECONDS`）；
  落位引入 `tar` 这一条外部依赖（构建机与目标机均需 `tar`，POSIX 系统标配）。
- 边界（如实声明）：**落位后不自动升级**（ADR-019 §9 第一条纪律）；归档内的
  `SHA256SUMS` 不覆盖归档自身（循环），那由外层签名承接；真机 air-gap 未实测
  （见 `deployment/hot-upgrade.md` §10）。
- 关联测试：`src/tests/deploy/offlineBundleIntakePolicy.test.js`（44 例，纯判据）、
  `src/tests/deploy/offlineBundleIntake.test.js`（11 例，真跑 tar 的端到端）、
  `src/tests/deploy/hotUpgradeAgent.test.js`（落位步骤与心跳）、
  `src/tests/services/upgradeService.test.js`（intake 归一化）、
  `web-admin/src/tests/views/aboutViewUpgrade.test.js`（落位状态展示）。
