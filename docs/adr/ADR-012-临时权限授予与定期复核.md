# ADR-012 临时权限授予与定期复核

- 状态：已接受
- 日期：2026-10-30
- 关联控制项：《FSMS 安全设计方案 v2》C-08（权限审批与定期复核）、C-09（特权账号管理中的双人复核部分）

## 背景

V2 安全设计方案把「权限变更」拆成两条要求：一是**任何提权都要有人签批且可追到人**，
二是**权限不能只增不减**——长期持有的高敏权限必须定期复核，超期未复核要能被点出来。
原系统的提权路径只有一条：`PUT /api/users/:id/roles` 直接改角色。它有三个结构性缺口：

1. **没有审批**：一次调用即生效，审计只在事后留痕，没有「事前两个人」这一环。
2. **没有时效**：为一次临时任务（季度报表、故障排查）加的角色，任务结束后没人记得收，权限事实上变成永久授予。
3. **没有复核节奏**：谁持有哪些高敏权限、持有多久，系统里没有一个可查询的口径。

同时仓库的治理面很硬：审计分类（`AUDIT_CATEGORIES`）是带 enum 的模型字段，
新增分类一旦漏登记，该分类的记录会在 `insertMany({ordered:false})` 里被**静默丢弃**
（不入库、不告警）。所以「给临时授权单开一个审计域」不是免费动作。

## 决策

引入「临时权限授予（Privilege Grant）」这一等公民，与角色授权并列，作为**窄化、限时、需签批**的提权通道：

1. **数据**：新集合 `PrivilegeGrant`（`models/PrivilegeGrant.js`）记录被授权人、权限码集合、申请理由、审批链、有效期与终态；索引 `{userId,status,expiresAt}`、`{status,expiresAt,createdAt}`。
2. **入口**：端点挂在 `/api/permissions/grants` 下（`routes/permissionRoutes.js`）——`GET`（列表）、`GET /review`（复核汇总）、`POST`（申请）、`POST /:id/approve|reject|revoke`。权限码为 `privilege:read`、`privilege:grant`、`privilege:approve`。
3. **规则**（`services/privilegeGrantService.js`，由 `services/privilegeGrantFlow.test.js` 与 `routes/privilegeGrantEndpoints.test.js` 双面设防）：
   - **到期在读取路径强制**：有效码的判定条件是 `status === 'active' && expiresAt > now`，`userPermissionService` 只并入满足该条件的码。后台批量过期（`expireDue`）只负责把状态收敛成 `expired` 供查询用，**不是**权限是否生效的前提。
   - **申请人不得自审**：`approvals` 里出现申请人自己即 `PRIVILEGE_SELF_APPROVAL_FORBIDDEN`。
   - **高敏双人复核**：命中 `HIGH_RISK_MODULES`（user/role/permission/security/system/privilege）的码需要 2 名**不同**审批人，其余 1 名；`constants/privilegeGrant.js` 的 `approvalPolicyOf` 是唯一判据。
   - **审批人必须自己持有被授予的每一个码**（通过注入的 `hasPermission` 判定）；不持有即 `PRIVILEGE_APPROVAL_FORBIDDEN`——不允许「批一个我都没有的能力」。
   - **授予范围只能是目录里启用中的码**（`PRIVILEGE_CODE_INVALID`），有效期 1–168 小时（`PRIVILEGE_DURATION_INVALID`），一次最多 20 个码。
   - **每次状态变更都失效目标用户权限缓存**（`setPermissionCacheInvalidator`）；钩子未注册时**抛错而不是跳过**（fail-closed），避免「批准了但不生效 / 撤销了还生效」。
4. **复核**：`services/accessReviewService.js` 提供 `reviewSummary`（各状态计数 + 超期未复核数）、`listOverdueGrants`（`REVIEW_OVERDUE_DAYS = 90`）、`markReviewed`；`scripts/access-review.js` 是运维与 CI 入口：默认打印 JSON 汇总，`--expire` 执行过期收敛，`--fail-on-overdue` 以退出码 1 让「有超期未复核」变成可挂 CI 的判据。
5. **审计分类不新增**：授予类路由挂在 `/api/permissions/grants` 下，`deriveAction` 派生出 `permission_grants`、`permission_grants_review`、`permission_grants_approve`、`permission_grants_reject`、`permission_grants_revoke`，category 仍是 `permission`。

## 理由

- **为什么读路径判到期，而不是靠定时任务**：定时任务会停、会延迟、会在多实例下重复；把「是否生效」交给「读的时候算一次」，漏收敛只影响查询展示，不影响权限边界。
- **为什么审批链存快照**（`approvals[{by,name,at}]`）：被授权人和审批人都可能改名或被删，审计要能回答「当时是谁批的」，必须就地固化。
- **为什么撤销也要有权限码**：撤销是回收动作，风险方向与授予相反，但仍要求 `privilege:grant`，避免只读账号就能收回别人权限。
- **为什么不复用角色**：角色是长期、可累积、可被他人复用的容器，天生不适合表达「给甲、到某个时刻为止、只这几项」；混用会让「角色」同时承担长期与临时语义，复核时无法区分。
- **为什么不新开 `privilege` 审计分类**：`AUDIT_CATEGORIES` 的取值全集要与 `ROUTE_CATEGORY_MAP`、模型 enum、前端 i18n 标签、导出列映射同时改；漏一处就是**记录静默丢弃**。而临时授权在语义上属于「权限治理」的一部分，与权限目录同域查询更自然。

## 备选方案

| 方案                                             | 结论 | 理由                                                             |
| ------------------------------------------------ | ---- | ---------------------------------------------------------------- |
| 只加角色、靠人工记得收回                         | 否决 | 正是本 ADR 要修的缺口；「记得」不是控制措施                      |
| 引入通用审批引擎（工作流表 + 状态机 + 多级条件） | 否决 | 当前只有这一个审批场景，通用引擎的配置面会成为新的攻击面与维护面 |
| 到期由后台任务独占判定                           | 否决 | 任务停摆即无限期有效，属 fail-open                               |
| 新开 `privilege` 审计分类                        | 否决 | 见「理由」末条；分类扩容的代价远大于同域查询的收益               |
| 允许审批人自审（简化流程）                       | 否决 | 一人闭环等于没有审批，C-08 的核心判据就是「申请人 ≠ 审批人」     |

## 后果与局限

- **C-09 只落地了「双人复核 + 时效」这一半**：代码里没有堡垒机或跳板机会话代理，也没有 JIT 提权会话录屏。「谁能拿到高敏码」已可控、可追、会过期，但「拿到之后在什么通道上操作」仍由操作系统与运维流程保证，属已知残余缺口。
- **前端入口已补齐（2026-10-30）**：`web-admin/src/views/PrivilegeGrantView.vue` 提供状态筛选、复核汇总五计数、申请表单与签批/驳回/撤销三条决定链路；菜单挂 `/system/privilege-grants`，路由 `meta.permission = privilege:read`，按钮门控 `privilege:grant|approve` 与后端 `checkPermission` 同码。高敏授予的「还需几人签批」在提交提示里显式给出。
- **到期收敛是粗粒度扫批**：`expireDue` 按 `{status:'active', expiresAt ≤ now}` 批量置为 `expired`，记录保留不删（审计要能回看）。「已过期」状态的可见延迟取决于定时器频率（默认每小时），但权限本身不受影响。
- **复核是「提议 + 留痕」，不是自动降权**：`--fail-on-overdue` 能让超期可见，但不会自动撤销——是否收回是管理判断，系统只保证这个判断不会被悄悄跳过。
- **授予面受审批人权限约束**：审批人不能批出自己没有的码，因此「两名中层批出其自身权限之外的能力」需要额外安排超管参与，这是刻意的。
