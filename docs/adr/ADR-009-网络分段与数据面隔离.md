# ADR-009：网络分段（边缘/监控面 + 数据面 internal）

- **状态**：已接受
- **日期**：2026-10-17
- **涉及**：`docker-compose.yml`（networks 段、各服务 networks 归属）、`docs/architecture.md` §4；审计 finding F-06

## 背景

2026-10-01 的审计 finding：compose 里六个服务（app / mongo / redis / prometheus /
alertmanager / grafana）共处一张扁平的 `fire-safety-net` bridge。于是：

- Grafana 的**数据源 URL 可配任意地址** ⇒ 它能直连无密码的 redis（删黑名单键 = 撤销封禁、
  清限流计数 = 解除封顶），也能直连 mongo；
- 同网任一容器被攻破即得 mongo 全量读写，而"数据面不可达"这条边界在**网络层**并不存在，
  只能靠应用层鉴权兜；
- 架构文档画的又是另一回事（把 mongo 画在 `fire-safety-net` 里与 app 同网），
  按图排障会连错网络。

## 决策

拆成两张网络，**服务归属固定**：

| 网络              | 成员                                   | 属性                                                |
| ----------------- | -------------------------------------- | --------------------------------------------------- |
| `fire-safety-net` | app、prometheus、alertmanager、grafana | bridge，可出网（app 的 webhook 走这张）             |
| `data-net`        | **只有** app、mongo、redis             | bridge + `internal: true`（不接宿主 NAT、不出外网） |

- **mongo / redis 只接 `data-net`**：没有宿主端口映射，监控栈与宿主发布面都摸不到。
- **app 是唯一同时接入两张网络的服务**。原因有三条，缺一条都不成立：
  1. 要被 prometheus 抓取（`prometheus → app:3000/metrics`，走 `fire-safety-net`）；
  2. 要出网发安全告警 webhook（`securityAlertDelivery`，走 `fire-safety-net`）；
  3. 要访问 mongo/redis（走 `data-net`）。
- **允许直连 app 的来源**（其余一律视为越界）：宿主 Nginx（`127.0.0.1:3000` 反代）、
  prometheus（抓取）。grafana / alertmanager 不访问 app 的 HTTP 面——前者只查 prometheus，
  后者只接收 prometheus 推送。
- **新增服务时的默认归属**：`fire-safety-net`。加进 `data-net` 必须同时改本文与
  `docs/architecture.md`，并说明"它为什么需要数据面"。

## 理由

- **隔离要在网络层成立，不能只靠鉴权**：redis 上承载的是限流计数与封禁黑名单，
  它们的**可写性**本身就是权限（改一个键等于撤销一次封禁）。把可达性降到零，
  比"给 redis 加密码、再指望每个消费方都配对"更可靠。
- **`internal: true` 是关键的一半**：只拆网络但不设 internal，容器仍可经宿主 NAT 出网，
  数据面容器被攻破后依然能外联。这条属性让"数据面不出网"成为结构事实。
- **app 双网络而非加一个代理容器**：加代理会引入第三跳与额外故障点，而 app 本身就是
  唯一需要横跨两侧的组件——把它显式标注为"唯一的数据面访问者"，边界比藏起来更清楚。

## 备选方案

- **单网络 + redis 密码 + mongo 认证**：可行但把边界交给凭据；且 Grafana 的数据源
  可配任意 URL，凭据泄露或配置错误时边界即刻消失。被否。
- **给监控栈单独一张网、数据面保持默认 bridge**：解决了 Grafana 直连 redis，
  但 mongo/redis 仍可出网（被攻破后能外联），且宿主端口一旦被误加就重新暴露。被否。
- **引入服务网格（mTLS + 授权策略）**：能力更强，但对本项目的规模是过度设计，
  且把"网络边界"变成"控制面配置"，排障成本上升。被否（若将来上 K8s，见 F-12 的多副本议题）。

## 后果与局限

- 本地排障不能再用"同网直连 mongo"的捷径：需要在 app 容器内执行，或临时给 mongo
  加 `127.0.0.1:27017` 映射（compose 里已有注释说明这个临时改法）。
- 监控栈若要新增"直连数据库的 exporter"，必须重新评估本决策（那正是被这条边界挡住的形态）。
- 宿主端口全部绑 `127.0.0.1`：公网访问只能经宿主 Nginx。端口清单见
  `docs/architecture.md` §4 的表格，与 compose 的一致性由
  `src/tests/deploy/architectureDocContract.test.js` 钉住。
- 网络分段不解决**多副本**问题（审计 F-12/F-13）：那属于实例间状态与资源配额，见 ADR-005。
