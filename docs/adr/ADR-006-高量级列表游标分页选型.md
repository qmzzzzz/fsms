# ADR-006：高量级列表游标分页选型

- **状态**：已接受
- **日期**：2026-08-30
- **涉及**：`src/utils/cursorPagination.js`、设备/告警/巡检/审计日志列表接口；优化清单 E-2

## 背景

设备、告警、巡检、审计日志等列表随运营时间单调增长。原 offset 分页（`skip((page-1)*limit).limit(limit)`）有两个随规模恶化的开销：

1. **深分页退化**：MongoDB 的 `skip(N)` 需要扫描并丢弃前 N 条，代价 O(skip+limit)——第 500 页比第 1 页慢一到两个数量级；
2. **`countDocuments` 全量统计**：返回 `total/totalPages` 需要每次全表计数，在深分页场景与 skip 并列为最大开销。

且 offset 在并发写入下有页间漂移：翻页过程中新增/删除记录会让条目在相邻页重复出现或凭空消失。

## 决策

高量级列表改用**游标（Keyset/Seek）分页**，工具集中在 `src/utils/cursorPagination.js`：

- **游标编码**：不透明 `base64url(JSON{v, id})`——`v` 为排序键值，`id` 为文档 `_id`。解码端对非法输入（非字符串/超长/非 base64url/非对象/缺字段/非法 ObjectId）一律抛 `ApiError(400)`，客户端无法注入查询结构。
- **平局裁决**：排序键可能重复（同一秒多条记录），条件固定为 `(field < v) OR (field == v AND _id < id)`（降序；升序换 `$gt`）。**光有这条子句不保证无重复无遗漏**：`.sort()` 必须同样带 `_id` 次级键且与子句同向（降序 ⇒ `{field:-1,_id:-1}`）。单字段索引下的隐式平局序是 `(key, RecordId 升序)`，与降序子句方向相反，实测 5000 条 / 每页 20 时重复 950、漏 3950（79% 永久不可达）并提前 `hasMore:false`。
- **两处改动各挡一类风险**：`.sort()` 带 `_id` 挡**正确性**（顺序契约与计划、索引形态无关），复合索引挡**代价**（否则每页从索引有序扫描退化成全表扫描 + 阻塞排序）。本机 2×2×2 矩阵（2000 条 / 40 个等值组 × 50 / 每页 20，块内插入次序为「自然正序」）：

  | 索引形态            | `.sort({ts:-1})`                   | `.sort({ts:-1,_id:-1})`          |
  | ------------------- | ---------------------------------- | -------------------------------- |
  | 只有 `{ts:-1}`      | **漂移**：重复 380、漏 1580、41 页 | 一致，但 `SORT→COLLSCAN` 扫 2000 |
  | 有 `{ts:-1,_id:-1}` | 一致，`LIMIT→FETCH→IXSCAN` 扫 20   | 一致，`LIMIT→FETCH→IXSCAN` 扫 20 |

  读法：丢数据只发生在「单字段索引 + 只排主键」这一格。所以部署顺序上，「代码先上线、迁移后跑」的那段窗口里是显式 `_id` 次级键在兜正确性（代价是这期间每页扫全表，见下面理由一节）；而「迁移先跑、`.sort()` 还没带 `_id`」那一格也恰好一致——但那是索引隐式序（`(key, RecordId)`）碰巧与子句同向的偶然：同一批夹具改成组内反序插入，四格全绿。一条查询漂不漂预知不了，所以方向必须由 `.sort()` 写死，不能留给选型。

- **翻页能力表达**：游标模式不返回 `total/totalPages`（省掉全量计数），改以 `hasMore/nextCursor` 表达；拉取用 `limit+1` 探测是否还有下一页。
- **兼容语义**：客户端混传 `cursor` 与 `page` 时 **cursor 优先**；不提供排序键自由切换（排序键变更需重新从第一页开始）。

## 理由

- 每页代价恒定 O(limit)，与页深无关；正好消除深分页与计数两大开销。
- 范围查询利用 `(排序键, _id)` 同向复合索引的前缀，每页只扫 `limit` 量级。注意"与现有列表索引形态兼容"这一条当初并不成立：原有索引是单字段 `{排序键:-1}`，加上 `_id` 次级排序键后退化为 COLLSCAN + 阻塞排序（实测 `totalDocsExamined` 20 → 5000，大集合还会撞 32MB 内存排序上限而 500）⇒ 必须先建 `{排序键:-1,_id:-1}` 再改排序，存量库对齐走 `migrations/20260926000000-cursor-tiebreak-compound-indexes.js`。报警/巡检/审计三条是**替换**旧的单字段索引（最左前缀覆盖旧键，写放大为零），唯独 `auditlogs` 只能**新增**：它的 `{timestamp:-1}` 挂着 TTL，而 mongod 6.0 实测拒绝在复合索引上挂 `expireAfterSeconds`。
- 不透明游标把「排序键+方向+值类型」的约定留在服务端，未来换排序策略不破坏客户端契约（旧游标解码失败即 400 重查）。

## 备选方案

- **继续 offset + 禁用深页**（限制最大页码）：实现最省，但只是掩盖问题；审计追溯类需求天然要深翻，被否。
- **搜索式分页**（仅按条件过滤，不提供页码）：适合检索界面，但管理后台的表格翻页心智强，被否。
- **`$search`/全文引擎**：引入额外组件与运维成本，当前数据量级不需要，暂缓。

## 后果与局限

- 客户端失去「跳第 N 页」能力，只能前后翻页——管理界面已按此交互收敛；导出/统计不走分页接口，不受影响。
- 游标只在同一排序方向内有效；用户切换排序列时前端必须丢弃游标（接口以 400 兜底非法游标）。
- `explain` 抽查（`scripts/perf/explain-spotcheck.js`）纳入性能回归，防索引缺失导致游标查询退化为全表扫描。
