# ADR-016 管理员重置口令后的口令复用收口

- 状态：已接受
- 日期：2026-11-01
- 关联：审计二-2（管理员重置口令是否写口令历史）、ADR-015（登录失败触发的人机挑战与锁定收口，其「关联」行提出本问题）、审计一-7（数据分类分级台账）

## 背景

`PUT /api/security/users/:userId/password/reset`（P1-2，管理员账号救济主通道）在落地时只做了三件事：
签发一次性临时口令、`tokenVersion++` 踢掉全部会话、`mustChangePassword=true`。**被替换掉的那一代口令没有任何留痕**，
于是这条链是通的：

1. 用户口令 `P0` 因泄露/失窃被管理员重置；
2. 用户（或拿着临时口令的攻击者）首次登录被强制改密，改成 `P1`；
3. 用户再把口令改回 `P0` —— `PASSWORD_REUSED` 只查 `User.passwordHistory`（HMAC 摘要），而重置路径
   **没有往历史里写任何东西**，`P0` 不在历史里，于是放行。

即「管理员重置」这道救济动作可以被用户自己撤销，而撤销回来的正是最该作废的那条口令。

为什么重置路径没有写历史：`utils/passwordHistory.js` 记的是**被替换掉的口令的 HMAC 摘要**，算摘要需要明文；
而重置路径能拿到的只有库里那条 bcrypt 摘要——**明文不可知**（也不该可知）。所以「照抄改密路径的写法」在
密码学上不成立：这不是漏了一行代码，而是缺一个能表达「我知道旧口令的可校验摘要、但我没有它的明文」的载体。

## 决策

1. `models/User.js` 新增 `passwordRetiredHash`：`{ type: String, select: false }`，**不设 default**
   （default 会让裸载入的文档把默认值写进 save 的 `$set`，反过来抹掉保护，机制见
   `tests/services/userSaveCredentialWipe.test.js`）。同时进 `USER_RESPONSE_EXCLUDE_FIELDS`
   （与 `password` / `passwordHistory` 同规格：只排不减）。
2. 重置路径（`controllers/securityController/admin.js::resetUserPassword`）：用
   `User.findById(userId).select('+password +passwordRetiredHash')` 取出旧 bcrypt 摘要，在同一个原子 `$set` 里写
   `retiredHashForReset(user)`——与 `password` / `tokenVersion` / 范围快照同一条条件更新，
   不存在「新口令已生效、退役摘要还没写」的窗口。取值规则：当前口令仍是**未被消费的临时口令**
   （`mustChangePassword` 未清）且已有摘要时**保留已有摘要**，否则写本次被替换掉的口令摘要。
   连续两次重置（临时口令没送达/过期）替换掉的只是管理员签发的临时口令，照写覆盖会把真正要防的
   那一代用户自选口令**静默**放开——这是本项保护最容易被绕过的一种运维路径。
3. 改密路径（`services/authService/password.js`）：`assertPasswordRotatable` 在 HMAC 历史之后追加一次
   `matchesRetiredPassword(user.passwordRetiredHash, newPassword)` 比对，命中即返回 `PASSWORD_REUSED`。
4. 判据自带形态闸与失败口径：摘要不匹配 `/^\$2[aby]\$/`、或比对抛错 ⇒ 记 `logger.error`、**本条按放行处理**。
5. 分级台账：`constants/dataClassification.js` 登记
   `'User.passwordRetiredHash': F('L4','bcrypt',false,…,'account')`；`docs/data-classification.md` 的计数同步（57 → 58）。
6. 删除权（`services/userService.js::anonymizeUserDocument`）：匿名化时把 `passwordRetiredHash` 与
   `password` 改写同批置空。账号已停用、会话已吊销、口令已随机化，这份摘要只剩「可离线爆破的旧口令」
   这一种用途 ⇒ 留着违反数据最小化，注销后必须抹掉（与 realName/phone/email/avatar 同一张抹除清单）。

## 理由

- **为什么留 bcrypt 摘要，而不是换一种「能算明文摘要」的写法**：改密路径判「是否复用」只需要*能否验证
  候选口令等于那条旧口令*，bcrypt 摘要恰好够用；把它再转成 HMAC 需要明文，而明文在重置路径上根本不存在。
  唯一的替代是「重置时要求提供旧口令」——那等于把救济通道变成需要旧口令才能走，与救济的目的相反。
- **为什么不复用 `passwordHistory`**：语义不同。历史记的是「已退役口令的 HMAC 摘要」，其价值是
  「读到它能当『某口令是否用过』的预言机」；退役摘要记的是**可离线爆破的 bcrypt 摘要**，是更重的凭证材料。
  混进同一个数组会让两件事的泄漏后果、分级理由、清理策略一起含糊。
- **上限 1 条是有意的**：`utils/passwordHistory.js` 头部已经算过「bcrypt 在改密端点上每条约 250–300ms」的账，
  `HISTORY_DEPTH=5` 走 HMAC 正是为了避开这个成本。若退役摘要也留 N 条，改密端点就要背 N×250ms，而它换来的
  只是「连续被重置两次以上、且要逐个试回」这一种场景。取 1 条把成本钉死在一次比对，且只出现在**曾被管理员
  重置过口令**的账户上（新账户与从未被重置的账户零成本）。
- **判不了就放行**：这是**加强层**，主防线（当前口令必须正确 + HMAC 历史 + 强度校验）不依赖它。让一次数据
  形态异常把改密端点变成 DoS 面（所有人都改不了口令）比它挡住的场景更糟；代价是能写库里摘要形态的攻击者
  可绕过这一层——而能写库的攻击者本来就能直接改口令。
- **错误码复用 `PASSWORD_REUSED`**：用户侧要做的动作与历史命中完全相同（换一条没被重置掉的口令），
  拆一个码只会多一份前端文案与一致性维护面；两个来源在服务端日志里区分得开（`退役摘要命中` vs `命中复用历史`）。

## 备选方案

- **（B）重置时把临时口令写进 `passwordHistory`**：不予采用。临时口令已经会在首次强制改密时以「被替换掉的
  旧口令」身份进历史（`withPrevious(user.passwordHistory, current.value)`），重置时再写一遍是重复；而它
  **完全挡不住**本 ADR 要挡的那条链（`P0` 仍然不在历史里）。附带代价是 `passwordHistory` 会同时含两种来源的
  条目，语义进一步变浑。
- **（C）重置时清空 `passwordHistory`**：不予采用。这是**反向**动作：清空历史会让更早的复用重新可行。
- **（D）留完整历史（N 条 bcrypt 摘要）**：暂不采用，理由见「上限 1 条」。若将来出现「必须覆盖连续多次重置」
  的合规要求，改法是给退役摘要另建**受限读**的集合（不塞进 User 文档），并把比对移到异步任务里——
  不要在请求路径上叠 bcrypt。
- **（E）不做，只在文档里声明残留**：不予采用。审计把它列为缺陷而非已接受风险，且修法在请求路径上的成本是
  一次比对、在库里是一个可选字段。

## 后果与局限

- 库里多一份可离线爆破的摘要（L4 凭证材料）。窗口是「最近一次重置替换掉的**用户自选**那一代口令」；
  下一次重置只在被替换掉的也是用户自选口令时才覆盖它（连续重置保留更早那代）⇒ 实质仍是
  **只覆盖一代**，再往前的退役口令不受保护。
- **只覆盖一代是刻意的，但连续重置那一格不能丢**：被替换掉的口令是不是「用户自选」由
  `mustChangePassword` 判定（它只在管理员签发口令时为 true、用户成功改密时清掉）。
- 文案口径：命中退役摘要复用 `PASSWORD_REUSED` 与「不能与最近 {historyDepth} 条使用过的密码相同」
  这句前端文案；被拒口令严格说不在最近 N 条历史里（它是重置前那一代，且在下一次重置前一直有效）——
  文案是**下界**，不算错但不够精确。用户要做的动作相同，拆一份文案要动错误码注册表 + 两个控制器 +
  两套 i18n + 前端映射，故按「错误码复用」同一取舍接受；服务端日志里两个来源区分得开。
- 曾被重置过的账户在改密端点各多一次 bcrypt 比对（~250–300ms，走 `utils/bcryptWorkerPool`，不在请求线程上算）。
- 重置路径现在要把旧口令的 bcrypt 摘要读进进程（`select('+password')`）：这是本决策的必要代价。
  响应与日志口径不变——`passwordRetiredHash` 进 `USER_RESPONSE_EXCLUDE_FIELDS`，审计只记「发生了重置」不记摘要，
  临时口令仍然只进一次性响应体。
- 残留：**重置前的口令明文不可知**，因此「用户把口令改回重置前那条」只在它正是被替换掉的那一代时才被挡住；
  跨两次以上「重置→改密」的更早口令不在覆盖内（见备选方案 D）。这条残留同时写在 `docs/threat-model.md` §3。
- 删除权：匿名化把 `passwordRetiredHash` 与口令改写同批置空，因此「注销后仍留旧口令摘要」不是本决策的残留；
  同一份抹除清单由 `tests/security/businessRetentionAndAnonymization.test.js` 用真库 before/after 判据盯着。
- 兼容性：存量文档没有该字段 ⇒ 读到 `undefined` ⇒ 视作「无退役摘要」放行，无需数据迁移。
