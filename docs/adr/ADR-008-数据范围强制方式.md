# ADR-008：数据范围（dataScope）的强制方式——显式登记而非路由级中间件

- **状态**：已接受
- **日期**：2026-09-17
- **涉及**：`src/middleware/rbac.js`、`src/constants/dataScopeFields.js`、全部 `src/controllers/*.js`、`src/routes/*.js`
- **来源**：2026-09-16 全面代码审计报告 §5.1「104 条路由中 `dataScope` 中间件的挂载数 = 0」

## 背景

审计报告指出：数据范围过滤**全部**由各控制器手工实现，路由层零强制。报告原话：

> 每新增一个涉及敏感实体的 handler，作者**必须记得**手工调用范围过滤，否则就是越权。
> **没有任何自动化手段能发现遗漏**——P0-1 的越权缺陷（`PUT /api/users/:id`）正是这种架构缺陷的必然产物。

报告建议「评估将 `dataScope` 提升为**路由级中间件**，从架构上消除越权面」。

本次实测（2026-09-17，逐文件扫描 `src/routes` 54 条写路由 + `src/controllers` 99 个 handler）：

| 类别                                         | 数量        | 说明                                                                                           |
| -------------------------------------------- | ----------- | ---------------------------------------------------------------------------------------------- |
| handler 显式调用范围 helper                  | 20 条写路由 | `isDeviceInScope` / `isInspectionInScope` / `assertRecordInScope` / `applyRoleScopeToQuery` 等 |
| 路由块声明 `PERMISSION-EXEMPT`               | 14 条       | 公共端点（register/login/refresh）与恒为本人资源的端点                                         |
| 仅自作用域（操作对象恒为 `req.user.userId`） | 15 条       | MFA、会话管理、本人密码等                                                                      |
| **两者皆无**                                 | **5 条**    | 见下                                                                                           |

**5 条待定项**：

| 路由                          | handler                  | 判定                                                                                                                                                                              |
| ----------------------------- | ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/inspections`       | `createInspection`       | **已确认无缺口但未登记**：创建动作的"范围"体现为 `assignedTo` 白名单——路由校验器限定为 ObjectId 数组，服务层不接受其他归属字段。它是"新建资源"而非"读/改他人资源"，故无横向越权面 |
| `POST /api/permissions`       | `createPermission`       | 权限定义属**全局管理面**，由 `checkPermission('permission:create')` 把关；不存在"部门权限"这一业务概念                                                                            |
| `POST /api/permissions/batch` | `batchCreatePermissions` | 同上                                                                                                                                                                              |
| `PUT /api/permissions/:id`    | `updatePermission`       | 同上                                                                                                                                                                              |
| `DELETE /api/permissions/:id` | `deletePermission`       | 同上                                                                                                                                                                              |

即：**5 条全部有合理解释，无一为真缺口**。但这恰好印证了报告的核心论点——这 5 条与真缺口的**外在表现完全一致**（都"没有 scope 调用"），只能靠人工逐条读业务语义才能区分。

## 决策

**不引入路由级 `dataScope` 中间件**，改为「**显式登记 + CI 守卫**」。

理由见下节。守卫落在 `src/tests/routes/dataScopeContract.test.js`。

## 理由（为何不选路由级中间件）

### 1. 范围策略是「按 handler 分支」的，中间件无法在路由层决定

`dataScope` 的实际形态由**同一 handler 内的不同代码路径**决定，而不是由路由决定：

- `userController.updateUser`：本人改自己 → 放行；改他人 → `assertRecordInScope`；改 `department` 字段 → 额外要求 `department` 范围（P0-1 修复引入的 `touchesScopeField` 判定）
- `securityController.viewSensitiveData`：本人查看免鉴权；查看他人要求 `opLevel > targetLevel`
- `deviceController.listDevices`：列表走 `buildDataScopeFilter`（查询过滤）；详情/写操作走 `isDeviceInScope`（单文档判定）——**同一个 `dataScope` 对象，两种消费方式**

路由级中间件只能产出「范围描述对象」，无法代替上述判定；若中间件试图在路由层拒绝，必须知道请求体里是否含敏感字段——那是业务逻辑，不是路由关注点。

### 2. 单文档判定的时机不可前置

`assertRecordInScope(dataScope, doc, ...)` 需要**先加载文档**才能判定（`isRecordInScope` 要读 `doc` 的 `createdBy` / `location.building` / `maintenanceRecord.operator`）。路由中间件运行在控制器之前，此时文档尚未加载。可行的替代是中间件挂 `req.loadScopedDoc` 之类的惰性加载器，但那只是把控制器的 3 行样板换成中间件 + 约定的 3 行调用，**并未消除"必须记得用"这一根本问题**，反而多了一层间接。

### 3. 查询过滤与响应裁剪无法在中间件完成

- 列表接口需要把范围编译成 Mongo 过滤条件（`buildDataScopeFilter`）后传给 service，与业务筛选条件合并——合并顺序、`$or` 组合方式随接口而异；
- 响应裁剪（如列表里逐条过滤）需要访问已查询的结果集。

两者都发生在 service 调用边界，中间件不在那个位置。

### 4. 真问题不是「没有中间件」，而是「无法自动发现遗漏」

审计报告的原话是「**没有任何自动化手段能发现遗漏**」。这一点与是否使用中间件无关——即使挂了中间件，控制器仍可能**绕过 `req.dataScope` 自己查全表**，静态扫描同样发现不了。

因此本 ADR 选择的解法直接对准"可发现性"：**把"这个写路由如何实现数据范围"变成必须显式登记的事实，并由 CI 守卫强制登记**。

## 后果与局限

### 落地方式

`src/tests/routes/dataScopeContract.test.js` 对全部写路由（POST/PUT/PATCH/DELETE）逐条断言三选一：

1. handler 体内出现范围判定调用（白名单正则，含 `is*InScope` 等本地包装）；
2. 路由块内声明 `SCOPE-EXEMPT: <理由>`（理由不可为空）；
3. handler 体内出现自作用域引用（`req.user.userId` / `req.user.id`）。

任一不满足即 CI 红，**必须显式登记**才能通过。这不能阻止开发者写错范围逻辑，但能阻止"**根本没想过范围问题**"——后者才是 P0-1 的成因。

### 局限（明确声明，避免过度承诺）

- **不能替代逐条业务审查**：本守卫只能证明「作者处理过范围问题」，不能证明「处理正确」。例如把 `department` 范围误写成 `self` 仍会通过。
- **正则判据有误报/漏报可能**：本地包装函数名不在白名单内会误报（已收录 `is*InScope` 模式与 `assertRecordInScope` 等）；反之，若有人把范围调用写进死分支，守卫无法识别。
- **豁免标记可能被滥用**：`SCOPE-EXEMPT` 只需非空理由即可通过，与 `PERMISSION-EXEMPT` 同理——它把"沉默的遗漏"变成"可评审的声明"，但声明本身仍需人来判断对错。
