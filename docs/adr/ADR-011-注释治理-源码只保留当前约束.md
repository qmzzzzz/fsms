# ADR-011 注释治理：源码只保留当前约束

- 状态：已接受
- 日期：2026-10-26

## 背景

2026-10-25 审计（§3.1）测得生产代码注释密度 39.2%（22,504 注释行 / 34,799 代码行，
`src/**` 排除 `src/tests/**`）。高密度本身不是缺陷——本仓的注释大量承载「为什么必须这样」
（安全裁决、失败方向、不可逆后果），删掉会直接降低可维护性。真正的问题是其中混入了
**变更史**：

- 「此前写作 X」「原先漏了 Y」「2026-10-15 由 A 收紧到 B」「本轮之前没有断言」；
- 修复叙事与当前代码混排，读代码的人要先还原历史才能确认现在的约束；
- 历史描述会随代码演进失真，而它看起来像事实，比没有注释更危险；
- 行号锚点（`file.js:123`）随任何一次编辑漂移，已经需要专门的闸门兜底。

## 决策

1. **源码注释只写当前约束与不明显的 Why。** 禁止变更史叙事（「此前 / 原先 / 已修复 /
   本轮 / 某日整改」）。当前代码为什么只能长这样、违反后果是什么，保留；它是怎么变成
   这样的，不保留。
2. **变更史归 CHANGELOG，权衡归 ADR，一次性迁移说明归审计报告 / PR。** 源码里可以指向
   它们（`见 ADR-00X`、`见 CHANGELOG 2026-10-26`），但不复述内容。
3. **锚点优先符号锚定。** 引用代码位置时写「文件名 + 符号/谓词」（如
   `securityHeaders.js` 的 `frameguard`），必须给行号时由 `commentAnchorFreshness` /
   `bareAnchorAttribution` 登记并在漂移时转红，不得裸写未登记的行号。
4. **密度棘轮只降不升。** `scripts/commentDensity.js` 按上述口径统计生产代码，基线落
   `scripts/commentDensity.baseline.json`；`src/tests/ci/commentDensityRatchet.test.js`
   强制：已登记文件的注释行数不得增加，新增文件密度 ≤ 30%，总量不得回升。
   `--update-baseline` 在存在回退时拒绝写盘。

## 理由

- **失真成本**：历史注释与代码不同步时没有任何机制会发现；保留它等于让读者把过期
  结论当现状。git 历史与 CHANGELOG 已经完整记录了「发生过什么」。
- **评审成本**：注释密度越高，改动时越难判断哪一段仍是约束；把「当前约束」与
  「变更记录」分开后，diff 里新增的注释应当只解释新增的约束。
- **棘轮而非一次性清理**：一次性删几千行注释的 diff 无法逐条复核，且容易误删
  关键约束；基线 + 只降不升让每次改动顺手收紧，风险局部化。

## 备选方案

- **一次性重写全部注释**：diff 规模过大，安全相关约束无法逐条确认，且会与并行改动
  冲突。不采用。
- **只靠 ESLint 规则**：现有规则能限制行数/风格，但无法度量「历史叙事占比」，也无法
  阻止增量。不采用。
- **完全禁止注释**：会丢掉本仓最有价值的部分（失败方向、顺序约束、不可逆后果）。
  不采用。
- **只治理测试注释**：测试不在密度口径内，且其头注释多为「这条用例为什么存在」（属于
  当前约束）。不采用。

## 后果与局限

- 每个文件新增一行注释，需要先删掉该文件一行历史注释（或由评审确认例外并
  收紧基线）。这是一种有意的摩擦：注释是维护成本，不是免费文档。
- 密度是**行数**指标，不能区分「一行关键约束」与「一行废话」；棘轮只防增长，
  注释质量仍由评审负责。
- 基线更新只能在改善时进行（脚本拒绝回退），但基线与测试常量仍可能被同时手改；
  这与其他棘轮（lint-ratchet）同级的信任边界，靠代码评审兜底。
- 测试代码不在棘轮内：测试头注释的「为什么需要这条用例」是当前约束，不按历史叙事处理。
