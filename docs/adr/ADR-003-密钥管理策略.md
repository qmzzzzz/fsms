# ADR-003：密钥管理策略

- **状态**：已接受（2026-10-20 更新「当前状态」与 AES 用途；决策未变）
- **日期**：2026-08-29（追溯建档）
- **涉及**：`src/config/secrets.js`、`src/config/validate.js`、`src/utils/encryption.js`、`src/utils/piiCrypto.js`、`scripts/migrate-mfa-secret.js`、`scripts/migrate-pii-encryption.js`、`scripts/resign-audit-hmac.js`

## 背景

系统依赖多把密钥（JWT 签发、数据加密、审计签名、登录 ECDH 私钥等）。需要明确：密钥从哪来、如何注入、如何轮换、以及启动期如何拦截弱配置。

## 决策

**1. 密钥清单与用途**（`src/config/secrets.js` 的 `FILE_BACKED_SECRETS`）：

| 密钥                                                                                                                | 用途                                                                                                                                    |
| ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `JWT_SECRET` / `JWT_REFRESH_SECRET`                                                                                 | 访问 / 刷新令牌签发（HS256）                                                                                                            |
| `AES_SECRET_KEY`                                                                                                    | MFA TOTP seed 落库加密；经域分离派生后加密 PII（`User.phone` / `User.email` / `FireAlarm.reporter.phone`，见 `src/utils/piiCrypto.js`） |
| `HMAC_SECRET`                                                                                                       | 审计链 `hmac` 签名 + 通用 HMACSigner                                                                                                    |
| `LOGIN_ECDH_PRIVATE_KEY`                                                                                            | 登录口令信封加密（见 ADR-001）                                                                                                          |
| `MONGODB_URI`、`MONGO_ROOT_PASSWORD`、`ADMIN_INITIAL_PASSWORD`、`DOCS_PASSWORD`、`LOG_SHIPPING_TOKEN`、`SENTRY_DSN` | 基础设施与集成                                                                                                                          |

**2. 文件注入（`*_FILE`）**：`hydrateSecretsFromFiles()`（`src/config/secrets.js`）读取 `<NAME>_FILE` 指向的文件，去尾换行后回填 `process.env[NAME]`，适配 Docker secrets。`NAME` 与 `NAME_FILE` 同时存在且不一致时告警并以文件为准；读取失败直接抛错，不静默跳过。

**3. 静态加密算法**：

- **MFA seed**：`src/utils/encryption.js` 用 AES‑256‑GCM 加密（唯一消费者 `utils/mfaSecret.js`），密文格式 `gcm:<ivHex>:<authTagHex>:<base64>`，落库带 `enc:v1:` 前缀。遗留 CBC 解密默认关闭，须显式 `ALLOW_LEGACY_CBC_DECRYPT=true` 才启用（防填充预言机）。
- **业务 PII**：`src/utils/piiCrypto.js` 由同一把 `AES_SECRET_KEY` 经 HKDF 式域分离派生独立子密钥，覆盖 `User.phone`、`User.email`、`FireAlarm.reporter.phone`（realName 因需要子串检索保持明文，取舍见该文件头注释）。密文带 `enc.v1.` / `enc.v2.` 版本前缀；v2 以 `pii:v2:<subjectId>:<field>` 作为 GCM 的 AAD 做行绑定，防止把一行密文搬到另一行解出他人 PII。等值/子串检索走独立 HMAC 检索键，不使用确定性加密。

**4. 启动期强校验**：`src/config/validate.js` 在生产环境强制拦截弱密钥（黑名单 + 长度 <32）、`MONGODB_URI` 含 localhost、缺 `CORS_ORIGIN`、非法 `TRUST_PROXY_HOPS`，失败 `process.exit(1)`。

**5. 轮换脚本**：

- `npm run rotate:mfa-secret`：轮换 `AES_SECRET_KEY` 时，用旧钥解密 → 新钥重加密 `users.mfaSecret`，逐条回读校验。**不经此脚本直接换钥，会导致已加密的 MFA secret 无法解密、TOTP 校验静默失败。**
- `npm run rotate:audit-hmac`：轮换 `HMAC_SECRET` 后对存量审计记录重签（见 ADR-002）。
- `scripts/migrate-pii-encryption.js --rotate`：AES 轮换时同步重加密 PII 列（含 v1→v2 升级）。**只跑 `rotate:mfa-secret` 会漏掉 phone/email，换钥后这些列将无法解密**；完整顺序与旧钥处置见 `deployment/secret-rotation.md` 的 AES 与 PII 小节。

## 理由

- **文件注入**让密钥不落 `.env` 明文、不进镜像层，符合容器化部署的 secrets 最佳实践。
- **启动即校验**把「弱密钥上线」从运行期风险前移到部署期硬失败，避免静默降级。
- **加密格式带版本前缀**（`enc:v1:`）为未来换算法/再轮换留出迁移空间。

## 备选方案

- **仅 `.env` 明文**：最简单，但密钥入仓/入镜像风险高，已被文件注入取代。
- **外部 KMS（云厂商托管）**：安全性更高，但引入外部依赖与成本，当前单机/私有化部署场景收益不足，列为规模化后评估项。

## 当前状态（2026-10-20）

- **`.env` 不入库**：`.env` 已在 `.gitignore` 中且从未进入版本历史；生产默认把密钥放在 `secrets/` 并以 `*_FILE` 注入（`generate-secrets.js` 生成、`FILE_BACKED_SECRETS` + `hydrateSecretsFromFiles()` 读取）。建仓初期提出的 R-1「轮换并迁出 `.env`」对版本库已闭合；**若手工保留过含真实密钥的历史 `.env` 副本或备份，仍应视为已泄露并按 `deployment/secret-rotation.md` 轮换**。
- **AES 的消费者不止 MFA**：截至 2026-10-16，PII 写入侧已切到 v2（AAD 行绑定），存量 v1 行由 `scripts/migrate-pii-encryption.js` 升级（v1 读兼容仍在，`ALLOW_PII_V1_DECRYPT` 尚未落地）。轮换 AES 时必须同时迁移 `mfaSecret` 与 PII 列：用新钥作为 `AES_SECRET_KEY`、旧钥作为 `PII_ROTATION_OLD_AES_KEY` 跑 `migrate-pii-encryption.js --rotate`，完成后**必须 unset 旧钥变量**（`immutableConfigGuard` 会在生产报警）。完整命令见 `deployment/secret-rotation.md` 的 AES 轮换第 2b 步。
- **决策本体未变**：文件注入 + 启动期强校验 + 算法版本前缀仍是现行策略；本文后续「后果与局限」保留建仓时的原始判断，括号内为现状修订。
