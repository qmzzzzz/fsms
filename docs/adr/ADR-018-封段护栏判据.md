# ADR-018 封段护栏：四条判据与"缺省不等于最重"

- 状态：已接受
- 日期：2026-11-01
- 相关：ADR-011（注释治理）、`src/services/ipPoolBan.js`、`src/services/ipPoolLiveTraffic.js`、
  `src/controllers/forensicController.js`、`src/routes/securityRoutes.js`

## 背景

取证溯源页可以"一键封段"：把某个 /24 整个拉黑。对消防系统来说，这条能力的
代价不对称——**封错一次，整栋楼的报警可能再也报不上来**，且不可逆。第 18 轮
审计因此在 `ipPoolBan` 上加/确认了四道判据。本 ADR 记录它们**为什么是这样**，
源码里只留结论（ADR-011：权衡进 ADR，源码留判据）。

## 决定

### ① 并集判据，而不是单条判据

单条 `/1` 不是全网段，但"已封 `0.0.0.0/1`，再封 `128.0.0.0/1`"的并集等价于 `/0`：
全 IPv4 拒服，管理员把自己锁在门外。只判单条 `/0` 会漏掉这种**分片绕过**。
判据因此是"与现有黑名单求并集后是否铺满任一地址族"，且**不接受只铺满一半**。
名单快照（10s TTL）与运行期匹配同一口径，避免"判的时候没满、用的时候满了"。

被拒原因：`union_covers_family`。

### ② 业务活跃度护栏（本系统特有）

通用安全产品没有这一条。封段会切断该网段**全部**业务流量，所以只要最近还有人
在这段里正常用系统，就不许封。这条判据一旦失效且静默，等于护栏不存在——第 18
轮实测过它的失效形态（见下"踩过的坑"）。

被拒原因：`live_traffic_inside`。查不到（数据库故障）时**保守返回"有活动"**：
宁可挡下一次封禁，也不让一个可能封错的段放行。

### ③ 打字确认的门槛与它的两侧

`HIGH_IMPACT_HOSTS = 256`。聚类产出的段永远是 `/24` 或 `/64`，而 `/24` 的主机数
正好 256 ⇒ **UI 能封的每一个段都需要打字确认**。这不是过度设计：能封的段本来就
只有这一种规模。

关键是**两侧都必须实现**。后端加了门槛、前端不发 `typedConfirm`，结果是每次封段
都在第二步 400，功能 100% 不可用；前端加了输入框、后端不校验，门槛等于装饰。
因此：

- 后端：`requestBan` 回票时带 `needTypedConfirm`（由后端算，前端不自己算——
  两边各算一次就是两份事实，一旦漂移，界面会以为不用确认而服务端一律拒）；
- 前端：看到 `needTypedConfirm` 就停在"请逐字输入网段"这一步，**必须是真的两次交互**：
  首次点击只拿票并露出输入框，用户敲完再点第二次才落库。

被拒原因：`typed_confirmation_required`。

### ④ "缺省不等于最重"

`durationMs = 0` 在 `IPBlacklist.blockIP` 里表示 `expiresAt = null`，即**永久**。
控制器若把"未填 / 非法 / 0"一律折成 0，前端选"永久"和"忘了选"落库结果相同，
`DEFAULT_BAN_MS` 永远轮不到生效——**漏填即最重**，方向反了。

因此把 0 显式解释为永久**只在调用方明确要求时**成立：由 `applyBan` 的 `permanent`
开关表达（`durationMs === 0 && durationHours !== undefined`），缺省走 24 小时。

## 踩过的坑（都被实测钉住，不是推测）

- **活跃度护栏的 IPv4 正则恒不命中**：把 CIDR 网络号当字面前缀，`/24` 拼出
  `/^10\.9\.8\.0\./`，要求地址以 `10.9.8.0.` 开头——任何真实主机都匹配不上，
  护栏恒返回 `{live:false}` 且静默。修法是"按位截断后的前若干段"作前缀。
  IPv6 分支本来就是对的，**只有 IPv4 坏**，这类"半边对半边错"最容易漏。
- **落库判据用错字段**：`blockIP` 的契约是**返回落库文档**，不是 `{banned:true}`。
  早先按 `r.banned` 判生效 ⇒ `bannedCount` 恒 0、审计恒 `success:false`，
  而条目其实已经落库：界面报"一条都没封住"，库里却封了。
- **护栏只加在一侧**：四道判据只在 `/api/security/forensic/pool-ban/*` 生效，同权限
  （`security:config`）的 `POST /api/security/ip-list` 一条都不查——能从那边把操作者
  自己的网段加黑，且省略时长即永久。**同一个权限位上的两个入口必须共享同一套判据**。

## 后果

- 拒绝原因是枚举值，**单一事实来源是 `src/constants/banRefusalReason.js`**（此前有六份
  副本：产出字面量、OpenAPI、注册表注释、本 ADR、前端 `BAN_REFUSAL_KEYS`、前端用例；
  实测差集已经出现——文档少列 3 个，其中 `typed_confirmation_required` 是唯一"再点一次
  就能自救"的原因，按文档实现分支的第三方会精确漏掉它）。前端 i18n 必须逐个有文案，
  漏了界面就把英文枚举暴露给运维；三向对账（产出 / 前端映射 / OpenAPI 产物）由
  `src/tests/ci/banRefusalEnumSingleSource.test.js` 钉住。
- 票据是**一次性**的：**落库成功后**立刻作废（`ipPoolBan.test.js` 的对照用例钉住，防止「不消耗」
  被放宽成可重放）。但**打错字不消耗票**——`applyBan` 在 `pending.delete` 之前判打字确认，
  改对了仍能用同一张票。判据：打错字只是没确认，不是用掉了票；防手滑靠的是「两次交互 + 逐字敲对
  网段」本身，再加一道「重新申请」并不会更安全，只会让人为了省事去复制粘贴网段。
  （2026-11-02 更正：本行此前写作「打错字要重新申请」，与同一提交里的实现、注释和用例三处相反；
  三者一致而本句孤立，故按实况改写。）
- 护栏的回归用例必须**红先绿后**：把 `live_traffic` 的前缀改回网络号整体、
  把 `banned` 判据改回 `r.banned`、把打字确认的两次交互合并成一次，都必须有用例变红。
