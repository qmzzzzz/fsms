# ADR-010：不引入分布式追踪（OpenTelemetry）的适用边界

- **状态**：已接受
- **日期**：2026-10-26
- **来源**：七维审计报告 O-3（`deliverables/audit-2026-10-25/audit-report.md` §8.4）

## 背景

系统当前的请求关联依赖三样东西：

1. `AsyncLocalStorage` 注入的 `requestId`（`src/utils/logger.js:14-26`），业务代码零改动；
2. 认证成功后在同一上下文里补 `userId`；
3. 结构化日志（生产 JSON）+ 统一错误码，错误响应体里回传 `requestId`。

这套机制在**单进程、同步调用链**下足够：一条日志串起来就是一次请求的完整轨迹，
运维拿到用户报的 `requestId` 就能 grep 出全部相关日志。

审计指出的问题是：**没有把"什么条件下这套机制不再够用"写下来**。缺这份边界声明时，
两种错误都会发生——要么在一次小需求里顺手引入 OTel（带来新的采集端、采样策略、
跨服务传播格式、存储与成本），要么在链路已经跨进程之后仍然靠 `requestId` 硬撑，
排障时才发现关联不上。

## 决策

**当前架构下不引入分布式追踪。** 以 `requestId` + 结构化日志为唯一关联机制，
并把"何时必须重新评估"写成可判定的条件，而不是"以后再说"。

## 理由

- **架构形态**：单体 Express 服务 + 单进程调度器，请求处理不跨进程。唯一的跨进程
  通信是 WebSocket 推送（服务端 → 客户端，单向）与可选的 Redis 缓存，
  二者都不构成"一次请求被拆到多个服务"。
- **成本不对称**：引入 tracing 需要 SDK、采样策略、exporter、后端存储（Jaeger/Tempo）、
  以及跨服务传播头的一致性维护。当前没有跨进程链路，这些成本换不来任何新信息。
- **已有信号覆盖了 tracing 的主要用途**：延迟分布有 `http_request_duration_seconds`
  直方图（逐路由），错误率有 `http_requests_total` + `/api/metrics` 快照，
  审计链有独立的哈希校验与 WAL，异常有 Sentry（含 `requestId` 标签）。
  tracing 相对它们的增量价值主要是"跨服务依赖图"，而本系统没有跨服务依赖。

## 必须重新评估的条件（可判定，不靠感觉）

出现以下**任一**条件时，本决策作废，须新开 ADR 取代本文：

| 条件                                                            | 判定方式                                                                          |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 引入任何独立的业务服务（拆分出报表服务、通知服务、审计服务等）  | 仓库出现第二个 `package.json` 的 HTTP/gRPC 服务进程，或部署拓扑出现第二个业务容器 |
| 引入消息队列 / 异步任务消费者（BullMQ、Kafka、RabbitMQ）        | 依赖树出现队列客户端，或 `docker-compose.yml` 增加 broker                         |
| 引入 API 网关 / BFF 且它做请求聚合                              | 网关侧出现"一次外部请求扇出多个内部请求"的编排逻辑                                |
| 排障时出现"同一业务操作的多段日志无法用 `requestId` 关联"的实例 | 事后复盘中记录到具体案例（须点名 requestId 断在哪一跳）                           |

## 备选方案

1. **立即引入 OpenTelemetry（全量）** —— 否决：无跨进程链路，成本换不到信息；
   且会与现有 `requestId` 形成两套关联口径，运维要判断"看哪个"。
2. **只引入 trace context 传播（W3C `traceparent`）不接后端** —— 否决：
   没有消费端时，传播头只是给日志多加一个字段，收益接近零。
3. **保持现状但不写边界** —— 否决：这正是审计指出的问题本身。

## 后果与局限

- **局限一（必须承认）**：`requestId` **不跨进程**。多实例部署下，同一次业务操作若
  被不同实例处理（重试、LB 重放），日志会分属不同 `requestId`，只能靠业务键
  （userId + 时间窗 + action）人工关联。多实例本身已受 ADR-004/ADR-005 约束。
- **局限二**：WebSocket 长连接的推送不产生 `requestId`——它们由服务端事件驱动，
  排障依据是 `ws_connections` / `ws_inbound_throttled_total` 指标 + 带 `socketId` 的日志。
- **局限三**：Sentry 的 performance 采样与本文无关，它是错误监控的附带能力，
  不构成跨服务链路视图。
- **反向代价**：一旦触发上表的任一条件，补 tracing 的窗口会很紧（新服务上线同时要
  考虑可观测性），因此**新增服务时必须先看本表**，而不是等排障出问题。
