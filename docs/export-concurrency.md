# 报表导出并发闸（exportConcurrency）说明

本文件承接 `src/services/exportConcurrency.js` 文件头的论证（注释密度棘轮按文件封顶，论证移此，代码内只留一行指针；行内不变量注释仍在原处）。

## 缺陷

`/api/reports/export` **必须**有并发上限：`writeExportWorkbook` 对每个请求把命中的行全部 `addRow` 进工作表、再整包序列化（同步 CPU）——峰值与「并发人数 × 单次行数」成正比。自研写入器（utils/xlsxWriter）单次常驻远小于 exceljs 的单元格对象模型（实测 5000 行整包 0.17 MB），但判据是那个**乘积**：十几个并发仍能把进程推过容器内存限制，而失败形态是 OOM 杀死整个进程——连不导出的人一起掉线；导出低频、可重试，不该有同等并发权。

## 策略（用户 2026-10-26 拍板：上限 2 + 有界排队）

- 上限：`EXPORT_MAX_CONCURRENCY`，默认 **2**。导出是 CPU/内存重活，2 个并发已能吃满单核的 zip 压缩与行转换，再多只是把内存峰值线性放大。
- 排队：超出上限的请求**不立即失败**，进有界队列等槽位（导出常在页面上点一次就走，直接回 429 的体验是「偶发失败」，而排队 3 秒拿到文件是「慢一点但成功」）。
- 队列上限：`EXPORT_MAX_QUEUE`，默认 **8**。没有队列上限的「有界等待」是自欺——100 个请求同时进来就变成 100 个连接挂着等 30 秒，内存没省、连接还被占满。
- 排队超时：`EXPORT_QUEUE_TIMEOUT_MS`，默认 **30000**。超时回 429 + `Retry-After`，让客户端知道「不是坏了，是忙」。

三个值都读环境变量并在**每次 acquire 时**读取：导出路径不在热循环里，多读三次 `process.env` 的成本可以忽略，换来的是测试不必重置模块、运维改配置后新请求即生效。取值一律**钳制**到安全区间：`EXPORT_MAX_CONCURRENCY=0` 会让所有导出永久 429（比 OOM 更隐蔽的可用性事故），而 `=10000` 等于没设。

## 为什么单独成文件

`reportController` 的行数/复杂度贴着棘轮红线；且这段状态机需要**独立证伪**（槽位转移、超时与释放的先后、幂等释放），塞进控制器只能靠 HTTP 间接测。

## 分池（2026-11-03：三导出端点同闸）

审计 CSV（5 万行上限 + 逐行 SHA-256）与取证 JSON 导出此前**不占槽**——它们恰是每请求最重的两条导出链。扩进同一闸时若三端点共用一个池，一个 5 万行审计 CSV（长 CPU）能把报表导出饿死。所以按端点**分池**：`report-export` / `audit-export` / `forensic-export` 各持独立 active/waiters，互不排队；上限/队列/超时三参数与既有环境变量共用（每池各自独立生效，运维按总量调参即可）。

## 指标

状态变化即推送 `utils/metricsRuntime`（`export_inflight` / `export_queued` / `export_rejected_total{reason}`）。不在这里自己渲染文本：指标口径只有一处，否则 `/metrics` 与 JSON 快照会各说各话（本仓反复踩过的那类「同一条判据的第二处实现」）。分池后 gauge 取**各池之和**（标签面不变，避免 /metrics 消费方破坏性变更）；进程内计数语义不变：多实例部署时全局上限 = 各池上限 × N 实例。
