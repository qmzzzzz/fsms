# 数据分类分级与同意记录

> 对应审计缺口：一-7「数据分类分级 / 同意记录」。
> 单一事实来源是代码而非本文：等级、静态存储形态、个人信息标记与同意范围全部声明在
> `src/constants/dataClassification.js`，由 `src/tests/ci/dataClassificationInventory.test.js` 双向强制。
> 本文回答「怎么用这份台账」以及**同意**这条链路怎么走通、边界在哪。

## 1. 为什么需要一张台账

改动前，仓里对「哪些字段是个人信息」只有零散口径：`piiCrypto` 的加密范围、各模型的
`select:false` 清单、审计脱敏名单。**没有任何一处**能回答「`User.email` 属于第几级、依据是什么、
静态存储是否已加密」。后果是可核对的分类分级不存在：

- 新增字段时没人能判断它该不该加密、该不该进审计脱敏名单、该不该要单独同意；
- 等保 2.0 三级与《个人信息保护法》的测评项「数据分类分级」「个人信息处理告知同意」
  无法出示证据，只能口头说明；
- 三份清单各自演进，任何一个都能在无人察觉时与另外两份漂移。

## 2. 台账的形状

| 声明                    | 含义                                                                             |
| ----------------------- | -------------------------------------------------------------------------------- |
| `CLASSIFICATION_LEVELS` | L1 公开 / L2 内部 / L3 敏感 / L4 关键（等保 2.0 三级口径），每级附判定依据       |
| `AT_REST_FORMS`         | 静态存储形态：`gcm` / `hmac` / `sha256` / `bcrypt` / `plain`                     |
| `MODEL_LEVELS`          | 17+1 个模型的基线等级（逐字段声明未覆盖的路径继承基线）                          |
| `FIELD_LEVELS`          | 逐字段声明：等级 / 静态形态 / 是否个人信息 / 依据 / 归属的同意范围               |
| `CONSENT_SCOPES`        | 同意范围表，每项注明是**向用户告知**（notice）还是**组织法定基础**（legalBasis） |
| `GCM_WITHOUT_GETTER`    | 加密但没有 schema getter 的路径（解密在业务层完成），必须写明理由                |

`classifyField(model, path)` 是唯一查询入口；未登记模型返回 `null` 而不是猜一个默认等级——
"猜"正是这份台账要消灭的东西。

## 3. 门禁强制了什么（不是"登记即完成"）

`dataClassificationInventory.test.js` 用**真实加载的 schema**（`require('../../models')`）对拍：

1. **反空自证**：模型数 ≥ 17、schema 路径 ≥ 300、个人信息命中 ≥ 40、`FIELD_LEVELS` ≥ 50（实况 18 / 58），
   外加一个必然零命中的负向对照——扫描器失效时后面全绿也没有意义。
2. **模型清单双向闭合**：`models/index.js` 的每个模型都分级，分级表里没有僵尸模型。
3. **声明路径真实存在**：每条 `FIELD_LEVELS` 的路径必须在 schema 里找得到（声明不存在的字段 = 假覆盖）。
4. **个人信息正则命中的每个路径都必须声明**，且标为个人信息的必须 ≥ L3 并归属某个同意范围；
   L2 条目**不得**带同意范围（否则界面会为"内部"数据征得同意）。
5. **`select:false` 的每个路径都必须声明**：凭证材料不会因为漏登记而变成未分级。
6. **`atRest='gcm'` 与 schema getter 双向对拍**：声明加密就必须真的解密得出来；有 getter 就必须登记为 gcm；
   例外只能来自 `GCM_WITHOUT_GETTER`，且理由非空、无僵尸条目。

> 这条门禁**不**验证「加密强度是否合适」或「字段是否该被收集」——那是评审判断，不是静态判据。
> 它验证的是**声明与实况一致**，这是所有后续判断的前提。

## 4. 同意记录怎么落地

### 4.1 记录形态

`src/models/ConsentRecord.js`：一条记录 = 某账号对某一版告知的一次同意。

| 字段                              | 作用                                                                |
| --------------------------------- | ------------------------------------------------------------------- |
| `userId` / `username`             | 同意主体；`username` 是快照，账号匿名化后这条证据仍可追溯到当时的人 |
| `policy` / `version`              | 政策标识（固定枚举 `privacy`）与告知版本号                          |
| `scopes`                          | 本次同意覆盖的数据范围（取自 `CONSENT_SCOPES` 的 notice 项）        |
| `acceptedAt` / `ip` / `userAgent` | 作出同意的时间与当时的网络上下文（同意是**行为**，不是状态）        |
| `source`                          | `self-register` / `profile-renew` / `admin-recorded`                |

三条不变式（由 `src/tests/models/ConsentRecord.test.js` 逐条真调验证）：

- **append-only**：`save` 改写与 9 类批量写入口（与 `auditLogHooks` 同宽）全部被拒；
  只有 `NODE_ENV=test` + 显式 `bypassAppendOnly` 可清理测试数据。可改可删的证据不是证据。
- **幂等**：`{userId, policy, version}` 唯一索引；重复提交不产生第二条记录，"同意了几次"仍可判定。
- **改版不继承**：`consentStatus()` 只认**现行版本**；旧版同意不会被当成对新版的同意。

### 4.2 注册链路上的强制点

`POST /api/auth/register` 的 `privacyConsent` 必须是布尔 `true`，三道闸：

1. 路由层 `registerValidation`：`body('privacyConsent').custom((v) => v === true)`，
   缺省、`'true'`、`1`、`{}`、`false` 一律字段级 400（不接受"看起来像同意"）。
2. 服务层 `authService.registerUser` 的 fail-closed 复判（`outcome='CONSENT_REQUIRED'`）：
   绕过路由直接调业务函数的路径同样过不去。
3. **签发任何令牌之前**落库同意记录；落库失败则回滚刚建的账号并整体失败
   （`REGISTER_SERVICE_UNAVAILABLE`）——绝不留下「有账号、无同意证据」的用户。

前端 `RegisterView.vue`：末步渲染勾选框 + 可点开的告知全文（版本号与范围清单来自
`web-admin/src/utils/privacyNotice.js`，与后端逐字对拍）。勾选框用 `validator` 判 `value === true`
而非 `required:true`——`el-checkbox` 的 `false` 会被 `required` 判成"有值"，那样勾选框形同虚设。

### 4.3 刻意划定的边界

- **只覆盖自助注册**。管理员建号属于《个人信息保护法》第十三条的组织法定基础
  （劳动合同/人力资源管理所必需），不以同意为前提，故不写同意记录、界面也不提示。
- **告知正文不写"注册即表示同意"**。这种写法把同意变成默认值，正是本轮要关闭的形态；
  告知必须可读、同意必须由用户显式勾选（弹窗的「我已阅读」按钮只关闭弹窗，**不代勾**）。
- **没有撤回同意的自助入口**。当前只有"联系管理员注销账号"这条路径；
  撤回同意导致账号不可用的语义已在告知正文里写明。自助撤回属未实现项，如实登记在此。

## 5. 残余风险（测评时按此口径答）

| 风险                             | 现状与处置                                                                                                            |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `realName` 明文存储              | 姓名模糊检索依赖它（`utils/queryBudget.js` 对 realName 子串检索计预算），A5 决策记录已申报；见 `docs/threat-model.md` |
| `User.avatar` 为 L2 且无同意范围 | 头像属个人信息，但用户可自行上传/不传；未纳入告知范围，若将来强制采集需升版告知                                       |
| 分类分级只覆盖 schema 字段       | 日志正文、审计 `details` 快照里的自由文本不在台账内；它们按整模型等级继承（AuditLog 为 L3）                           |
| 台账本身需要人维护               | 门禁能抓「声明与 schema 不一致」，抓不到「新字段登记了错误等级」——后者只能靠评审                                      |
| 同意版本升级后存量用户不重新征得 | 本次仅注册路径强制；已有账号在告知改版后不会被要求重新同意（未实现项）                                                |
