# 内部留档引用索引（deliverables/ 引用台账）

> 背景（F-14，2026-10-16 审计）：源码注释、脚本与文档里大量引用 `deliverables/` 下的
> 评估报告、审计台账与实测基线，而该目录**不在 Git 跟踪清单中**（见 `.gitignore`
> 的 `deliverables/` 段与 `CONTRIBUTING.md` §9）。干净 checkout 打不开这些引用，
> 代码审查也无法核对注释里写的"证据"。
>
> 本文件是这些引用的**唯一台账**：新增一处引用就必须在此登记，否则
> `src/tests/docs/deliverablesReferenceIndex.test.js` 会红；反向也一样——
> 台账里登记的文件若源码不再引用，同样会红（防僵尸条目）。

## 一、为什么这个目录不入库

本仓库是**公开仓库**（github.com/qmzzzzz/fsms）。`deliverables/` 里是带 `file:line`
坐标的**可利用漏洞细节**（fail-open 路径、越权臂、审计链抹哈希手法等）与旧测量结果。
入库等于把攻击说明书公开，因此刻意排除。这不是疏漏，是 2026-09-28 的显式决定
（提交 `1f11eaf`「deliverables 移出公开仓库」）。

推论：**长期有效的设计依据必须另存一份到 `docs/`**。ADR（`docs/adr/`）、
威胁模型（`docs/threat-model.md`）、多实例一致性清单、备份加密与轮换手册都已在
`docs/` 与 `deployment/` 里，不依赖本目录。

实测 0 条），克隆后并不存在，其内部「旧报告引用旧台账」属于快照内部的自洽，不承担

被淹没。该豁免由用例 ④ 反向钉住：这三个前缀必须仍在 `.gitignore` 里，否则用例转红。

## 三、已断链的四条（待处置）

`安全缺口核查-2026-09-30.md`、`待优化项总清单-2026-08-29.md`、
`审计与迭代汇总-2026-09-28.md`、`审计复核第3轮…-2026-10-01.md` 这四份
**从未进入 Git 历史、当前磁盘上也不存在**，引用它们的地方（合计约 19 处）
无法被任何人复核。

处置口径（逐条二选一，不得悬空）：

1. 结论仍然有效的 ⇒ 把结论本身搬进 `docs/`（ADR 或 `docs/` 下的说明），注释改为引用新位置；
2. 结论已过时的 ⇒ 把引用改成"历史背景"表述并注明"原始记录未入库"，不再当作可核对证据。

> 第 4 条还有个附带问题：引用里的文件名带省略号（`…`），说明当时是手写截断的。
> 引用路径必须是**可直接打开**的完整文件名，否则连"文件是否存在"都无法机器判定。

## 四、纪律

- 新增 `deliverables/` 引用 ⇒ 必须在本表登记（否则 `deliverablesReferenceIndex` 用例红）。
- 结论要长期有效 ⇒ 写进 `docs/`，不要只写在 `deliverables/` 里。
- 注释里引用**行号**（`xxx.md:123`）只对入库文件有意义；对未入库文件请引用**章节名**。
