# 边缘防护与取证：分工、降级与速查

> 适用：生产边缘（nginx）与应用层（Node）之间的**安全职责划分**、DDoS 期间的**日志降级**判断，
> 以及按 IP 的**日志速查**。配套配置见 `deployment/nginx.conf.example`（边缘限速三档、
> TLS 取证两条头、取证日志格式 `fsms_forensic`）。
> 本文只描述"怎么判断、怎么查、边界在哪"；具体阈值与落点是配置事实，以配置文件为准。

## 1. 分工：应用层是主闸，边缘是快通道

| 能力     | 应用层（主闸）                                                                                                  | 边缘 nginx（辅）                                                                                                                                                                                                 |
| -------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| IP 封禁  | `src/middleware/security/ipBlacklist.js` 的 `checkIPBlacklist`：库持久化、TTL、分级升级、审计留痕、降级分支可见 | 可选 `deny` 快通道：省一次到 app 的连接与 JSON 解析                                                                                                                                                              |
| 限速     | `src/middleware/rateLimit.js` 三档（general/strict/login），带白名单与探针豁免、JSON 429 语义、审计             | `limit_req` 三档保守值，只截扫描器/爆破量级洪峰                                                                                                                                                                  |
| 身份判定 | `src/utils/ipUtils.js` 的 `clientIpForSecurityDecision`：可信边界内取 `req.ip`，边界外退回 socket 对端          | 提供 `X-Forwarded-For`（追加式）与 `X-Real-IP`，**不参与判定**。LB 直连 app 且 `PROXY_PROTOCOL=on` 时（ADR-021），LB 以 PROXY v1/v2 头声明真实客户端，由应用连接层还原进 socket 对端——nginx 不在场，XFF 语义不变 |
| 审计     | 全量写审计链（append-only + 哈希链）                                                                            | 无                                                                                                                                                                                                               |

**为什么边缘 `deny` 只能当快通道**（三条硬理由，不是偏好）：

1. **名单在库里**：封禁状态由应用写入 MongoDB，nginx 无法实时读；同步到 nginx 需要生成 include
   并 reload，天然有延迟。延迟窗口内攻击者仍能打通。
2. **边缘封禁没有留痕**：`deny` 只回一个状态码，没有审计事件、没有升级计数、没有"谁在什么时候
   因为什么被封"。取证与复核都要回到应用侧。
3. **口径会分叉**：应用侧的封禁判据带白名单、探针豁免与可信边界（见第 1 节第 3 行）。
   在 nginx 再写一份，等于制造第二份真源——两处不一致时，值班人员无法判断哪一份是对的。

因此：**判定与留痕在应用层；边缘只做"丢洪峰"和"可选快封"**。边缘封禁的启用属于部署决策，
启用后必须同时确认应用侧仍会独立记录（不能因为 nginx 拦掉了就把应用侧的观测关掉）。

## 2. DDoS 期间应用日志为什么会先降级

这是**设计上的顺序**，不是故障：应用日志的写入依赖事件循环、审计 IO 与日志出站链路，
这三样都是稀缺资源，压力上来时它们最先让位。链路逐段看：

1. **连接层打满**：连接数或带宽被占满时，请求在 nginx 侧排队、超时或直接拒绝。
   应用**根本没看到**这些请求——应用日志里自然没有它们。
2. **事件循环排队**：已接受的请求仍要 JSON 解析、限流计数、审计写入。单线程排队时
   请求处理变慢，日志时间戳与真实发生时间拉开。
3. **审计 IO 抖动**：审计是 append-only 写库 + WAL 兜底。上游 IO 抖动时审计写入失败会
   计数可见（`auditWriteFailure`）并降频记日志——应用日志本身开始被"限频"。
4. **日志出站受阻**：转发链路（`src/utils/logShipper.js`）出站失败时本地缓冲增长，
   轮转/丢弃策略介入。
5. **进程内降级**：采集与落盘被限流后，**记下来的条目变少，但攻击并没有变少**。

**最危险的误判**是把"应用日志条目变少"读成"攻击停了"而撤掉防护。判断方法见下节。

### 2.1 观察方法：区分"攻击停了"与"应用侧记不下了"

同一时间窗内**同时看两层计数**，差距本身就是信号：

| 观察点                    | 正常                            | 应用侧在降级           |
| ------------------------- | ------------------------------- | ---------------------- |
| 边缘请求数 vs 应用收到数  | 接近（差值 = 静态资源与拒绝量） | 差值显著拉大           |
| 边缘 502/504/499 比例     | 接近 0                          | 上升（上游排队或断开） |
| 边缘 `limit_req` 429 比例 | 低                              | 上升（边缘闸在丢洪峰） |
| 应用审计写入失败计数      | 0 或偶发                        | 持续非 0               |
| 日志出站失败 / 缓冲长度   | 0                               | 持续非 0 或单调增长    |
| 应用进程事件循环延迟      | 平稳                            | 抬升                   |

判读规则：**边缘计数上升 + 应用计数下降 = 攻击仍在，应用侧已经看不到**。
此时先保观测（提高日志级别与落盘优先级、临时开启取证日志），再谈处置。

## 3. 按 IP 统计日志速查

两种格式的字段位置不同，**先看一行再套命令**（`head -1` 打印一条即可对齐列号）。

### 3.1 默认访问日志（`fsms_no_query`，不含查询串）

字段：`1=$remote_addr`、`4=[本地日期`、`5=时间+时区]`、`6="方法`、`7=路径`、`8=协议"`、`9=$status`。

```bash
# Top 20 来源 IP
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -20

# Top 20 被边缘限速拒绝的 IP（状态 429）
awk '$9 == 429 {print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -20

# 某个 IP 的请求路径分布（把占位符换成真实地址）
awk '$1 == "203.0.113.77" {print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -20

# 按分钟观察某个 IP 的速率变化
awk '$1 == "203.0.113.77" {split($4, d, "["); print d[2], $5}' /var/log/nginx/access.log | sort | uniq -c
```

### 3.2 取证日志（`fsms_forensic`，攻击窗口按需启用）

字段顺序与配置里的 `log_format` 一致：
`1=$remote_addr`、`2=$http_x_forwarded_for`、`3=[本地日期`、`4=时间+时区]`、
`5="方法`、`6=$request_uri`、`7=协议"`、`8=$status`、`9=tls=协议/套件`、
`10=ua="UA"`、`11=ch="sec-ch-ua"`、`12=rt=耗时`、`13=urt=上游耗时`。

```bash
# Top 20 来源 IP（含被拒绝的请求）
awk '{print $1}' /var/log/nginx/forensic.log | sort | uniq -c | sort -rn | head -20

# Top 20 的 XFF 原链（长度异常 = 有人在伪造链路）
awk '{print length($2), $2}' /var/log/nginx/forensic.log | sort -rn | head -20

# 某个 IP 的 TLS 参数分布（UA 与 TLS 指纹不一致时往往是脚本/自动化）
awk '$1 == "203.0.113.77" {print $9}' /var/log/nginx/forensic.log | sort | uniq -c | sort -rn

# 慢请求（rt 字段大于阈值的行）
awk -F'rt=' '{split($2, a, " "); if (a[1] + 0 > 5) print}' /var/log/nginx/forensic.log | head -20
```

**口径提醒**：`$http_x_forwarded_for` 是**原链文本**（本层追加、不解析）。用它做取证时，
可信来源是**应用侧**判定的地址（`clientIpForSecurityDecision`），不是日志里的左段——
左段由请求方自带，可任意伪造。日志的价值在于"留了原文可复核"，不在于"直接当结论"。

## 4. 取证窗口：启用与关闭

取证日志含完整 `$request_uri`（带查询串，可能含一次性凭据），因此**默认不挂线**，
只在攻击窗口按需开启：

1. **开启前**：确认磁盘余量足够覆盖预计窗口（按当前 QPS × 窗口时长估算），并记下开启时间。
2. **开启**：按 `deployment/nginx.conf.example` 中 `access_log` 那一行的说明取消注释，
   `nginx -t` 通过后 reload（reload 只影响新连接）。
3. **窗口内**：不要临时改动格式；格式一变，前后的字段位置不可比，速查命令会错位。
4. **关闭**：窗口结束**立即**改回注释并 reload，然后对 `forensic.log` 做一次归档或删除，
   不要长期留在磁盘上。
5. **交付**：归档文件与本文第 3.2 节的统计结果一起交付；报告里写明窗口起止时间与格式版本。

## 5. 如实边界（测评/复盘时按此口径答，不要拔高）

- **L3/L4 打满时，应用日志会先降级**：带宽或连接数被打满时，请求进不到应用，应用侧
  既看不到也记不下。此时**边缘日志是唯一可靠的证据源**，这正是在边缘保留取证格式的原因。
  但边缘日志同样会丢——队列打满时 nginx 自己也会丢弃或写不进磁盘。
- **"有日志"不等于"日志完整"**：本文第 2 节列出的每一段链路都可能静默丢条目。
  把日志条数当作"攻击规模"来汇报是错的，它只是"被记录下来的规模"的下界。
- **边缘 `deny` 不是审计手段**：它不产生审计事件，不能作为"已处置"的证据。
- **XFF 左段不可信**：只有应用侧按可信边界判定出的地址才可用于封禁决策。
- **本文不含流量清洗/带宽扩容方案**：边缘防护能挡住的是**应用层洪峰**，
  真正的带宽型攻击需要在网络层/运营商侧处理，超出本仓交付范围。
