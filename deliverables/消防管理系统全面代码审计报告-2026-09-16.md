## 3. 主审计员独立复现的 8 项实证

> 以下全部由主审计员在本次审计中独立编写探针、真实运行得出，**可重跑**。探针脚本见附录 A。

### 3.1 【越权链】跨部门数据越权（P0-1）

**完整攻击链复现**：

```
① 以 dept=东区 的部门管理员身份登录
② PUT /api/users/<自己>  { department: '总部' }        → HTTP 200 成功
③ GET /api/devices                                     → 返回「总部机密设备」
   （攻击前同一请求只返回「东区设备」）
④ GET /api/devices/<总部设备id>                        → HTTP 200 越权读取成功
```

**根因**：`src/controllers/userController.js:209-318` 的 `updateUser` 是 **396 行文件中仅 2 处引用 `dataScope` 之外**的写入口；`:290` 的 `if (department !== undefined) user.department = department` **无任何范围校验**。

**可达性**：前端 `web-admin/src/views/UserView.vue:655-697` 的 `submitForm` 会提交 `department` 与 `allowedIPs` 字段——即该越权**无需构造原始请求**，UI 上就能点出来。

**横向对比**：同文件 `:44` 与 `:623` 两处正确使用了 `dataScope`，说明作者知道该机制存在，只是这一路径漏了。

### 3.2 【WebSocket 双绕过】（P0-2）

```
同一 JWT：
  HTTP  GET /api/devices                → 403 AUTH_IP_RANGE_DENIED
  WS    CONNECT (auth.token = 同一 JWT) → 认证通过；socket.userId 已绑定；userConnections 已登记
```

**两条独立的失效信号在 WS 侧均零校验**：

1. `allowedIPs = 10.0.0.0/8`，而来源 IP 为 `127.0.0.1`（不匹配）
2. 该会话 `status = revoked`（已吊销）

**根因**：`src/services/websocketService.js:293-382` 的 `authenticateSocket` 校验了 JWT 签名 / 黑名单 / 用户 status / tokenVersion / passwordChangedAt，但**全文 0 处**引用 `sid` / `allowedIPs` / `sessionService`（已 grep 确认）。

**放大面**：`websocketService.js:139-150` 的连接数配额可被**未认证连接**占满（DoS），`:288-293` 的 `dispose` 缺少 `await io.close()`。

### 3.3 【审计双写】`res.locals.skipGlobalAudit` 全局失效

```
POST /api/security/report  → HTTP 200
控制器手写 1 条 suspicious_report
auditBuffer 仍收到 1 条 security_report（全局中间件派生）
⇒ 双写确认
```

**根因**：`src/middleware/security.js:540-542` 在请求**入口**只检查一次该标志；而 12 个控制器赋值点（`securityController.js:127,240,332,432,526,766,822,878`、`ipListController.js:225,320`、`auditController.js:107`）都在**之后**执行。

**注释失实**：`security.js:496-497` 声称该机制"避免同一操作产生两条重复记录"——与实际相反。

**次生影响**：`securityController.js:237` 的注释写"该处已设 skipGlobalAudit，故这是该操作的唯一留痕"——该前提**不成立**，实际是双写且两条记录的 `action` / `category` 都不同（如 `password_changed` vs `security_change-password`）。

### 3.4 【零审计】导出接口与 25 条 GET 路由

GET /api/reports/export                  → 6,747 字节 xlsx 实际下载，auditBuffer 计数 0

**更广的盲区**：`auditGetPaths` 只覆盖 6 个前缀，25 条派生 action 虽在白名单却永不产生，实测未审计：

即**「看了哪台设备」「看了哪个报警」这类敏感读取完全无留痕**。

### 3.6 【append-only 正反两面】

### 3.8 【Express 5 迁移残留】query 侧防护失效（本轮新发现）

```
GET  ?status=a&status=b   → {"status":["a","b"]}   ← hpp 未收敛（预期应保留单个）
GET  ?search[$regex]=^a   → {"search":{"$regex":"^a"}}  ← sanitizeMongo 未清洗
POST body {u:{$ne:null}}  → {"u":{}}               ← body 侧正常清洗
```

**根因**：Express 5 的 `req.query` 是 **getter**（`node_modules/express/lib/request.js:217`），每次访问重新 `queryparse(parse(this).query)`。`sanitizeMongo`/`hpp` 的原地赋值的对象**在下次访问时被丢弃**。

**纵深仍成立**：`queryScalarGuard`（`app.js:237`）把两种形态都拦成 400 `QUERY_PARAM_MUST_BE_SCALAR`——**这是唯一真正生效的防线**。

**风险**：`security.js:163` 注释"原地修改，兼容 Express 4.x getter-only req.query"与 `queryLimit.js:79-80` 注释"看到的是清洗后的最终形态"**都是错误前提**。若未来有人删掉 `queryScalarGuard`（认为 `sanitizeMongo` 已覆盖），query 注入防线**归零**。

## 16. 审计结论

### 16.1 一句话总结

**FSMS 是一个工程规范度显著高于同类项目平均水准、但安全边界尚未闭环的系统。** 其文档密度、常量单源治理、审计链设计、权限矩阵完整性、运维演练完备度均属优等；但**"声称已修复"与"实际已修复"之间的系统性偏差**，导致多个高危缺陷在"已补齐审计盲区""避免重复记录"这类注释的掩护下长期存活。

### 16.2 三个最需要制度性解决的元问题

1. **注释与实现脱节**（12 处确认）。本项目注释信息量是最大优势，但也是最大风险源。建议：**任何"已修复/已覆盖/已避免"类的声明性注释，必须附带一个能失败的测试**。没有测试的声明不允许写入注释。

2. **有机制但不强制**。`dataScope` 中间件存在但挂载数 0；`destructiveGuard` 存在但 2 个高危脚本未接；`sanitizeAuditBody` 存在但只有 1 个调用点；`isCanceledError` 存在但 13 视图仅 1 个用；`errorReporter` 能力完善但 4 个关键降级点没接。**机制的正确性没有问题，问题是"用不用"取决于开发者记忆。**

3. **门禁阈值贴实测值**。后端 8 个棘轮余量 >10pt（可删大量测试而 CI 仍绿）；前端 fn 阈值 5% vs 实测 6.96%（删一个测试就红）。门禁既拦不住退化，也不激励补测。**建议改为"新增代码覆盖率"口径，而非总量口径。**

### 16.3 值得肯定的地方（同等重要）

- **审计链完整性设计**：哈希链 + append-only 护栏 + 链尾重同步 + WAL 兜底 + 启动期一致性断言，**架构完整**
- **加密与密钥治理**：ECDH 信封 + HKDF + AES-GCM + 跨平台权限收紧（含本机实测教训记录）
- **Redis 原子性**：用 Lua `EVAL` 而非"读-改-写"——**这是很多项目做不到的**
- **优雅关闭**：10 步顺序经核对完全正确，且有失败隔离（`runStep`）
- **运维文档**：8KB 的回滚演练记录，同类项目中罕见
- **生产代码卫生**：0 TODO / 0 `v-html` / 0 `innerHTML` / 0 硬编码密钥 / 0 后端 `eval`
- **无过度设计**：没有 IoC 容器、没有复杂继承树、没有为抽象的抽象
