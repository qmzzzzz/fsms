# 迭代报告：审计链「整窗无哈希」可拿到完整性背书

- **日期**：2026-09-26
- **范围**：`src/services/auditChainVerify.js` 的完整性判据 `computeChainVerdict`
- **性质**：新增否决位（fail-closed 收紧），非重构
- **状态**：已落地并验证

---

## 1. 缺陷（已实测复现）

### 1.1 机制

`computeChainVerdict` 的入参里**没有 `legacy`**（无 hash 的记录数）。`verifyAuditChain`
逐条扫描时，无 hash 的记录走 `legacy += 1` 分支（`auditChainVerify.js:159-180`），
而判据侧只消费 `breaks`，于是：

- 攻击者把审计集合**整表** `$unset:{hash:1,prevHash:1,hmac:1}`（直连驱动 / `mongosh`
  可绕过 mongoose 中间件，**这正是该服务文件头声明的威胁模型**）；
- 整窗记录全部落 `legacy` 分支 ⇒ `seenHashed` 恒 false ⇒ `breaks = 0`；
- 五条既有否决（`truncated` / `hmacSkipped` / `emptyWaived` / `nothingVerified` / `scoped`）
  **全部为 false** ⇒ `code = 0`、`canAttestIntact = true`。

### 1.2 后果

- 在线接口 `GET /api/security/audit-logs/verify` 回答「审计链完整」；
- 核验审计记录被写成 `riskLevel: 'low'`（`auditController.js:169`）——
  即**用一条"核验通过"的绿记录为一次彻底灭迹背书**。

### 1.3 反向激励（本次实证）

复现脚本（只读、不连库、用假模型喂数据）对照：

| 场景                 | `breaks` | `legacy` | `code` | `canAttestIntact` | `riskLevel` |
| -------------------- | -------- | -------- | ------ | ----------------- | ----------- |
| 对照 A：只抹**链尾** | 1        | 0        | 1      | false             | high        |
| 实验 B：**整表全抹** | **0**    | 3        | **0**  | **true**          | **low**     |

⇒ **攻击越彻底、结论越好**。既有测试只覆盖了「抹链尾」（`auditChainVerify.test.js:74`）
与「抹中间」（`:94`），**未覆盖「整表全抹」**。

## 2. 修法

### 2.1 判据

`src/services/auditChainVerify.js`

- `computeChainVerdict` 新增入参 `legacy`，新增独立豁免 `allowAllLegacy = false`；
- 新增否决位：

  ```
  nothingHashed = total > 0 && legacyCount >= total && !allowAllLegacy
  legacyCount   = Number.isFinite(legacy) ? legacy : total   // 缺省=未知 ⇒ 视同整窗无哈希
  ```

- 计入 `vetoes` 数组与返回值，并在 `chainVetoReasons` 中给出可读理由。

**为什么缺省按"未知 ⇒ 视同整窗无哈希"**：与 `isPartialScan` 对缺 `scanned` 的处理同向
（该函数注释：_"调用方漏传只会得到偏保守的 INCOMPLETE（响亮），不会得到一个假的 PASS（静默）"_）。
漏传参数只损失"不该否决"的那一格，不产生假背书。

### 2.2 调用点（三处，全部补传 `legacy`）

| 文件                                 | 行   | 改动                                                            |
| ------------------------------------ | ---- | --------------------------------------------------------------- |
| `src/controllers/auditController.js` | 138  | `legacy: report.legacy`                                         |
| `scripts/verify-audit-chain.js`      | 132+ | `legacy: result.legacy` + `allowAllLegacy: args.allowAllLegacy` |
| `scripts/resign-audit-chain-v3.js`   | 158  | `legacy: verify.legacy`                                         |

### 2.3 豁免口（与既有范式同构）

`scripts/verify-audit-chain.js` 新增 `--allow-all-legacy`，与 `--allow-no-hmac`、
`--allow-empty` **彼此独立**（任一未豁免的不完整理由都把退出码钉在 2）。
脚本头注释的"三个豁免"同步更新为"四个豁免"。

```

  report: total=3 legacy=3 breaks=0 intact=true
  verdict: code=2 canAttestIntact=false
  reasons: ["本次扫到 3 条，但全部无哈希（legacy=3）：一条都没有经过哈希校验，不得宣称链完整
             ——"链启用前的存量集合"与"整表 $unset 掉 hash/prevHash/hmac"在数据上不可区分"]
```

套件，失败数从 14 收敛到 7 且**剩余 7 个全是 CLI 型**，证明与环境相关而非本次改动引入。

## 4. 附带发现（环境，非代码缺陷）

对本机审计库跑一次真实核验：

```
total=6939  legacy=768  breaks=5944
byType: hash_mismatch=19  hmac_missing=0  hmac_mismatch=5925  chain_break=0  hash_stripped=0
```

内容哈希与链接均正常，**只有 HMAC 验不过** ⇒ 签名密钥与当前 `.env` 不一致
（测试经 `tests/setup.js` 注入的密钥写入了同一个库）。**不是篡改**；
CLI 判 FAIL / exit 1 属正确行为。

另：真实数据 `legacy(768) < total(6939)` ⇒ 新判据在现有数据上**不会误伤**。
