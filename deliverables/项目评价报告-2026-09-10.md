## 一、TL;DR

**这是一个工程成熟度显著高于同体量平均水平的项目。** 安全能力不是"堆依赖"——AES-256-GCM 认证加密、审计哈希链 v1/v2/v3、ECDH 登录信封、条件原子更新的报警状态机、fail-closed 的令牌黑名单，都是逐行验证过的真实实现。更难能可贵的是代码里留了大量**诚实的自曝缺陷注释**（v2 链盲区、Redis 回退语义、单进程锁假设），说明作者真的做过威胁建模。

**但它有一个贯穿始终的病灶：文档承诺 > 实现与 CI 强制。** 本次审查在文档层发现 6 处与实现直接矛盾的地方，其中 3 处会让读者对项目状态做出完全错误的判断（详见第六节）。

**本次新发现的最实质问题不在"代码写得差"，而在"架构约束未闭环"：**

1. 审计日志 / 用户 / 角色 / 权限接口**未接数据范围过滤** —— 持有 `security:audit` 的部门级管理员可读取并导出**全组织**审计日志，直接违背 RBAC"level 决定数据范围"的核心承诺；
2. 数据范围过滤字段**缺索引**，生产环境按属主查询将全表扫描；
3. 跨集合写**几乎无事务**（全仓仅 1 处使用），且单机部署下 `withTransaction` 降级为无回滚的顺序写。

**综合评分：8.0 / 10** — 设计与实现 8.5，架构约束闭环 6.5，文档一致性 7.5。

## 三、真正做得好的地方（值得保留的设计）

### 1. 报警状态机的并发安全设计 ⭐

`AlarmService` 用 `findOneAndUpdate({_id, status: <前态>})` 做**条件原子更新**（乐观锁），controller 对返回 `null` 统一响应 `409`。`arriveAtScene` 用 `arrivedAt: null & handler: operatorId` 双重条件防冒用与重复登记。

> 这不是"写完能跑"，是真正推演过并发场景的状态机。
> `src/services/AlarmService.js:168-184`、`src/controllers/alarmController.js:21/43/72`

### 2. 审计哈希链 + 诚实的盲区标注 ⭐⭐

`prevHash → hash` 链式 HMAC-SHA256，Redis `chain-tail` 分布式锁 + 链尾指针防分叉，版本化到 v3，配 `auditBuffer` 异步落库与 `flushAndStop` 关闭保护。

最加分的是 `src/utils/auditChain.js:174-182` 自己承认：约 4182 条 v2 存量记录的 `riskLevel`/`riskFactors` 在算 hash 时未纳入（落库后才被 Mongoose 补默认值），篡改这两个字段链校验发现不了。**有这种注释的项目，说明作者真的在做威胁建模。**

### 3. 覆盖率棘轮机制的自我修正 ⭐⭐

`jest.config.js:40-51` 的注释记录了完整心路：发现"基线与实测拉开 10~46 个百分点后门槛形同虚设（可删掉三分之二测试 CI 依然全绿）"，于 2026-08-27 按全量实测重设，并确立"贴实测下方一档、只升不降"。

当前 global 阈值 **branches 79 / functions 87 / lines 91 / statements 91**，另有 **35 个安全关键模块**单设独立阈值（`jest.config.js:66-116`）。

### 4. 密码学实现优于其文档声称 ⭐

- AES-256-GCM 配 `randomBytes(12)` 随机 IV，CBC 模式默认关闭，HMAC 用 `timingSafeEqual` 恒定时间比较（`src/utils/encryption.js:17,40,184`）
- MFA TOTP seed 以 `enc:v1:` 前缀 AES-GCM 加密落库，**明文 fail-closed 拒绝落库**（`src/utils/mfaSecret.js:56-86`）
- JWT 固定 `algorithms:['HS256']` 防 alg 混淆；令牌黑名单 DB 故障 **fail-closed 返 503**（`src/middleware/auth.js:196-234`、`tokenBlacklist.js:69-140`）
- 登录口令 ECDH(P-256/P-384) + HKDF-SHA256 + AES-256-GCM 信封，含 ±5min 时间窗与 nonce 原子一次性消费（`src/utils/loginCipher.js:130-225`）
- NoSQL 注入双保险：`sanitizeMongo` 删 `$`/`.` 键 + `queryScalarGuard` 拒绝对象/数组型 query（`src/middleware/security.js:166-201`、`src/utils/queryLimit.js:84-112`）

### 5. 前端安全工程化 ⭐

- **token 全链路 httpOnly Cookie**，前端 JS 不可读（`web-admin/src/utils/api.js:5-14,105`）
- **全局零 `v-html` / `innerHTML`**，XSS 面收敛到框架默认转义
- 401 并发刷新**单飞去重**（`isRefreshing/refreshPromise`），且 `UNCANCELABLE_METHODS` 保护写请求不被 `cancelAllPendingRequests` 误杀 —— 避免"看似未保存实则已落库"的状态错位（`api.js:128-199`）
- Element Plus / ECharts **按需引入**（`vite.config.js:25-94` 深路径解析器），ECharts 实例全部 `onUnmounted` dispose
- 竞态守卫 `useLatestRequest` 在 7 个主要列表视图落地，防响应乱序覆盖

### 6. 防误操作的运维脚本 ⭐

`scripts/restore-mongo.sh:65-81` 三道门禁：回显目标主机/库名 → 交互确认或 `RESTORE_CONFIRM` 匹配 → `--drop` 须显式 `RESTORE_DROP=true`；凭据经 `--config` 临时文件（`umask 077` + `trap` 清理）传递，不进 `ps`/`cmdline`。`scripts/migrate-mfa-secret.js:140` 默认 dry-run，加 `--apply` 才写库。

## 四、风险清单

### 🔴 高危

**H1｜多副本部署时限流 / 黑名单 / 审计链锁整体退化为单实例**

`src/constants/runtime.js:96-129` 的 `detectMultiProcess()` 仅识别 **单进程多 worker**（PM2 `instances`/`NODE_APP_INSTANCE`、cluster、`WEB_CONCURRENCY`、`INSTANCE_COUNT`、`REPLICAS`），对最常见的 **N 个独立容器**（docker-compose scale / k8s replicas，每个容器单进程）**检测不到**——除非运维显式注入 `INSTANCE_COUNT`/`REPLICAS`。

后果链：`src/config/validate.js:102-107` 的 `REDIS_URL` 强制校验不触发 → `src/middleware/rateLimit.js:39-55` 的 `makeSharedStore` 返回 `undefined` → express-rate-limit 回退**每实例一份 MemoryStore**；登录 nonce 去重（`loginCipher.js:219`）与审计链锁同理。

> **攻击场景**：把登录爆破请求均匀打散到 N 个副本，每副本只看到 ≈1/N 的尝试，永远触不到 `loginLimiter`(10/15min) 与自动 IP 封禁阈值 → **分布式暴力破解绕过**。多实例并发写审计链还可造成链分叉、完整性校验误报。

**修复**：生产环境（`NODE_ENV=production`）**无条件强制** `REDIS_URL`，缺失则 fatal 退出（与弱密钥同级），不依赖 `detectMultiProcess` 探测。

---

**H2｜审计日志 / 用户 / 角色 / 权限接口缺失数据范围过滤（部门级越权）**

已验证：`src/controllers/auditController.js` 全文**无** `getDataScope` / `applyDataScopeToQuery` / `assertRecordInScope`（grep 确认为空）。而 `src/routes/securityRoutes.js:220-252` 的 `/audit-logs`、`/export`、`/verify` 仅挂 `checkPermission('security:audit')`。

对照组：`src/services/AlarmService.js:15,53,332` 与 `DeviceService.js:53`、`InspectionService.js:56` 均正确接入了数据范围。

> **影响**：RBAC 承诺"level≥7 仅本部门、≥5 仅本人"。持有 `security:audit`（典型为 level 8 安全管理员）的用户访问 `/api/security/audit-logs` 与 `/export`，会**读出并导出全组织所有用户的审计日志**，部门级数据范围形同虚设。`/api/users`、`/api/roles`、`/api/permissions` 列表同理。

**修复**：在 `auditController.queryAuditLogs/exportAuditLogs` 与 user/role/permission 列表控制器中按 `getDataScope(req.user.userId)` 注入 `applyDataScopeToQuery`（审计日志按 `userId` 字段过滤属主/部门）。

---

**H3｜数据范围过滤字段缺索引 → 生产全表扫描**

| 模型                       | 已定义属主字段                                  | 现有索引                                                                                    | 缺失                                          |
| -------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `src/models/FireAlarm.js`  | `reporter.userId`(:64)、`location.building`     | `:139-143` 仅 occurredAt / status / handler / level / alarmType                             | **`reporter.userId`、`location.building`**    |
| `src/models/FireDevice.js` | `createdBy`(:171)、`maintenanceRecord.operator` | `:182-186` deviceType+status / building+floor / lifecycleStage / expiryDate / nextCheckDate | **`createdBy`、`maintenanceRecord.operator`** |
| `src/models/Inspection.js` | `locations.building`                            | `:153` 有 `assignedTo`                                                                      | **`locations.building`**                      |

数据范围口径来自 `src/constants/dataScopeFields.js:21`。列表/详情/统计/导出均按这些字段过滤，缺索引即 COLLSCAN，且**越权过滤本身也依赖这些字段**，性能问题会诱发"为提速而绕过过滤"的后续风险。

---

**H4｜跨集合写几乎无事务，且单机部署降级为无回滚**

全仓 51 处写点**仅 1 处**使用事务：`src/services/DeviceService.js:226`。

且 `src/utils/transaction.js:43-52`：

```js
// MongoDB standalone 拓扑：withTransaction 降级为顺序写，
// 多集合一致性依赖应用层写入顺序（生产请部署副本集）
return fn(null);
```

即项目默认部署形态（dev/test/单机）下**顺序写、无回滚**。跨集合写场景（createUser+角色、assignRoles、MFA 双写+审计、IP 名单+审计）任一步失败即残留幽灵数据——最危险的是**写成功但审计落空**。

**M2｜全局审计中间件依赖拦截 `res.json`/`res.send`，存在漏记盲区**

`src/middleware/security.js:621-633` 的 `auditLog` 通过**重写响应方法**触发写库。若控制器用 `res.redirect()` / `res.end()` / 流式响应返回，则不经过被重写的出口 → **该次操作不进审计**，与"全量审计"承诺不符。

**修复**：改用 `res.on('finish')` 统一采集，不依赖具体响应方法。

**M3｜生产明文 HTTP / Host 头未配置仅告警不阻断**

`src/config/validate.js:43-50`：`ENABLE_HTTPS !== 'true'` 仅 `warnings.push`，**不** `errors.push`，进程照常启动；`:31-37` 的 `ALLOWED_HOSTS` 同样仅告警。`src/middleware/protocolCompliance.js:151` 的 Host 校验 `if (allowedHosts.length > 0)` 才生效。

> 若服务直连暴露（无反代终结 TLS），令牌与 httpOnly Cookie 以明文传输 → 会话劫持；Host 头未校验 → 缓存投毒 / 密码重置链接投毒。`loginCipher` 的 ECDH 信封在主动 MITM 下可被替换公钥（代码注释已承认此点）。

## 八、结论

**这个项目最值得肯定的是"诚实的工程态度"** —— 代码里主动标注 v2 链盲区、Redis 回退语义、单进程锁假设、CBC 默认关闭；`jest.config.js` 里记录了"门槛形同虚设→重设基线"的完整反思；运维脚本宁可麻烦也要加三道防误删门禁。这些比任何架构图都更能说明工程质量。

**它现在最需要的不是写更多功能，而是把已承诺的约束闭环**：

- **数据范围**是 RBAC 的核心承诺，但只覆盖了 device/alarm/inspection 三个业务实体，审计/用户/角色/权限这四个**恰恰最敏感**的模块反而没接 —— 这是本次发现的最实质的安全缺口。
- **文档**是项目最容易被低估的资产，也是当前最脆弱的一环：6 处矛盾里，D1 让人以为项目还在 Express 4，D2 让人以为测试门禁是坏的，D3 说明连评价报告本身都会过期。**建议把文档一致性纳入 CI**（例如校验 README/CHANGELOG 中的版本号、覆盖率数字与配置实际值一致）。

评分 8.0 的含义是：**设计与实现已达 8.5 分水准，扣掉的 2 分中，约 1.2 分来自"架构约束未闭环"（H1-H4），0.8 分来自"文档滞后"（第六节）**。这两块都是可以在 1-2 个迭代内补齐的，且补完后项目整体可信度会有不成比例的提升。
