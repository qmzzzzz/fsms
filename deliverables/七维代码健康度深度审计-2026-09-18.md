### 2.1 F-02：数据范围越权（调用生产函数 `DeviceService.getDevices`）

```
self 范围, 无 search         → 条数=1  count=1  → B自己的设备
self 范围, search="A"        → 条数=2  count=2  → A的灭火器 / A的烟感器
department(2号楼)+search="A" → 条数=0
>>> self 用户经 search 看到他人(createdBy=A)设备 2 台（含名称/编号/楼栋/楼层）
```

机制：`applyDataScopeToQuery` 对 `device` 的 `self` 范围写入 `query.$or = [{createdBy},{maintenanceRecord.operator}]`（`constants/dataScopeFields.js:21` 属主声明为数组），`DeviceService.js:59` 随后无条件 `query.$or = [正则,正则]` 覆盖。出厂角色 `FIREFIGHTER`（`initData.js:410` level 4）经 `rbac.js:196` 恰落入 `self` 档并持有 `device:read`。`department` 范围因写的是普通键而幸免；报警/巡检因属主为单字段而暂不受影响——**这是巧合安全，不是设计安全**（`AlarmService.js:59`、`InspectionService.js:62` 是同一段代码的第 2、3 次复制）。

#### 3.5.1 接缝盲区：为什么 3,542 条用例没发现 F-30（本轮补做前端与 e2e 测量的新发现）

F-30（实时层握手永不认证）之所以能在 171 套件 + 84 个前端测试文件下存活，根因不是「缺测试」，而是**跨进程契约的两侧各自 mock 了对方**：

- 前端 `web-admin/src/tests/utils/websocket.test.js:25-26` 把 `socket.io-client` 整体换成 `ioMock`，文件头声明覆盖「io() 参数：握手凭证设置确实被传递」；我在该文件中 grep `path|cookie|auth` **零命中** —— 它断言的是「我把 options 交给了 io()」，而不是「浏览器会不会带 cookie」。
- 全仓**没有任何一条**测试同时持有「cookie 的 Path」与「socket.io 的 path」这两个事实（`grep -rn "socket.io" src/tests | grep -i "cookie\|path"` 零命中）；`e2e/*.spec.js` 里 socket 相关引用 **0 处**。

同一模式还解释了另两处存活缺陷：`api.js` ↔ `routes/*.js` 的字段契约（`openapiSync` 只比端点存在性，不比 `requestBody` 与校验器同源 → 30+ 处漂移全绿）、`usePermissionSync` ↔ `emitRoleUpdate`（两侧各自测自己的收发，中间的事件名与房间投递从未端到端验证）。

```
守卫遍历源 = PAYLOAD_FIELDS_V3（25 项）
反方向（schema 有、payload 没有）应为空，实际漏掉：
  targetType, targetId, dataType, description          ← 真实缺口 4 项
  clientInfo.browser/os/device, location.country/province/city  ← 由父对象整体参与哈希，属误报
```

这正是 P1-12 那次「补 schema 字段忘了补哈希清单」能静默通过全 CI 的机制：**守卫与被校验的数据同源，等价于恒真断言**。修法必须是 `Object.keys(AuditLog.schema.paths)` 减去一个**显式白名单**（`hash/hmac/prevHash/hashVersion/_id/__v/createdAt/updatedAt` + 参与哈希的父对象展开路径）后 ⊆ `PAYLOAD_FIELDS_V3`，方向反过来，且新增字段默认「必须进清单，否则红」。

**同一手法应立即补的另两条契约测试**：① `PAYLOAD_FIELDS_V3 === PAYLOAD_FIELDS_V2` 目前是**同一数组引用**（`auditChainPayload.js:47`），将来给 V2 追加字段会静默改变 V3 语义 —— 断言两者必须是不同快照；② `securityAlertDelivery.isWebhookTargetAllowed` 用一组真实/构造地址做纯函数单测（`169.254.169.254`、`100.64.0.0/10`、`fd00::/8`、`::ffff:127.0.0.1`、十进制/八进制/短写 IPv4 变体、以及"域名解析后落在内网"的形态），这是 SSRF 防线的唯一有效回归形式。

**反向指标（耦合热点）**：`models/User.js` 被 67 个测试文件直接引用、`models/Role.js` 51 个 —— 模型是全局接缝，任何 schema 变更会同时打红几十个文件，这也是 `mockRestore` 泄漏与顺序耦合难以排查的放大器；配合 86/171 文件各自复制一份"连接守卫"、40 文件各自签 JWT、29 文件复制同一串号去重技巧，**测试自身的 DRY 债务显著高于生产代码**。

## 4. 前端专章（web-admin，61 个源文件 / 21,284 行）

**先给应得的肯定（全部经我独立扫描核对）**：`src/` 非测试代码中 **`v-html` / `innerHTML` / `insertAdjacentHTML` / `document.write` / `eval` / `new Function` 零命中**（`vue/no-v-html` 为 ESLint error 级硬门禁）；`console.log` **零残留**（我实测计数 0）；`vite.config.js:652` 显式 `sourcemap:false`；无事件总线（只有 props/emits + Pinia + socket 三条通道）；全部路由懒加载；上报侧 `redactUrl` 同时打码 query 与两种 hash 形态并解释了「今天没有、明天加个回调链接就泄露」的取舍；vitest 覆盖率实测 `src/utils` 98.77%、`src/views` 95.4% 且阈值是真门禁（92/84/90/93）。这套「看得见的安全卫生」在同类管理后台里属前 5%。

**但三个「声称的能力」实际不成立**：

1. **[F-30 · Critical] 实时层从未认证成功。** `src/utils/cookie.js:22` 把 access cookie 限在 `Path=/api`，`websocketService.js:116-128` 建 `socketIo()` 时**没有设 `path`** → 握手走默认 `/socket.io/`；`extractHandshakeToken`（`:335-343`）先取 `handshake.auth.token`（前端 `websocket.js:17-33` 的 options 里根本没有 `auth` 字段），再取 cookie 头里的 `access_token`（RFC 6265 下 `/api` 的 cookie 不会随 `/socket.io/` 发出）→ 返回 null → 30 秒 `AUTH_TIMEOUT` 后 `emit('auth-error') + disconnect(true)`，重连 5 次同样失败。前端注释（`websocket.js:29-31`）恰恰写着「后端 websocketService 优先读握手请求头 cookie，无需再 emit 令牌」——**这是必现而非竞态**。后果链：`permission-sync` 永远收不到（叠加 F-32 使权限快照永久陈旧）、`role-updated` 收不到（多管理员互不可见）、`RoleView.vue:374-381` 弹一条**永不消失且刷新无效**的「实时推送已中断」、后端每 30 秒自造一条 warn。修法（前端一处决策即可闭环）：后端把 socket.io 挂 `path: '/api/socket.io'`（cookie path 命中，`nginx.conf.example:158` 与 `vite.config.js:601` 同步），或增设一次性短时效握手票据端点 + 前端 `auth:{token}`；`usePermissionSync` 应处理 `auth-error` 并降级为轮询 `/auth/me`，而不是静默。

2. **[F-31 · High] httpOnly 抗 XSS 的前提被自己的响应体击穿。** `authController.js:185-197` 与 `:246-259` 在 Set-Cookie 之外**仍把 `token` 与 `refreshToken` 放进 JSON 响应体**，注释自陈是为「兼容现有测试与 API 消费者」。而 `web-admin/src/store/storage.js:13-16`、`api.js:5-9`、`auth.js:36-39` 三处注释都据「JS 不可读」下了「XSS 无法窃取令牌」的结论。只要出现任意一个 XSS 原语，攻击者 `fetch('/api/auth/refresh',{credentials:'include'})` 即可从 JSON 里读到**新的 access + 有效期 7 天的 refresh**，此后轮换刷新，等同账户接管且受害者改密前不掉线。修法：删掉两个响应字段（前端本就不需要——`LoginView.vue:347` 解构后把值传给 `setAuth` 却忽略），同步 `schemas/index.js:92-93` 与 `setAuth` 的占位参数；在删掉之前，至少把三处注释改成诚实表述。

3. **[F-32 · High] 权限快照在页面生命周期之外永不刷新。** `store/auth.js:193` 的 `restoreSession()` 首行 `if (this.currentUser) return true`，而 `currentUser`/`permissions` 存在 localStorage、跨标签页与跨刷新共享 → 正常路径下 `/auth/me` **一次都不会被调用**；唯一的权限刷新通道是那条永不认证的 WS。真实越权不会发生（`rbac.js` 每次查库），但被降权者的菜单/按钮/守卫判据在最长 7 天内保持原样，`messages.permissionsUpdated`（「界面已自动更新（无需重新登录）」）是一句永远不会出现的文案。修法：`restoreSession` 加 TTL（写入时间戳，超 5 分钟强制重取），或布局 `onMounted` 无条件发一次带 `silent401` 的权限刷新。

## 7. 结论

这个仓库的**意图与执行都明显优于平均水平**：零 CVE、密钥卫生与日志脱敏经得起逐字节核对、真密码学而非装饰性加密、96.69% 行覆盖配 36 条按文件校准的阈值、`/health` 与 `/readyz` 正确分离、`app.param` 穿透这类 Express 5 真问题被独立发现并修对。

但把它定位为「权限管控 + 合规审计」系统的两条腿，当前都是断的：

- **权限**：垂直方向（能不能做这个操作）基本经得起证伪；水平方向（能对哪些记录做）不成立，而且有一条默认角色即可走的**垂直提权链**（F-01）和一条已实证的**数据范围越权**（F-02）。104 个端点全都挂了权限中间件——问题从来不是「忘了挂」，而是「挂了但校验的维度不对」。
- **审计**：append-only 钩子、链式 HMAC、WAL、逐字段签名，组件都在；但四个取证字段不参与哈希（F-04）、置空 hash 即洗白（F-06）、WAL 是未签名的签名预言机（F-07）、尾部截断与记录插入不可检出，而 `intact:true` 对外承诺位对这四类全部沉默。合规意义上的「防篡改」当前只是「防住了一部分随手改」。
- **运行能力**：三个被文档与注释宣称的能力实际为零 —— 实时推送/权限热同步因 cookie path 与握手路径不匹配而**从未认证成功过**（F-30），火警房间没有任何生产发射方（F-24），告警投递端是占位 URL 且无 dead-man switch（F-25）。三者共同的失效特征是：**界面与监控都显示正常**（后端仍返回 200、测试仍全绿、Alertmanager 仍启动成功），所以缺陷只会在真正需要它的那一刻暴露。

结构性根因是**多轮按条目整改累积出的补丁型安全栈**：每轮把一个点修得很深（连注释都带着实测数据和被否决方案），但很少回头收口「同一个威胁模型还剩哪些面」。`metricsAuth.js` 已经写下了正确的攻击模型（「直连端口的攻击者只需发送 `X-Forwarded-For: 127.0.0.1`」），这句话却只用于 `/metrics` 一个端点；`applyDataScopeToQuery` 自称「唯一收敛点」，同一函数族的 `buildDataScopeFilter` 仍在被裸用于统计与导出。因此建议下一轮整改的原则是：**以收敛点为单位删除并行实现，而不是以端点为单位补检查**——本次 10 项 Critical 中有 5 项（F-01/F-02/F-03/F-04/F-12）在并行实现被合并后是自然消失的，另有 1 项（F-30）是纯粹的「注释里的结论没有对过一次运行时事实」。
