一、审计结论概览

总体评价：这是一个工程质量明显高于平均水准的 RBAC 权限管控型业务系统。七个维度得分普遍在 8.5～9.5 之间，无高危缺口（依赖审计 0 漏洞、无高危越权、无密钥泄露），安全性与可观测性维度尤其突出。项目大量采用「fail-closed」原则（权限校验失败默认拒绝）、时序侧信道防护、原子化防重放、审计哈希链等企业级做法，且每个安全决策都附有详细注释说明「为什么」。系统具备直接投入生产使用的条件，剩余问题均为工程完善类而非阻断类。

1. 代码质量与规范性

9.0 / 10
可读性复杂度控制DRY注释质量
  • 命名与一致性：全库使用语义化命名（如 walTrimLines、unshiftChunked、applyDataScopeToQuery），缩进统一 2 空格（.editorconfig / .prettierrc 约束），ESLint + Prettier 双门禁。
  • 复杂度控制：核心模块（authService 40KB、security 中间件 31KB）虽有体量，但内部按功能拆分清晰、函数职责单一；对 V8 参数上限（unshift(...docs) 数十万级 RangeError）、bcrypt 超长输入等隐蔽复杂度陷阱均有针对性处理。
  • 注释质量：项目最大的亮点之一。关键业务逻辑均解释「为什么」（如 JWT 算法锁定原因、审计 WAL 前缀裁剪不整文件截断的原因、fail-closed 决策），不是流水账式注释；注释与代码同步更新（多次看到注释标注修复批次号）。
  • DRY：错误码集中注册表（src/utils/errorCodes.js）、审计留存天数单一声明（constants/retention.js）、label 映射单一来源等，重复逻辑均已合理抽象。

2. 架构设计与工程结构

9.0 / 10
分层解耦模块化配置外部化设计模式
  • 分层清晰：路由（11）→ 控制器（9）→ 服务层（19）→ Mongoose 模型（12）四层；请求级中间件链（requestId → metrics → Sentry → IP黑名单 → CORS → 安全头 → 限流 → 查询防护 → morgan → 审计）职责单一。
  • 模块化：服务层覆盖会话、权限、验证码、审计缓冲、设备/告警/巡检业务，高内聚低耦合；多实例状态外置（sharedCache + Redis 回退）有专门 ADR-005 记录。
  • 设计模式应用：中间件链、AsyncLocalStorage（请求上下文）、单例/工厂、状态机（设备生命周期）等使用克制，无过度设计。
  • 配置外部化：全部密钥走 *_FILE 注入或环境变量，生产启动强校验（config/validate.js 拦截弱密钥/危险配置）；无魔法数字泛滥（阈值均具名常量）。
发现（技术债，作者已自认）：架构文档注明「部分控制器直连模型」（原优化清单 D-1），新功能已强制经服务层。此债不影响当前正确性，但后续维护需收敛。

3. 安全性

9.5 / 10
认证授权输入验证敏感数据依赖安全

本维度是项目最强项，呈现典型纵深防御（Defense in Depth）：

安全域实现情况
口令传输前端 WebCrypto ECDH（P-256/P-384）+ HKDF + AES-256-GCM 信封加密，时间戳窗口 + 一次性 nonce 防重放；密文轨/明文轨灰度，strict 模式拒绝明文
口令存储bcrypt 加盐哈希；哑口令摘要对齐比对耗时（防时序侧信道用户枚举）
登录防护三层限流（IP/用户/登录专用）、图形验证码开关、失败计数原子递增、≥10 次锁定 10 分钟、统一响应防用户名枚举
会话与令牌JWT 算法锁定 HS256（防 alg:none）；access 2h / refresh 7d 分离；黑名单 + tokenVersion 全局吊销 + 设备级会话（踢单设备）；refresh 原子消费防重放；改密后全会话吊销（fail-closed）
MFATOTP + 恢复码；seed 以 AES-GCM 加密落库（enc:v1:）；验证码原子条件更新防重放；防爆破锁定
授权（RBAC）菜单/按钮/接口三级权限；实时从库加载角色（不信任 token payload）；数据范围按角色 level（全部/本部门/本人）过滤且对空部门显式 deny，防横向越权
Web 层Helmet + CSP(nonce)、NoSQL 注入防护（$ 与 . 键清理）、HPP 防护、CSRF（SameSite=Lax + JSON-only）、IP 黑/白名单（CIDR）、敏感操作二次验证
审计与取证写操作全量审计；SHA-256 哈希链 + HMAC 认证（防篡改）；WAL 落盘兜底；敏感字段脱敏；留存天数合规区间校验
密钥管理Docker secrets 挂载（非环境变量）、.gitignore/.dockerignore 双排除、CI Gitleaks 密钥扫描、AES/HMAC/JWT 密钥分离
依赖安全npm audit = 0 vulnerabilities（官方 registry 实测）；CI 独立 security-audit job 对前后端均执行
发现（轻微）：本地 .env 中 JWT_EXPIRE=24h 与代码默认 2h 不一致（本地开发配置，非生产风险，但建议统一口径避免误用）；审计链采用「单进程锁」假设（ADR-004 已显式记录边界），多实例并发写链需依赖外置锁，Redis 模式下已接分布式锁。
证据：src/middleware/auth.js / rbac.js / security.js、src/services/authService.js、src/utils/auditChain.js、docker-compose.yml

4. 性能与资源效率

8.5 / 10
查询效率缓存批量写入容量保护
  • 数据库交互：高量级列表采用游标分页（ADR-006，避免 skip 深分页性能劣化）；审计日志缓冲批量 insertMany（非高频事件型审计直写以保证暴力破解检测即时性）。
  • 缓存策略：统计类接口 statsCache（TTL + maxSize + 清理周期）；权限结果 userPermissionService 缓存；sharedCache 支持 Redis 跨实例失效广播（多实例一致性）；登录公钥、验证码等均带限流防滥用。
  • 容量保护：审计缓冲硬上限（防 OOM）、WAL 字节上限（防磁盘写放大）、分块 unshift（防 V8 参数上限）——对极端场景做了充分防御。
  • 并发与异步：WAL 操作串行化在 walChain（防读写竞争）；锁内完成「读尾→串链→落库→推进尾」防幻影链尾；IO 密集路径（日志、审计）均异步化。
发现（需运行期验证）：模型层索引定义存在（unique/index），但审计未在真实数据量下做 explain 验证；控制器直连模型路径未经过服务层缓存，存在个别 N+1 可能性。建议上线前用生产规模数据做 explain() 压测。
证据：docs/adr/ADR-006-高量级列表游标分页选型.md、src/services/auditBuffer.js、src/services/statsCache.js
